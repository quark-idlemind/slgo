Guide · a bot that talks

slbotd with an LLM

Let the bot's avatar hold conversations by IM, through a language model you run yourself with llama.cpp's llama-server. This page covers setting it up, what to do when it stays silent, and where residents' words end up.

~45 min, plus the model download

Read this first

Only llama-server

slbotd talks to one kind of model server: llama-server, from llama.cpp. It does not work with Ollama, and it does not talk to OpenAI, Anthropic or any other hosted API. There is no API key setting anywhere, and it sends no Authorization header. It speaks plain HTTP to a server you run.

The reason is the endpoints. Only one of the four is the chat API that many servers share. The other three are llama.cpp's own:

EndpointWhat slbotd uses it for
POST /v1/chat/completionsWriting a reply. The OpenAI-style call.
GET /propsThe model, its build, its context size and how many slots the server has. slbotd asks on the first reply, and the reply fails if it cannot.
POST /slots/N?action=save|restore|eraseSaving each conversation's cache to disk and loading it back, so a conversation picks up in milliseconds instead of being re-read from the start.
POST /apply-templateRendering the model's chat template, to find out whether the template keeps the memory note.

A server without /props, like Ollama or a hosted API, gets no replies out of slbotd at all, only an entry in :errors for each message. That is worked out from the code rather than tried.

slsh's how feature is different: it works with Ollama too. That is slsh, not slbotd.

Because the model is local, nothing is billed. The limits on this page are about load on your machine, and about making replies arrive at a human pace.

How the pieces fit

Conversation is IMs to the bot's avatar that do not start with the command prefix. Commands keep working exactly as before. Only one-to-one IMs are answered; local chat and group IMs never are.

Set it up

  1. Have slbotd taking commands

    Do Adding slbotd first. Before you add a model, :status should answer.

  2. Get llama-server

    llama-server comes with llama.cpp. The steps below are llama.cpp's, not slgo's. They change from time to time, and llama.cpp's own README at github.com/ggml-org/llama.cpp is the authority. They have not been measured here.

    $ git clone https://github.com/ggml-org/llama.cpp
$ cd llama.cpp
$ cmake -B build
$ cmake --build build --config Release -j
$ ./build/bin/llama-server --version
    $ git clone https://github.com/ggml-org/llama.cpp
$ cd llama.cpp
$ cmake -B build
$ cmake --build build --config Release -j
$ ./build/bin/llama-server --version

    That is the CPU-only build. With an NVIDIA GPU and the CUDA toolkit installed, make the first cmake line cmake -B build -DGGML_CUDA=ON instead.

    Or, with Homebrew: brew install llama.cpp.

    Put llama-server somewhere on your PATH, or call it by its full path. Once it is on your PATH, by copying it there or with brew install, csh, tcsh and zsh need rehash before they find it; in sh or bash, hash -r.

  3. Pick a model

    llama-server loads one model file, named with -m. slbotd has no say in which: its own llm-model setting is passed along and ignored. What the model needs:

    • A GGUF file, the format llama.cpp loads.
    • An instruct or chat model, with a chat template, since slbotd sends chat messages. A base model is the wrong kind.
    • No long reasoning before it answers. "Thinking" models can spend their whole token allowance reasoning and return nothing. slbotd has no way to add a per-request field to turn that off, so pick a model that answers directly, or turn reasoning off on the server side. The server-side option has not been tried here.
    • Small enough to answer in seconds on your hardware. A reply is a few sentences, so a small model goes a long way.

    For reference, the measurements in the repository used Qwen2.5-0.5B-Instruct and Qwen2.5-3B-Instruct, both quantised to Q4_K_M, on an Intel i9 with no GPU. That is what was measured, not a recommendation.

  4. Start llama-server

    Give it a directory to save conversation caches in, and as many slots as you want conversations live at once:

    $ mkdir -p -m 700 ~/.local/state/llama-server/slots
$ llama-server -m ~/models/your-model.gguf \
    -c 8192 -np 4 \
    --slot-save-path ~/.local/state/llama-server/slots \
    --host 127.0.0.1 --port 8080
    -c 8192 -np 4
    The server splits -c evenly among -np slots, so each slot here holds 2048 tokens. That is what the repository's measurements used. slbotd uses every slot the server reports, pins each conversation to one, and when there are more conversations than slots, saves the oldest to disk to make room.
    --slot-save-path DIR
    Where those saved caches go. Without it, replies still work, but every turn adds an error to :errors because the save fails.
    --host 127.0.0.1 --port 8080
    Loopback only. The server has no authentication worth the name here, so keep it there unless you read Where to run it.

    Do not start it with --api-key. slbotd sends no key, so the server would refuse every request.

    Check it is up by asking for the endpoint slbotd asks for first. It answers with a JSON description of the model, which includes total_slots.

    $ curl -s http://127.0.0.1:8080/props

  5. Tell slbotd where the model is, and who to talk to

    Chat needs two things in slbotd.conf: an llm-url and at least one chat line. With only one of them, chat stays off. Add these to the file from the quick start, or build a whole file with the config builder.

    ~/.config/slgo/slbotd.conf (added lines)
    # the base URL: slbotd adds /v1/chat/completions, /props and /slots itself
llm-url   = http://127.0.0.1:8080
# who the avatar will talk to: * is anyone who IMs it
chat      = *
# the character, re-read every turn
backstory = builder ~/characters/builder.txt
# the server's --slot-save-path, if this machine can see it
slot-save-path = ~/.local/state/llama-server/slots

    Leave /v1 off the URL. The backstory file is plain text: who the avatar is and how it talks. A short paragraph is enough to start. See The character.

  6. Check the file

    $ slbotd --check

    Where it said chat: off before, it now shows the model settings. It also prints a line starting PROBLEM: if the chat setup is half done, and one line per backstory with its assembled size, or BROKEN: and the reason. --check does not contact llama-server.

  7. Restart slbotd

    The file is read once, at startup. Stop slbotd and start it again. Look in its log for these two lines, which say chat is on:

    • chatting through http://127.0.0.1:8080, conversations in …
    • will talk to *

    If you see CHAT IS OFF: instead, the line after it says why. See Problem solving. Commands keep working either way.

    Order does not matter. slbotd asks nothing of the model at startup, so llama-server can start before or after it.

  8. Say hello

    IM the bot's avatar something without the prefix, like hello. Then wait. slbotd holds a reply back until a person could have typed it, so with the default pacing a reply can take a minute or more. The avatar shows "typing" while it waits.

    On the first reply the log gains a line starting model that names the model, its slots and the server build. That line means llama-server was reached.

    From a trusted avatar, :chat shows the model, the slots, the backstory path, the chat list and the conversations so far. :forget NAME deletes one conversation for good.

    Where to run it
    
        
    On the slbotd machine is the simple case. Bind llama-server to 127.0.0.1, point llm-url at it, and set slot-save-path to the same directory as the server's --slot-save-path, so :forget can delete the saved cache too.
    
        
    On a GPU machine is fine, with one thing to know: the connection is plain HTTP with no authentication. Everything residents say to the avatar crosses it in the clear, and anyone who can reach the port can use the server and read or overwrite the saved caches, which hold conversations. So either:
    
        
      
          
    • Tunnel it. Keep llama-server on 127.0.0.1 on the GPU machine, and forward the port from the slbotd machine with SSH. slbotd then sees it on its own loopback. (General SSH practice; not something the repository documents.)
      • 
          
    • Or keep it on a network you trust, bound to that network's address only, never to the internet.
      • 
        
    
        
    To forward local port 8080 to llama-server on the GPU machine:
    
        
    $ ssh -N -L 8080:127.0.0.1:8080 you@gpu.example
    
        
    With llama-server elsewhere, leave slot-save-path out of slbotd.conf, since slbotd cannot see that disk. The caches are then left behind when you :forget someone; delete them on the GPU machine by hand.
    
        
    Sharing with slsh
    If slsh's how feature uses the same llama-server, each of its questions lands in a slot slbotd thinks is holding a conversation, and replaces that cache without slbotd knowing. Nothing should break, but as far as the code shows, that conversation's next reply is then read from the start. A cold start was measured at 5.0 s against 0.53 s warm, for a 1442-token conversation on a 0.5B model with no GPU. A separate server for how avoids it.
    
      
    

      
    
        
    Linux and macOS
    
        
    slbotd behaves the same on both. Its config is ~/.config/slgo/slbotd.conf and its conversations are under ~/.local/state/slbotd on macOS as well; it does not use ~/Library.
    
        
    Linux vs macOS, for llama-server
    
          
    This is general guidance about llama.cpp, not measured here. The repository's own timings were taken on an Intel i9 with no GPU, and nothing here compares platforms.
    
          
      
            
    • macOS on Apple silicon: llama.cpp builds with Metal, Apple's GPU interface, by default, and the GPU shares the machine's memory. A model that fits in memory can use the GPU without a separate card.
      • 
            
    • Linux with an NVIDIA card: build with CUDA (-DGGML_CUDA=ON) and install NVIDIA's toolkit first. The model has to fit in the card's memory to be fast.
      • 
            
    • Linux or an Intel Mac without a usable GPU: the CPU build works. Small models answer in seconds; bigger ones get slow quickly.
      • 
            
    • llama.cpp's documentation describes -ngl (--n-gpu-layers) for how much of the model goes to the GPU. Check what your build does by default.
      • 
          
    
        
    
        
    If replies are slow on any platform, the levers slbotd has are a smaller model, a lower chat-max-tokens and a longer llm-timeout.
    
      
    

      
    
        
    The character
    
        
    backstory = AVATAR PATH gives an avatar its system prompt. The AVATAR has to be written exactly as in its avatar line, including case: the startup check ignores case, but the lookup when replying does not, so a mismatch passes the check and then finds no backstory. (Worked out from the code.)
    
        
      
          
    • A file: the whole file is the prompt. slbotd adds one sentence of its own: "You are speaking through instant messages in a virtual world. Reply in a few sentences at most, in character, as speech rather than prose. If you are told how long it has been since they last wrote, remark on it."
      • 
          
    • A directory: default or default.txt is for everyone, and a file named for a person is used when that person is speaking. Only one file is used. Names match ignoring case, with -, _ and spaces treated alike; a uuid works as a file name.
      • 
          
    • Includes: a line that is only ./path or ../path is replaced by that file. A person's file that does not include ./default.txt gets no default character, and nothing warns you; --check shows the assembled sizes.
      • 
          
    • The backstory is re-read every turn, so editing it needs no restart. Everything else in slbotd.conf does.
      • 
          
    • If a backstory cannot be read, the avatar still replies, with no character at all, and no backstory: … goes into :errors.
      • 
        
    
        
    ~/characters/builder/ (a directory backstory)
    default.txt              # everyone
example-resident.txt     # only when Example Resident speaks; its first line is ./default.txt
    
      
    

      
    
        
    The chat settings
    
        
    
          
    KeyDefaultWhat it does
    
          
            
    llm-urlemptyBase URL of llama-server, without /v1. Empty means no chat.
    
            
    chatnoneWho to talk to: a name, a uuid, * for anyone, !name or !uuid to refuse. Repeat the line. A refusal wins over a permission whatever the order.
    
            
    backstorynoneAVATAR PATH, a file or directory. ~ is expanded.
    
            
    llm-modelemptySent as the model name. llama-server ignores it.
    
            
    llm-timeout2mLimit on each HTTP call to the model. The whole reply gets this plus 30 s.
    
            
    chat-jobs2Conversations one avatar answers at once. Past it, a new message gets silence. Separate from jobs, so talk cannot crowd out commands.
    
            
    chat-context1536Token budget for the prompt, at least 64. Crossing it folds old turns into a memory note.
    
            
    chat-keep6Turns kept word for word through a fold. Even, at least 2.
    
            
    chat-summary200Token cap on the memory note, at least 32. Must be under half of chat-context, or chat is off.
    
            
    chat-max-tokens160Longest reply in tokens, at least 16.
    
            
    chat-reply-limit2Most IMs one reply is sent as.
    
            
    chat-temperature0.8Sampling temperature for replies. Summaries always use 0.2.
    
            
    chat-own8How much two avatars this slbotd drives, or one of them and a chat-bot, may say to each other before one stops answering. 0 means they never talk at all.
    
            
    chat-own-rest30mSilence between the two after which the chat-own count starts again. 0 means it never does.
    
            
    chat-botnoneAn avatar another program's model drives, by name or uuid, one a line. Bounded by chat-own like this daemon's own avatars.
    
            
    llm-slots0 (all)Use only the server's first N slots, leaving the rest to another program that sends id_slot for them.
    
            
    chat-gap1hAfter this much silence the model is told how long it has been. The hint is sent, not stored.
    
            
    chat-dir~/.local/state/slbotdWhere conversations are kept (under $XDG_STATE_HOME if that is set).
    
            
    slot-save-pathemptyThe server's --slot-save-path, as this machine sees it. Only used to delete a cache on :forget.
    
            
    read-cps23.0Characters a second the avatar "reads" at. read-cps = builder 12 sets one avatar.
    
            
    type-cps3.2Characters a second it "types" at. Can be set per avatar the same way.
    
            
    pace-max0Ceiling on the whole wait, as a duration like 45s. 0 is off.
    
              
        
    
        
    Most keys also take an underscore spelling, like llm_url. Per-avatar speed lines are not checked against the avatar list, so a misspelt name quietly uses the default speed.
    
        
    Sizing against the server
    
        
    Each slot holds -c divided by -np tokens. The prompt, up to about chat-context, and the reply, up to chat-max-tokens, should fit in one slot together. The defaults, 1536 plus 160, fit in the 2048 of -c 8192 -np 4. (That rule is worked out from the code, not measured.)
    
        
    Memory
    
        
    When a conversation outgrows chat-context, the older turns are folded into a three-line note by an extra model call, and the last chat-keep turns stay word for word. The backstory is never part of the fold, so it cannot be lost to it. :chat shows the note.
    
      
    

      
    
        
    Pacing
    
        
    slbotd waits as long as a person would. First it is silent for the length of the message divided by read-cps. Then it shows "typing" for up to the length of the reply divided by type-cps. The time the model takes counts toward the wait.
    
        
    With the defaults a long reply is slow on purpose: the repository's guide puts a 160-token reply at 3.2 characters a second at about four minutes. To shorten it, lower chat-max-tokens first, which gives shorter replies; raising type-cps or setting pace-max also works.
    
        
    Two avatars on the same slbotd will talk to each other if both are on each other's chat list. Before chat-own existed, one message led to 26 exchanges in ninety seconds. chat-own stops that after 8 by default, until the two have been quiet for chat-own-rest (30 minutes); or refuse the other avatar with !. An avatar driven by another program's model, such as an LLM client of your own, is bounded the same way once it is named with chat-bot.
    
      
    

      
    
        
    Problem solving
    
        
    A resident whose message could not be answered gets silence, never an error. The reason is in slbotd's log and in :errors, as could not answer …:  followed by the cause. Parts shown as … vary.
    
        
    
          
          
          
          
          
          
        
    

        
    
          Startup says CHAT IS OFF: chat names somebody to talk to but no llm-url says where a model is, so nothing will be answeredlog
          
    
            
    Why
    There is a chat line but no llm-url. Chat needs both. It is logged at every start and is not fatal: commands still work. :chat says no model is configured; this avatar answers commands only.
    
            
    Fix
    Add llm-url = http://127.0.0.1:8080 (your server's address) and restart slbotd.
    
          
    
        
    

        
    
          Startup says CHAT IS OFF: llm-url names a model but no chat line says who may be answered, so nothing will be answeredlog
          
    
            
    Why
    There is an llm-url but nobody to talk to. Being trusted does not put someone on the chat list; they are separate lists.
    
            
    Fix
    Add chat = * for anyone, or a chat line per person, and restart.
    
          
    
        
    

        
    
          Startup says CHAT IS OFF: chat-summary is … tokens and chat-context only …; the summary has to be well under the budget or there is no room left to talklog
          
    
            
    Why
    chat-summary must be less than half of chat-context.
    
            
    Fix
    Raise chat-context or lower chat-summary. The defaults, 1536 and 200, are fine. slbotd --check shows the same thing as a PROBLEM: line.
    
          
    
        
    

        
    
          slbotd will not start: line 7: unknown setting "llm-ulr"startup
          
    
            
    Why
    A key slbotd does not know. Any unknown key is fatal, which is how typos get caught.
    
            
    Fix
    Correct the key on that line. The chat settings lists the right spellings. There is no key for an API key, because none is used.
    
          
    
        
    

        
    
          No replies; :errors has could not answer …: the model at http://127.0.0.1:8080: …connection refused:errors
          
    
            
    Why
    Nothing is listening at llm-url. llama-server is not running, is on another port, or is bound to another address. The part after the URL is Go's network error; its exact wording was not recorded here.
    
            
    Fix
    Start llama-server, and check that the host and port in llm-url match its --host and --port. From the slbotd machine this should answer:
    
            
    $ curl -s http://127.0.0.1:8080/props
    
          
    
        
    

        
    
          could not answer …: GET /props: 404 …, or Ollama does not work:errors
          
    
            
    Why
    Either llm-url ends in /v1, so slbotd asks for /v1/props, or the server is not llama-server. Ollama and hosted APIs have no /props and no /slots. (The exact text here is worked out from the code.)
    
            
    Fix
    Use llama-server, and give the base URL only: llm-url = http://127.0.0.1:8080.
    
          
    
        
    

        
    
          could not answer …: GET /props: 401 …:errors
          
    
            
    Why
    llama-server was started with --api-key. slbotd never sends a key. (Worked out from the code.)
    
            
    Fix
    Start llama-server without --api-key, bound to loopback, and reach it through an SSH tunnel if it is on another machine. See Where to run it.
    
          
    
        
    

        
    
          could not answer …: … context deadline exceeded or Client.Timeout exceeded:errors
          
    
            
    Why
    The model took longer than llm-timeout (2 minutes by default) for one call. The model is too big or too slow for the machine, or the server is busy with other slots. (The exact wording is Go's, and was not recorded here.)
    
            
    Fix
    Use a smaller model or put it on a GPU, lower chat-max-tokens, or raise llm-timeout.
    
          
    
        
    

        
    
          the model said nothing at all, or the model answered with no choices at all:errors
          
    
            
    Why
    The model returned an empty reply. The usual cause is a reasoning model that spent all of chat-max-tokens thinking.
    
            
    Fix
    Use an instruct model that answers directly, or turn reasoning off on the server. Raising chat-max-tokens can help, at the cost of slower replies.
    
          
    
        
    

        
    
          Replies work, but every turn adds could not keep the context for …: POST /slots/0?action=save: …:errors
          
    
            
    Why
    llama-server has nowhere to save slot caches. Replies still go out, but conversations resume slower, and these errors fill :errors (up to 50) and set off the trouble notice for trusted people.
    
            
    Fix
    Restart llama-server with --slot-save-path DIR, a directory that exists.
    
          
    
        
    

        
    
          Log says the kept context for … would not load (…); starting it againlog
          
    
            
    Why
    A saved cache could not be loaded. It happens after changing the model, the server build, the context size or the backstory, because each cache carries a fingerprint of all of those and one that no longer matches is not used.
    
            
    Fix
    Nothing to fix. The conversation text is kept separately; the next reply reads it from the start, which costs a few seconds once.
    
          
    
        
    

        
    
          could not clear slot …log
          
    
            
    Why
    slbotd erases a slot before giving it to a different conversation, and the server refused.
    
            
    Fix
    Check llama-server's own output, and that it is llama-server and not something else on that port.
    
          
    
        
    

        
    
          could not summarise the conversation with … (…); dropped the oldest exchanges instead:errors
          
    
            
    Why
    The model call that folds old turns into the memory note failed. The reply still went out, but that conversation lost its oldest turns instead of keeping a note of them.
    
            
    Fix
    Look at the cause after the parentheses. Usually it is the same server trouble as the other entries here.
    
          
    
        
    

        
    
          It ignores someone; log says not answering …: not in the chat list or refused in the list by namelog
          
    
            
    Why
    That person is not on a chat line, or is refused with !. Names are matched ignoring case against the legacy name the grid sends, not the display name.
    
            
    Fix
    Add them with chat = Name or their uuid, or use chat = *. A ! line always wins, so remove it if you meant them to be answered.
    
          
    
        
    

        
    
          Nothing in the log at all for a messagechat
          
    
            
    Why
    Only one-to-one IMs are answered. Local chat and group IMs never are. And a message that starts with the prefix, :, is a command, not conversation.
    
            
    Fix
    Send a one-to-one IM that does not start with :.
    
          
    
        
    

        
    
          Some messages get no reply; log says too busy talking to answer …log
          
    
            
    Why
    The avatar was already answering chat-jobs conversations (2 by default). Past that a message gets silence by design.
    
            
    Fix
    Raise chat-jobs, and give llama-server enough slots (-np) for the extra conversations.
    
          
    
        
    

        
    
          Two of the bot's avatars stop talking to each other: which this daemon drives as well, and they have said … things to each other alreadylog
          
    
            
    Why
    chat-own (8 by default) stops two avatars this slbotd drives, or one of them and a chat-bot, from talking forever. The message ends by saying how long they must be quiet before the count starts again (chat-own-rest, 30 minutes by default).
    
            
    Fix
    Working as designed. Wait out the rest, raise chat-own for longer exchanges, or shorten chat-own-rest. chat-own = 0 means they never talk at all.
    
          
    
        
    

        
    
          Replies arrive minutes later, after a long "typing"pacing
          
    
            
    Why
    Pacing. The reply is held until a person could have typed it at type-cps, 3.2 characters a second by default. 600 characters works out at a little over three minutes.
    
            
    Fix
    Lower chat-max-tokens for shorter replies, raise type-cps, or set pace-max = 45s to cap the wait. See Pacing.
    
          
    
        
    

        
    
          The avatar has no character; :errors has no backstory: …, or --check says BROKEN: …:errors
          
    
            
    Why
    The backstory file is missing or unreadable, an include is missing, or includes loop. The avatar replies anyway, with no character.
    
            
    Fix
    Run slbotd --check; it shows each backstory's size or what broke. Fix the path; the next reply picks it up without a restart.
    
          
    
        
    

        
    
          The backstory is set and --check accepts it, but replies have no characterconfig
          
    
            
    Why
    The avatar in the backstory line is written with different case from its avatar line. The check ignores case; the lookup does not. (Worked out from the code.)
    
            
    Fix
    Write it exactly as in the avatar line, then restart.
    
          
    
        
    

        
    
          could not write the conversation with …: …:errors
          
    
            
    Why
    slbotd cannot write to its conversation store, chat-dir.
    
            
    Fix
    Check that the directory, ~/.local/state/slbotd by default, exists and belongs to the user slbotd runs as.
    
          
    
        
    

        
    
          Conversations sometimes restart slowly after slsh's how was usedllama-server
          
    
            
    Why
    slbotd uses every slot the server has. A how question sent to the same server overwrites one conversation's cache, and slbotd does not know, so that conversation's next reply is read from the start.
    
            
    Fix
    Give how a server of its own.
    
          
    
        
    
      
    

      
    
        
    Privacy and safety
    
        
    Where residents' words go
    
        
    With chat = *, everyone who sends the avatar a one-to-one IM is talking to your model. Nothing in slbotd tells them that; telling them is up to you. Their words go to:
    
        
      
          
    • llama-server, over HTTP, with the backstory, the memory note and the kept turns. The sender's name is not added by slbotd; the model knows it only if they said it or a per-person backstory does. (Worked out from the code.)
      • 
          
    • The conversation store, ~/.local/state/slbotd/AVATAR/THEIR-UUID.json: every turn with a timestamp, and the memory note. Kept forever. Nothing expires it. A file slbotd cannot read is renamed THEIR-UUID.json.unreadable-TIME beside it and kept as well; :forget does not remove those.
      • 
          
    • The saved caches in llama-server's --slot-save-path, also kept until deleted.
      • 
          
    • slbotd's log, unless you start it with -q. -q leaves conversation lines out; commands, decisions and connection events are still logged.
      • 
          
    • Things the avatar says through another client, such as you typing in slsh, are recorded into an existing conversation too.
      • 
        
    
        
    :forget NAME deletes one conversation for good, and its saved cache if slot-save-path is set. Otherwise prune the store by hand.
    
        
    Prompt injection
    
        
    Anyone on the chat list can type instructions at the model. The model has no tools and no way to run a command: its reply is only ever sent as IM text back to the person who spoke, and slbotd never answers its own IMs. So an injected instruction can change what the avatar says, and nothing else. (Worked out from the code.) What it can realistically do:
    
        
      
          
    • get the model to reveal the backstory, including anything a per-person file says about other people. Do not put in a backstory what you would not want read out;
      • 
          
    • get it to repeat that person's own memory note;
      • 
          
    • get it to say something offensive under your avatar's name, which you answer for under the grid's rules.
      • 
        
    
        
    Each conversation is kept per avatar and person, so one person's memory is not in another's prompt, and a slot is erased before it passes to someone else.
    
        
    Programs
    
        
    Chat never runs programs. Commands do, for trusted people. A program line runs an executable with the words the sender typed as its arguments. There is no shell, but there is no sandbox either: it runs as slbotd's user, with slbotd's whole environment. Never point a program line at a shell, an interpreter or a general tool like sh, python or curl. That turns "trusted in world" into "a shell on this machine".
    
        
    The model server
    
        
    llama-server has no authentication in this setup. Anyone who can reach its port can use it and read or overwrite the saved caches, which hold conversations. Keep it on loopback, or behind an SSH tunnel. The security page covers the rest of the system.
    
      
    

      
    
        
    What you now have
    
        
      
          
    • llama-server running a model you chose, on loopback or behind a tunnel.
      • 
          
    • The bot's avatar answering one-to-one IMs from the people on its chat list, in character, at a human pace.
      • 
          
    • Conversations remembered across weeks through the memory note, and resumed quickly through saved caches.
      • 
          
    • Commands working as before, separately limited.
      • 
          
    • A list of where residents' words are stored, so you can tell them, and prune it.
