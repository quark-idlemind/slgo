Helper · client machines only

sl-host

A small helper for a laptop that reaches slgod at different addresses in different places. It looks at which network the laptop is on and prints the address to use there. Most setups do not need it.

new usersexisting users~10 min

What it is

sl-host prints the address of the machine slgod runs on, as seen from whichever network this machine is on right now. It reads a small rules file, compares each rule with this machine's own addresses, and prints the address from the first rule that fits.

It runs on the client machine: the one with slsh, slrun, slbench or slbotd. slgod never runs it and never reads its file. You seldom run it yourself either; the clients run it when they need an address and were not given one.

~/.config/sl-host
192.168.1.0/24   192.168.1.20   home
0/0              10.8.0.1       anywhere else, over the VPN

On the home network (any address in 192.168.1.0/24) that prints 192.168.1.20, the server's LAN address. Anywhere else it prints 10.8.0.1, the server's address on a VPN such as WireGuard or Tailscale.

A rule can also carry a port, for a slgod that does not listen on 7807, and can be kept for one profile, so that slsh -a dev finds a second slgod while every other profile finds the first. See the example.

When you need it, and when you do not

Your setupsl-host?
slgod and the clients on the same machineNo. Do not install it.
slgod elsewhere, at an address that never changesNo. Put addr = HOST:7807 in ~/.config/slsh/config, or pass --addr.
slgod reached through an SSH tunnel on localhostNo. With no sl-host the clients use localhost:7807 anyway.
A laptop that reaches slgod one way at home and another way awayYes. This is what it is for.
Several client programs (slsh, slrun, slbench, slbotd) that should all agreeUseful. slrun and slbench have no config file, so sl-host is the one place all of them look.

Installed by accident, it breaks a one-machine setup

A client that was given no address checks whether sl-host is on your PATH. If it is not, the client uses localhost:7807, which is right when slgod runs on the same machine. If it is, the client runs it and uses its answer. When sl-host fails, the client stops. It does not fall back to localhost, because that would turn "sl-host is misconfigured" into a refused connection and point you at the wrong problem.

go install ./cmd/... installs every program in the source tree, sl-host included. On a machine with no rules file, every client then stops with:

slsh: cannot find the host slgod is on: sl-host failed: exit status 2: sl-host: cannot read ~/.config/sl-host
	--addr HOST:PORT overrides

Pick one fix:

  • Remove it, the simplest. which sl-host prints where it is, usually ~/go/bin/sl-host; remove that file with rm, then run rehash in csh or zsh, or hash -r in sh or bash, so the shell forgets it.
  • Set the address: addr = localhost:7807 in ~/.config/slsh/config. An address from the config file or --addr means sl-host is never asked. That covers slsh only; slrun and slbench still ask sl-host.
  • Give it rules that point at this machine; see the examples.

If you see no host configured instead, that wording belongs to the old shell script sl-host replaced, and the current program never prints it. Most likely an old copy of the script comes earlier on your PATH.

How clients use it

Every client settles where slgod is in the same order:

  1. An address on the command line: --addr HOST:PORT for slsh, slrun and slbench, -addr for slbotd.
  2. An address in the client's config: addr = in ~/.config/slsh/config for slsh, or in slbotd.conf for slbotd.
  3. sl-host, if it is on PATH.
  4. localhost:7807.

At step 3 the client runs sl-host with no arguments and takes the first word it prints as the address.

  • The port. If the answer has no port, the client adds :7807. An IPv6 answer then comes out in brackets, like [2001:db8::10]:7807. If the answer names a port, such as 192.0.2.20:7808 or [2001:db8::20]:7808, the client uses it as given. That port comes from the rule, so a slgod started with -listen :7808 can be found this way. The address as it comes out here is also what picks the secret file, for a slgod with a secret of its own: 192.0.2.20 becomes 192.0.2.20:7807, and the client looks first for ~/.config/slgod/secret.192.0.2.20.7807 (rules).
  • The profile. The client first works out which avatar it wants: -a, then $SLGO_AGENT, then agent = in its config. It runs sl-host with SLGO_AGENT set to that profile name, or with SLGO_AGENT removed when there is none, so the answer is about the avatar it is about to ask for. slbotd does this only when it holds exactly one avatar; holding several, it asks about none. Rules for one profile use it.
  • A non-zero exit stops the client. What sl-host wrote to standard error is included in the client's message, followed by the hint --addr HOST:PORT overrides.
  • If sl-host exits 0 but prints nothing, the client says cannot find the host slgod is on: sl-host printed nothing.

Careful

Build the clients and sl-host from the same checkout. An older client that gets 192.0.2.20:7808 from a newer sl-host adds :7807 to it and cannot connect. An older sl-host has never heard of SLGO_AGENT or @profile words; it takes an @ word for part of the label, so a rule meant for one profile answers for every one. An older client that does not set SLGO_AGENT still works with rules that name no profile.

Installing it

On the client machine, from the source checkout:

$ go install ./cmd/sl-host
$ which sl-host

If which does not find it, run rehash in csh or zsh, or hash -r in sh or bash, and ask again. The clients find it through PATH, so the Go bin directory (usually ~/go/bin) has to be on it. A client started by a service manager sees that service's PATH, which may not include your shell's; that is general service-manager behaviour, not something sl-host checks. Then write the rules file, below, before you run a client.

The rules file

The file is ~/.config/sl-host. It is a file at that path, not a directory. $SL_HOSTFILE names a different one. The path is under $HOME/.config even when XDG_CONFIG_HOME is set.

One rule a line:

format
<network>   <address>[:<port>]   [@profile ...]   [label ...]
network
Which network this machine has to be on for the rule to apply. Any of:
  • a CIDR: 192.168.1.0/24, 2001:db8::/32;
  • IPv4 with the trailing zero octets left off: 0/0, 10/8, 192.168/16;
  • a bare address, which means that one address: 192.0.2.5 is 192.0.2.5/32, and an IPv6 address is /128.
address
What to print on that network: slgod's address as seen from there. It is printed exactly as written, so a host name works too. It may carry a port: 192.0.2.20:7808, server.example:7808, or [2001:db8::20]:7808 for IPv6, which needs the brackets when there is a port. With no port the client adds :7807. A port that is not a number from 1 to 65535, or a port with no host, makes sl-host warn and skip the line.
@profile
Optional. Words that start with @, straight after the address, keep the rule for those profiles: @dev, or @dev @test. The name is the profile name, the same one you give -a, spelled exactly the same. An @ on its own makes sl-host warn and skip the line. See rules for one profile.
label
Optional free text, the rest of the line after any @ words. Only -v, -l and error messages show it.

How the rules are applied:

  • The first rule that matches wins. Put specific networks first and catch-alls last.
  • A rule matches if any of this machine's addresses is in its network. A machine often has several at once (wired and wireless, a VPN, a bridge for virtual machines), and each rule is tried against every one of them.
  • Only interfaces that are up count, and loopback (127.0.0.1, ::1) and link-local (169.254.x.x, fe80::) addresses are left out. They say nothing about where the machine is.
  • 0/0 matches every IPv4 address and no IPv6 one. ::/0 matches every IPv6 address and no IPv4 one. A machine that has only IPv6 addresses on some network needs a ::/0 rule to be caught there.
  • # starts a comment anywhere on a line. Blank lines are ignored.
  • A line sl-host cannot read is reported on standard error and skipped. The rest of the file is still used.

Rules for one profile

sl-host is told which profile the client wants, in SLGO_AGENT. To ask by hand, run sl-host -a NAME, or env SLGO_AGENT=NAME sl-host. -a wins over SLGO_AGENT.

  • A rule with no @ word is for every profile, and for a question that names no profile. A file written before profiles could be named means what it always meant.
  • A rule with @ words is tried only when the question names one of them. It never answers a question that names no profile.
  • The first matching rule still wins. Put a profile's own rules above the general ones, or a general catch-all answers first.
  • If only @ rules cover this network and the question names another profile, or none, nothing matches and sl-host exits 1.

Worked examples

Home LAN, and a VPN everywhere else

~/.config/sl-host
# at home, the server's LAN address
192.168.1.0/24   192.168.1.20   home
# anywhere else, the server's address on the VPN
0/0              10.8.0.1       anywhere else

The VPN address reaches the server from anywhere the VPN is up. Do not forward port 7807 from your router instead: that puts slgod on the internet with only the secret to guard it (Security). Without a VPN, an SSH tunnel does the same job; see the next example.

Home LAN, a VPN, and an SSH tunnel as the catch-all

~/.config/sl-host
192.168.1.0/24   192.168.1.20   home
10.8/16          10.8.0.1       vpn
0/0              127.0.0.1      anywhere else, through an SSH tunnel

10.8/16 is short for 10.8.0.0/16. Away from home with the VPN up, the laptop has a café address and a 10.8.x.x address. Both the vpn rule and the catch-all match, and vpn wins because it comes first. With the VPN down, only the catch-all matches, and the client connects to this machine's port 7807, where an SSH tunnel to the server has to be running (ssh -N -L 7807:127.0.0.1:7807 you@server.example, Route B). Without the tunnel that is a connection refused, not an sl-host error.

With IPv6

~/.config/sl-host
192.168.1.0/24   192.168.1.20   home
0/0              server.example anywhere else, IPv4
::/0             server.example anywhere else, IPv6

The last line catches a network that gives the laptop only IPv6 addresses, which 0/0 never matches. The address here is a host name, which sl-host prints as written; the client then looks it up.

A second slgod on another port, for one profile

A second slgod runs on the server on port 7808 (how) and holds the profile dev. You want slsh -a dev to reach it, and everything else to reach the first one.

~/.config/sl-host
# the development slgod, for the dev profile only; above the general rules
192.168.1.0/24   192.168.1.20:7808   @dev   the development slgod, home
0/0              10.8.0.1:7808       @dev   the development slgod, away
# everyone else, on the usual port
192.168.1.0/24   192.168.1.20        home
0/0              10.8.0.1            anywhere else

At home, slsh -a dev connects to 192.168.1.20:7808. slsh -a example, or plain slsh with no avatar named anywhere, skips the two @dev rules and connects to 192.168.1.20:7807. If both slgods run on the laptop itself, one rule is enough: 0/0 127.0.0.1:7808 @dev the development slgod, above the general rules.

Check each side by hand. These work the same in sh, zsh and csh:

$ sl-host -v -a dev
$ env SLGO_AGENT=dev sl-host -v
$ sl-host -v

The second slgod has to listen where the rules send clients: with -listen 127.0.0.1:7808 it can be reached from the server itself and nowhere else. To reach it over the LAN and the VPN, start it with -listen :7808 and let the server's firewall admit only those networks, as for the first (Security).

A machine that runs its own slgod and keeps sl-host

~/.config/sl-host
0/0    127.0.0.1   this machine
::/0   127.0.0.1   this machine

This works while the machine is on a network. With no network at all it has no address sl-host counts, since loopback is left out, and sl-host fails with no address found on any interface (read from the code). Removing sl-host is the better fix for a one-machine setup.

Paste a rules file, the addresses this machine has and, if you like, the profile a client would ask about, and see which rule sl-host would pick and where the client would connect. It follows the same rules as the program: first match wins, 0/0 matches only IPv4, short networks are filled out with zeros, a bare address is /32, a port in the address is kept, and a rule with @ words is tried only for those profiles. It takes IPv4 addresses for the machine; IPv6 rules are read, and never match an IPv4 address. Nothing leaves this page.

    -a NAME asks about that profile. Without it, sl-host asks about the profile in SLGO_AGENT, if that is set, so in a shell where you have exported SLGO_AGENT a plain sl-host -v answers for that profile.

    -v adds one line to standard error, in this form:

    sl-host: 192.0.2.10 (network 0/0 matched our <addr>) [anywhere else]

    When the question names a profile, the part in parentheses ends with it: (network 0/0 matched our <addr>, for dev).

    -l prints every rule: the network, the address, MATCH, - or other, then the rule's @ words and label and which of this machine's addresses matched. other marks a rule for other profiles than the one asked about, whatever its network; sl-host would not try it. This is what one measured run printed, before profiles existed, with the machine's own addresses replaced:

    $ sl-host -l
10.99.0.0/16         10.99.0.5        -        lab
0/0                  192.0.2.10       MATCH    anywhere else (via <our-addr>)
::/0                 2001:db8::10     MATCH    v6 (via <our-addr>)

    -l marks every rule that matches, not only the winner. The winner is the first MATCH. -l ignores SL_HOST, since listing the rules is its whole point.

    Any other argument prints usage: sl-host [-v] [-l] [-a PROFILE] and exits 2.

    Overrides: SL_HOST, SL_HOSTFILE and SLGO_AGENT

    SL_HOST
    If set, sl-host prints it as the answer and reads no file, so it works even with no rules file. For a one-off, in a café with a network no rule covers: env SL_HOST=192.0.2.20 slsh. That reaches sl-host because the client runs it as a child process, which inherits the environment (read from the code). To keep it for the rest of the terminal session, export SL_HOST=192.0.2.20 in sh or zsh, or setenv SL_HOST 192.0.2.20 in csh; unset SL_HOST or unsetenv SL_HOST drops it again. With -v it says sl-host: SL_HOST/RSSH_HOST override. It is the answer whichever profile is asked about, and it may carry a port too.
    SL_HOSTFILE
    Read the rules from this file instead of ~/.config/sl-host. Handy for trying a new file before replacing the old one: env SL_HOSTFILE=$HOME/new-rules sl-host -l.
    SLGO_AGENT
    The profile the question is about, when -a is not given. The clients set it for sl-host to the avatar they are about to ask for, and remove it when they have none; slbotd holding several avatars asks about none. By hand: env SLGO_AGENT=dev sl-host -v. It is the same variable slsh, slrun and slbench read to choose the avatar.
    RSSH_HOST, RSSH_HOSTFILE
    Older names for the same two, left over from the script sl-host replaced. Each is used only when its SL_ name is not set.

    When nothing matches, the message lists what it compared, because that shows which side is wrong. Its layout, from one measured run with the machine's addresses replaced:

    sl-host: no rule in ~/.config/sl-host matches this network.
  our addresses: <v6 addr> <v4 addr>
  rules:
    10.99.0.0/16       10.99.0.5        lab
  add a rule for this network, or set SL_HOST=<address> for a one-off.

    The rules in that list show their @ words before the label, so a rule kept for another profile is easy to spot.

    A line that cannot be read is skipped with a warning, and the rest of the file is used:

    sl-host: ~/.config/sl-host:3: a network and no address to use on it; skipped
sl-host: ~/.config/sl-host:4: "192.168.300/24" is not a network; skipped

    The first of those two lines was measured. The second is built from the program's format, with an example network in it. The program's other reasons to skip a line, read from the code, are "192.0.2.20:0": the port must be a number from 1 to 65535, ":7808" has a port and no host, and an @ with no profile name after it.

    A client that runs sl-host passes its complaint on, as in the missing-file message above. No rules file and no matching rule are in troubleshooting too, and so is a profile that reaches the wrong slgod.
