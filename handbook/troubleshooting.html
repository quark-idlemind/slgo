Question 1

Does slgod start and keep running?

Look at what slgod printed on the slgod machine, or in its -log file. When it is ready, the last line begins serving gRPC on.

Likely faults

    Every fault

    Paste an error message into the box, or pick a component. Words in the box must all appear in an entry for it to show. The <p>, <path> and similar parts of a message stand for a profile name, a file path and so on.

    slgod will not start, or starts without the avatar

    zsh: command not found: slsh, or slsh: Command not found., right after installingshell

    Why

    Your shell cannot find the program, which is a matter between the shell and its PATH; slsh, slgod and the rest never ran. The wording is the shell's own: zsh: command not found: slsh in zsh, slsh: Command not found. in csh and tcsh, and sh: slsh: command not found from the bash that macOS runs as /bin/sh. There are two causes.

    • ~/go/bin is not on your PATH. go install puts every program there (or in go env GOBIN, if that is set), and nothing adds the directory to the PATH for you.
    • csh or tcsh has not seen the new program yet. They make a list of the programs on the path when the shell starts and sets its path in ~/.cshrc, and a program installed after that is not found until you run rehash, even with the directory on the path. Tried the same way, sh and zsh found the new program without being told.

    The shells also remember where they last found a program. If you delete sl-host, typing sl-host is Command not found in every shell, which is what you want; but if there was a second copy further along the PATH, or you have just installed a new one earlier on it, all three shells went on running the copy they had used before, until rehash or hash -r. This affects only what you type: slsh, slrun, slbench and slbotd look sl-host up on the PATH afresh every time they start.

    Fix

    First see whether the program is there, and whether the shell can find it:

    $ ls ~/go/bin
$ echo $PATH
$ which slsh

    If ~/go/bin is missing from the PATH, add it as Shells shows for yours. If it is there, tell the shell to look again:

    $ hash -r
    $ rehash

    Opening a new terminal does the same.

    slgod logs the avatars in, then stops with a listen tcp :7807: bind: … lineslgod

    Why

    slgod binds its port only after every avatar has logged in. If something already holds the port, most often another slgod, the bind fails and slgod exits at once. The usual wording is address already in use, which comes from the operating system; the handbook has not captured that exact line. A port you are not allowed to use gives listen tcp 127.0.0.1:1: bind: permission denied.

    Because slgod exits straight away, it does not log the avatars out. They stay in the world until the grid times them out. We have read this in the code but have not watched it happen.

    Fix

    Find what holds the port. If it is another slgod, use that one. Do not start a second slgod for the same profiles (see the entry below).

    $ ss -ltnp 'sport = :7807'
$ pgrep -l slgod
    $ lsof -nP -iTCP:7807 -sTCP:LISTEN
$ pgrep -l slgod

    On Ubuntu 24.04, without sudo, ss printed a LISTEN line for the port ending in users:(("slgod",pid=…,fd=…)) for an slgod running as the same user, and pgrep -l printed each process id followed by slgod.

    If something else needs 7807, start slgod on another port with -listen. Every client then needs that port too: in --addr or addr =, or in the sl-host rule, since a client adds :7807 to an sl-host answer that has no port (see this entry).

    $ slgod -listen :7900 example
    slgod stops with cannot start: -config: …slgod

    Why

    The directory given to -config is not one slgod will use. It checks three things before anything else, and the message says which failed:

    • stat DIR: no such file or directory: it does not exist. slgod does not create it, because it is meant to hold profiles you put there.
    • DIR is mode 0755, wanted 0700: chmod 700 DIR: other users could list it, and it holds credentials.
    • DIR is not a directory: the path names a file.

    Fix

    $ mkdir -m 700 ~/.config/slgod.dev

    or chmod 700 on the one you have. Then put the profiles for that daemon in it. See A second slgod beside the first.

    slgod stops with cannot start: stat ~/.config/slgod: no such file or directoryslgod

    Why

    slgod needs its secret, and it has none. That is the file named by -secret FILE; else DIR/secret, when slgod was started with -config DIR and that file is there; else the shared secret, ~/.config/slgod/secret. A -secret file is held to the same rules as the shared one: its directory 700, the file 600. The same cannot start: line appears when the secret is there but its directory or file is open to other users (~/.config/slgod has mode 0755, must be 0700 -- it holds the shared secret; chmod 0700 ~/.config/slgod), or when the file holds no line that is not blank or a comment (~/.config/slgod/secret is empty). The next two lines slgod prints are these, with the file it was looking for in place of ~/.config/slgod/secret, written out from the root of the filesystem:

    Create one with:  (umask 077; mkdir -p ~/.config/slgod; openssl rand -hex 32 > ~/.config/slgod/secret)
Or pass -no-auth to serve loopback without it.

    slgod reads the secret before it logs any avatar in, so nothing has happened on the grid when it stops. When it does start, it logs secret: PATH with the file it read.

    Fix

    Make the secret, or fix its modes, then start slgod again. Ignore the -no-auth suggestion: none of the programs here can connect to a daemon started that way (see why).

    $ (umask 077; mkdir -p ~/.config/slgod; openssl rand -hex 32 > ~/.config/slgod/secret)
$ chmod 700 ~/.config/slgod
$ chmod 600 ~/.config/slgod/secret

    The shared secret is always at $HOME/.config/slgod/secret. XDG_CONFIG_HOME does not move it; for slgod, -secret FILE does. If the secret: line names a file you did not mean, check for a secret file in the -config directory, or pass -secret.

    WARNING: the shared secret in <path> is N bytes, which is short enough to guess; at least 16 is wanted.any program

    Why

    A warning, not a failure: the program carries on. Anyone who can reach port 7807 may try secrets, and the daemon slows repeated failures down, but a short hand-typed secret can still be guessed in time. slgod and every client print this.

    Fix

    Make a long one, then copy the same file to every client machine and restart slgod and its clients.

    $ (umask 077; openssl rand -hex 32 > ~/.config/slgod/secret)
    <p>: NOT hosted: agent: profile "<p>": open ~/.config/slgo/<p>: no such file or directoryslgod

    Why

    slgod looked for a profile file with that name and there is none. Check the spelling: the name is the file name in ~/.config/slgo, not the avatar's name.

    This also happens when a flag comes after a profile name. slgod stops reading flags at the first name, so slgod example -v treats -v as a second profile and reports -v: NOT hosted: ….

    Fix

    Put every flag before the profile names, and check the file exists.

    $ ls ~/.config/slgo
$ slgod -v -log ~/.local/log/slgod.log example
    <p>: NOT hosted: agent: ~/.config/slgo is mode 0755, wanted 0700: chmod 700 ~/.config/slgoslgod

    Why

    A profile holds the password, or its $1$ digest, which is just as good for logging in. slgod refuses a profile directory that other users can open, and a profile file other users can read: <p>: NOT hosted: agent: ~/.config/slgo/<p> is mode 0644, wanted 0600: chmod 600 ~/.config/slgo/<p>.

    Fix

    Run the chmod the message names.

    $ chmod 700 ~/.config/slgo
$ chmod 600 ~/.config/slgo/example
    NOT hosted: agent: <path>: needs first and last, needs password or line N: unknown setting "x"slgod

    Why

    The profile file is readable but something in it is wrong. It needs first, last and password. A key it does not know is an error, so a typo cannot pass silently. A line without = gives line N: want key = value, got "…".

    Fix

    Edit the file. The keys are listed in the reference. New-style accounts use last = Resident.

    <p>: not up yet (<err>); trying againslgod

    Why

    The login failed for a reason that may clear by itself, such as the network or the login server. slgod keeps trying in the background: after 5 s, 15 s, 30 s, 1 min, 2 min, then every 2 min. It still starts serving clients in the meantime.

    Fix

    Usually none. Read the error in brackets. If it names a network problem on the slgod machine, fix that; slgod will pick it up.

    <p>: NOT hosted: login refused (key…): <the grid's sentence>slgod

    Why

    The grid refused the login for a reason that will not clear by itself. key means the name or password is wrong. tos, update and critical are the other reasons slgod does not retry. The sentence after the colon is the grid's own; the handbook has not captured it.

    A client that asks for the avatar again too soon after a failure is told <name> failed to log in (<err>); not trying again for <dur>. The wait is there because a login server throttles whatever hammers it.

    Fix

    Check first, last and password in the profile, then restart slgod. You can make the $1$ digest with slhash, which asks for the password with echo off.

    $ go install ./cmd/slhash
$ slhash

    If the shell says slhash is not found, see command not found.

    Careful

    If slgod runs under launchd with KeepAlive, or systemd with a short RestartSec, a wrong password means it logs in, fails and restarts over and over. Keep the restart delay generous.

    no session came up; nothing to serveslgod

    Why

    Every profile named on the command line failed for good, so slgod has nothing to hold and exits. The lines above it say why each one failed.

    Fix

    Fix the first NOT hosted line above it: see no such profile, profile modes or login refused.

    cannot start: log: <dir> is mode 755, so other users can read or replace what is logged there; a log directory has to be 700 (chmod 700 <dir>), or log somewhere elseslgod · slbotd

    Why

    The log names avatars and holds what people said to them, so -log refuses a directory other users can enter. It also refuses a log file that belongs to someone else or is not a plain file (a symlink, say). slbotd reports the same check as slbotd: log: ….

    Fix

    $ mkdir -p ~/.local/log
$ chmod 700 ~/.local/log
    viewer: viewer: "9000" has no port or viewer: -viewer-cert and -viewer-key go togetherslgod

    Why

    -viewer takes an address with a port, like 127.0.0.1:9000. -viewer-cert and -viewer-key must be given together, and only with -viewer. An address that is not on this machine fails with viewer: viewer login: listen tcp …: bind: can't assign requested address (the macOS wording).

    Fix

    $ slgod -viewer 127.0.0.1:9000 example
    <p>: no active group (N joined, none chosen: …); parcels that only let a group build will refuseslgod

    Why

    A notice, not a failure. The avatar is in several groups and nothing says which one to act as. A name that matches no group gives no active group: no group named "X"; joined: …, and one that matches two gives "X" names 2 groups; use the uuid.

    Fix

    Put group = Example Builders (or the group's uuid) in the profile, or start slgod with -group example="Example Builders".

    A second slgod was started, and now neither holds the avatarslgod

    Why

    This is worked out from the code; nobody has watched it happen. An avatar can be in only one session on the grid. A second slgod for the same profiles logs the avatars in again, and the grid ends the first daemon's sessions. The first daemon treats being thrown off as deliberate and stays logged out. The second then fails to bind port 7807, because the first still holds it, and exits without logging out. Both have lost their avatars.

    Fix

    Stop the second one if it is still running. Then ask the first to bring the avatar back:

    $ slsh -c agents
$ slsh login example

    Before you start slgod, check it is not already running (pgrep -l slgod). Under launchd or systemd, start it only through the service manager. To run a second daemon on purpose, give it its own -config directory, its own -listen port and its own accounts (how).

    <name> is not connected (<why>); it will not come back on its ownslgod · slsh

    Why

    The session was ended on purpose: someone ran logout, or the avatar was thrown off the grid, most often because it was logged in somewhere else. slgod logs … -- staying logged out rather than taking the session back and does not retry, so it will not kick you off in turn. A dropped network connection or a region restart is different: slgod reconnects from those by itself.

    Fix

    First make sure nobody is using that avatar in a viewer. Then ask for it back by name. login always takes a stopped avatar back when you name it; its -f flag is accepted and changes nothing.

    $ slsh -c agents
$ slsh login example

    slbotd does not force this. It stops asking for an avatar someone logged out on purpose. A trusted resident can send it :host --force by IM once they have checked.

    slgod disappears when the terminal it was started in is closedslgod

    Why

    slgod handles Ctrl-C (SIGINT) and SIGTERM by logging every avatar out and printing done. It does not handle SIGHUP, which a closing terminal sends. From Go's default behaviour we expect that to end slgod at once, without a logout. This has not been measured.

    Fix

    Run slgod under launchd or systemd, or inside tmux or screen. See Linux & macOS for service files.

    slsh (or slbotd, slrun) cannot reach slgod

    slsh prints slsh: in front of each error. When the connection failed, it also prints --direct logs in without slgod on the next line. slrun, slbench and slbotd give the same text after their own prefix.

    slsh: sl: cannot reach slgod at 127.0.0.1:7807: login: rpc error: code = Unavailable desc = connection error: desc = "transport: Error while dialing: dial tcp 127.0.0.1:7807: connect: connection refused"slsh

    Why

    Nothing answered on that address and port. One of these:

    • slgod is not running, or has not finished logging the avatars in. It opens the port last.
    • The address is wrong. The at … part says what the client used. Where that came from is below.
    • slgod listens on another port (-listen :7900, say) and the client used 7807.
    • slgod was started with -listen 127.0.0.1:7807, so it takes connections from its own machine only.

    If instead the client waits about 30 seconds and then gives up, something on the way is dropping the packets, usually a firewall. That is worked out from the code (the client allows 30 s to connect), not captured.

    Fix

    On the slgod machine, check slgod is running and which address it serves on: its log has a line serving gRPC on <addr> for <profiles>. Then test the port from the client machine.

    $ nc -vz server.example 7807
$ slsh --addr server.example:7807 -c agents

    If nc cannot connect but slgod is running, open TCP 7807 on the slgod machine's firewall (see below). To reach slgod from another machine it must not be started with -listen 127.0.0.1:…, unless you connect through an SSH tunnel.

    slsh: sl: cannot reach slgod at HOST:7807: stat ~/.config/slgod: no such file or directory, then (looked first for …) and The client and slgod share this fileslsh

    Why

    The client has no shared secret. It reads the secret before it contacts the address, so here "cannot reach" means "has no secret". slgod was not even tried.

    The (looked first for …) line names the two files a client tries before the shared secret, kept for the address it was about to dial: secret.HOST.PORT and secret.HOST. They are only for a slgod with a secret of its own (rules). If you copied such a file and still see this, its name does not match the address as dialled; compare it with the names in that line, and see the entry on names.

    Fix

    Copy the secret from the slgod machine, byte for byte, over a secure route such as scp. On the machine slgod runs on, the file is already there.

    $ (umask 077; mkdir -p ~/.config/slgod)
$ scp server.example:.config/slgod/secret ~/.config/slgod/secret
$ chmod 600 ~/.config/slgod/secret

    Security

    Whoever holds this file can drive every avatar slgod holds. Do not send it by email or chat, and do not put it in a repository.

    ~/.config/slgod has mode 0755, must be 0700 -- it holds the shared secret; chmod 0700 ~/.config/slgodslsh · slgod

    Why

    The secret's directory or file can be read by other users on this machine. Every program refuses it: a client reports it after cannot reach slgod at …:, and slgod after cannot start:. For the file the message is ~/.config/slgod/secret has mode 0644, must be 0600 -- it holds the shared secret; chmod 0600 ~/.config/slgod/secret. A file with only blank and comment lines gives ~/.config/slgod/secret is empty.

    A per-address secret, secret.HOST.PORT or secret.HOST, is checked the same way. One that is there but refused is an error: the client does not fall back to the shared secret. Fix its mode the same way.

    A copy made with scp or a file manager often arrives with mode 0644.

    Fix

    $ chmod 0700 ~/.config/slgod
$ chmod 0600 ~/.config/slgod/secret
    login refused: rpc error: code = Unauthenticated desc = authentication failed (the secret used was PATH)slsh

    Why

    The client's secret, in the file the message names, is not the same as slgod's. The daemon gives the same answer for every kind of failure, so the message cannot say more.

    Look at the file named first:

    • If it is the shared secret, ~/.config/slgod/secret, and this slgod has a secret of its own, the client found no copy kept for the address it dialled. See the entry below.
    • If it is a secret.HOST.PORT or secret.HOST file, that copy is out of date, or belongs to another slgod.

    Two related messages:

    • login refused: rpc error: code = ResourceExhausted desc = too many failed logins lately; try again in a few minutes (the secret used was PATH). Failed attempts, yours or anyone else's, have tripped slgod's throttle. After 3 failures from one address slgod delays its answers, from 0.5 s up to 4 s, and past a limit it refuses outright. It forgets an address after 15 minutes of quiet.
    • slgod did not prove it knows the shared secret in PATH; refusing to talk to it. The client checks the daemon too. Whatever answered on that port is not your slgod, or its secret is different from the one in PATH.

    Fix

    slgod's log names the file it reads, in its secret: line at startup. Copy that file again to the one the client named, so both ends have the same secret. Only the first line that is not blank and not a # comment counts; spaces around it are ignored. Compare the two without printing them:

    $ sha256sum ~/.config/slgod/secret
    $ shasum -a 256 ~/.config/slgod/secret

    Use the paths the two ends named if they are not the shared secret.

    If you replaced the secret on the slgod machine, restart slgod: it reads the file only at startup. If the throttle tripped, wait a few minutes after fixing the secret.

    Works with --addr 127.0.0.1:PORT but not with localhost:PORT, or the other way roundslsh

    Why

    This slgod has a secret of its own, and the client keeps its copy under one address. A client picks the secret by the address exactly as it dials it: secret.127.0.0.1.7808 is found for 127.0.0.1:7808 and for nothing else. Dialling localhost:7808 looks for secret.localhost.7808 and secret.localhost, finds neither, and uses the shared secret, which this slgod does not accept. This has been seen with a tunnel on local port 7808: reached as localhost:7808, the client fell back to the shared secret and was refused.

    The refusal says so at its end: (the secret used was …/.config/slgod/secret), the shared one, where you expected the per-address file. The same happens with a host name and its IP address, a tunnel moved to another local port, or an sl-host answer that differs from the address the file is named for. Remember that a client given no address at all dials localhost:7807.

    Fix

    Dial the address the file is named for, or give the file the name for the address you dial. Copy it rather than rename it if you use both:

    $ cp -p ~/.config/slgod/secret.127.0.0.1.7808 ~/.config/slgod/secret.localhost.7808

    A file named for the host alone, such as secret.localhost, covers every port on it. Use that only if every slgod reached that way has the same secret. The naming rules, including IPv6, are in the reference.

    this client is older than slgod: it sends its name in a form slgod no longer reads. Rebuild and reinstall it with the same tree as the daemonslsh

    Why

    The client was built from an older checkout than the daemon, and the handshake has changed since. This is common when slsh on a laptop was built months before slgod on the server.

    Fix

    Build every program from the same commit. Compare what each machine runs with --version, then update and rebuild the older one.

    $ slsh --version
$ git pull
$ go install ./cmd/...

    Then run rehash in csh or zsh, or hash -r in sh, so the shell does not go on running an old copy from somewhere else on the PATH. slsh --version again shows which one it finds.

    transport: authentication handshake failed: tls: first record does not look like a TLS handshakeslsh · slgod

    Why

    The client speaks TLS and the thing on the port does not. Usually slgod was started with -no-auth, which serves plain, unauthenticated gRPC. slsh, slrun, slbench and slbotd always use TLS and the secret handshake, so none of them can connect to a -no-auth daemon. The whole line, as captured:

    slsh: sl: cannot reach slgod at 127.0.0.1:17809: login: rpc error: code = Unavailable desc = connection error: desc = "transport: authentication handshake failed: tls: first record does not look like a TLS handshake"
        --direct logs in without slgod

    The other cause is that the port belongs to some other program, not slgod.

    Fix

    Restart slgod without -no-auth, and set up the shared secret instead. slgod's own startup message suggests -no-auth when the secret is missing; do not follow it.

    Security

    slgod listens on every interface unless told otherwise, and nothing checks that -no-auth is used on loopback only. A -no-auth slgod on the default :7807 lets anyone who can reach the port drive the avatars.

    slsh: sl: cannot attach to that slgod's default session: rpc error: code = NotFound desc = this server holds no sessionsslsh

    Why

    You reached slgod and the secret is right, but it holds no avatar at the moment. Either the login is still being retried (not up yet), or every avatar has been stopped (not connected).

    Fix

    Read slgod's log. To start an avatar that slgod has a profile for:

    $ slsh login example
    slsh: sl: cannot attach to "builder": rpc error: code = NotFound desc = no agent named "builder"slsh

    Why

    The name you asked for, with --agent, SLGO_AGENT or agent =, is not a session slgod holds. The name is a profile name on the slgod machine, not the avatar's name. A profile slgod has but has never started also counts as not held. If you run two slgods and the profile is on the other one, sl-host sent the client to the wrong one; see this entry.

    Fix

    List what slgod holds and what it could start, then start the one you want.

    $ slsh -c agents
$ slsh login builder
    slgod works from its own machine, and another machine cannot connect or times outslgod machine

    Why

    slgod listens on every interface by default, so a host firewall is the usual thing in the way. On macOS the application firewall may ask whether slgod may accept incoming connections the first time it listens. We expect this from how macOS behaves; the handbook has not recorded the dialog.

    Fix

    macOS

    If a dialog asks whether slgod may accept incoming connections, allow it. Otherwise look in System Settings, Network, Firewall, Options, and allow slgod there. Rebuilding slgod makes a new binary, so macOS may ask again.

    Linux

    Allow TCP 7807 in whichever firewall the machine runs. Limit it to your own network where you can. These lines have not been run for this handbook; the ufw one matches the forms in ufw 0.36.2's manual on Ubuntu 24.04, and the firewalld one is unchecked.

    $ sudo ufw allow from 192.0.2.0/24 to any port 7807 proto tcp
$ sudo firewall-cmd --add-port=7807/tcp --permanent && sudo firewall-cmd --reload
    slsh: --first and --last are for --direct; through slgod the session knows who it isslsh

    Why

    Through slgod you choose an avatar by profile name, not by the avatar's name.

    Fix

    $ slsh -a example

    sl-host

    sl-host runs on the client machine only. A client runs it when no address was given and it is on $PATH. If it is installed and fails, the client stops; it does not fall back to localhost.

    slsh: cannot find the host slgod is on: sl-host failed: exit status 2: sl-host: cannot read ~/.config/sl-hostslsh · sl-host

    Why

    sl-host is on your $PATH but it has no rules file. This is the most common first-day problem: go install ./cmd/... installs sl-host along with everything else, and from then on every client asks it for slgod's address instead of using localhost. The next line of the message is --addr HOST:PORT overrides.

    Fix

    Pick one.

    • slgod is on this machine: remove sl-host. Clients then use localhost:7807.
    • slgod is at one fixed address: set it in slsh (set addr server.example:7807) or in slbotd.conf (addr = server.example:7807). sl-host is not asked when an address is set.
    • your computer moves between networks: write the rules file. See sl-host.
    # slgod on this machine: take sl-host off the PATH
$ which sl-host
$ rm ~/go/bin/sl-host

    If which names another file, remove that one instead. Clients look sl-host up afresh each time they start, so they stop asking it at once. Your shell may still remember it: run rehash in csh or zsh, or hash -r in sh (why).

    ~/.config/sl-host
    192.0.2.0/24   192.0.2.20      home
0/0            10.8.0.1        anywhere else, over the VPN
    sl-host: no rules in <path>; each line is a network and the address to use on it, e.g. "0/0 192.168.1.20"sl-host

    Why

    The file exists but no line in it could be used. sl-host reports each bad line and skips it, for example sl-host: ~/.config/sl-host:3: a network and no address to use on it; skipped, or sl-host: <path>:<n>: "<text>" is not a network; skipped.

    Fix

    Each line is a network, then the address to print, then an optional label. # starts a comment. A network is a CIDR such as 192.0.2.0/24, a short IPv4 form such as 0/0 or 10/8, or a single address. Check the file with:

    $ sl-host -l
    sl-host: no rule in ~/.config/sl-host matches this network.sl-host

    Why

    You are on a network none of the rules cover. When the client asked about a profile, the line ends matches this network for NAME., and rules kept for other profiles (@ words) were not tried; see the entry on profiles. sl-host lists this machine's addresses and the rules, then ends with add a rule for this network, or set SL_HOST=<address> for a one-off. The client reports it as … sl-host failed: exit status 1: ….

    0/0 matches IPv4 addresses only, and ::/0 IPv6 only. A network that gives you only an IPv6 address needs a ::/0 rule to catch it. The first rule that matches wins, so put catch-alls last.

    Fix

    For a one-off, give the address in the environment. For good, add a rule, or a catch-all as the last line.

    $ env SL_HOST=198.51.100.7 slsh
$ sl-host -v
    ~/.config/sl-host (last lines)
    0/0            10.8.0.1        anywhere else, over the VPN
::/0           2001:db8::7     anywhere else, IPv6
    sl-host: no address found on any interface -- is the network up?sl-host

    Why

    sl-host found no usable address on this machine. It ignores loopback and link-local addresses, so a machine that is not connected to anything has none. sl-host: cannot read this machine's addresses: <err> means it could not list the interfaces at all.

    Fix

    Connect to a network, or give the address for this once with SL_HOST, or use --addr.

    $ slsh --addr 127.0.0.1:7807
    sl-host picks the right machine, but the client tries port 7807 and slgod is on another portsl-host

    Why

    The rule that matched has an address with no port, and a client adds :7807 to an address with none. A slgod started with -listen :7900 is not there.

    If the rule does name a port and the client still tries 7807, the client is older than sl-host: an older client adds :7807 whatever sl-host printed, which makes an address that cannot be dialled (read from the code).

    Fix

    Put the port in the rule, then check what sl-host prints:

    ~/.config/sl-host
    0/0            server.example:7900    anywhere
    $ sl-host -v

    Rebuild the clients from the same checkout as sl-host (go install ./cmd/slsh ./cmd/sl-host, and slrun, slbench or slbotd if you use them). Or give the full address: --addr server.example:7900, set addr server.example:7900 in slsh, or addr = in slbotd.conf.

    slsh -a NAME goes to the wrong slgod, or a rule for one profile is never usedsl-host

    Why

    A rule with @NAME after its address is tried only when the client asks about that profile. The usual causes, most likely first:

    • Order. The first matching rule wins. A general rule above the @NAME rule, a catch-all most of all, answers first.
    • Spelling. The word after @ has to be exactly the profile name you give -a, which is the profile's file name. @Dev is not dev.
    • No profile named. With no -a, no SLGO_AGENT and no agent =, the client asks about no profile, and @ rules are never tried. slbotd holding more than one avatar asks about none too.
    • An old sl-host. One built before profiles could be named reads @NAME as part of the label, so the rule answers for everyone. sl-host -version says which build it is.
    • An old client. One built before this does not tell sl-host the profile, so sl-host answers for none.
    • An address was given. --addr or addr = means sl-host is never asked.

    Fix

    Ask sl-host the question the client asks, and read which rule it picks and why. These work the same in sh, zsh and csh:

    $ sl-host -l -a dev
$ env SLGO_AGENT=dev sl-host -v
$ sl-host -version

    -l marks rules kept for other profiles as other. Move the @dev rules above the general ones, fix the spelling, and rebuild sl-host and the clients from the same checkout if either is old. The sl-host page has a worked example.

    cannot find the host slgod is on: sl-host printed nothingsl-host

    Why

    Something called sl-host on your $PATH exited cleanly and printed nothing. The Go sl-host always prints an address or fails, so this is usually an old script or wrapper of the same name.

    Fix

    $ which sl-host
$ sl-host -version

    Replace it with go install ./cmd/sl-host.

    slsh settings, how and the viewer

    slsh: slsh: ~/.config/slsh/config line 1: unknown setting "hwo_url"slsh

    Why

    slsh will not start with a setting it does not know or a value it cannot use. slsh: really does appear twice at the start. Other forms:

    • … line N: want key = value, got "…": a line with no =.
    • … line 1: how_url: want the server's address with http:// in front, like http://127.0.0.1:8080, got "127.0.0.1:11434"
    • … line 1: how_extra: want a JSON object, like {"reasoning_effort": "none"}: …
    • … how_timeout: want a length of time, like 45s or 2m, got "…"

    A # comment after a value is part of the value. So how_url = http://127.0.0.1:11434 # ollama fails with got "http://127.0.0.1:11434 # ollama". On a setting that holds plain text, such as addr or agent, the comment is kept without any error and quietly breaks the value.

    Fix

    Edit the file named in the message, or clear the setting. Put comments on lines of their own.

    $ slsh -c 'set how_url ""'

    If slsh will not start at all, edit ~/.config/slsh/config directly: settings can only be changed from inside slsh once it has started.

    how answers From the index alone (nothing is answering at http://127.0.0.1:11434); …slsh

    Why

    how still answers when no model does, from its built-in index, and the words in brackets say why:

    • how_url is not set: no model is configured. That is the default.
    • nothing is answering at <url>: the model server is not running, or is on another port.
    • the model at <url> did not answer in time: slower than how_timeout (2 minutes by default).
    • the model at <url> refused: …: the server answered with an error, such as a 404 for a model name it does not have.

    Fix

    Start the model server, and check the URL and model name. Ollama needs how_model; llama-server ignores it.

    $ curl -s http://127.0.0.1:11434/v1/models
$ slsh -c 'set how_url http://127.0.0.1:11434'
$ slsh -c 'set how_model qwen3.5:4b'

    There is no API key setting. how sends no Authorization header, so a hosted service that needs a key cannot be used directly.

    From the index alone (the model's answer could not be used: … the message was empty and the limit of 512 tokens was reached; …)slsh

    Why

    A model that reasons before it answers spent all 512 tokens reasoning and gave no answer.

    Fix

    Turn reasoning off in the request. This is the setting slsh's own guide measured with qwen3.5:4b:

    Inside slsh it is set how_extra '{"reasoning_effort": "none"}'. slsh needs the single quotes to keep the double quotes in the value, so from the command line the quoting depends on the shell:

    $ slsh -c "set how_extra '{\"reasoning_effort\": \"none\"}'"
    $ slsh -c 'set how_extra '"'"'{"reasoning_effort": "none"}'"'"

    Or put how_extra = {"reasoning_effort": "none"} on a line of its own in ~/.config/slsh/config, which needs no quoting at all.

    this daemon serves no viewer logins.slsh

    Why

    viewer and viewer --launch need slgod to serve viewer logins, and it was started without -viewer.

    Fix

    Restart slgod with -viewer. For a viewer on another machine, bind it to an address that machine can reach, preferably a WireGuard or Tailscale address, and make that viewer trust ~/.config/slgod/viewer-cert.pem.

    $ slgod -viewer 127.0.0.1:9000 example
    nothing here knows how to start a viewer on linux; put a "viewer_launch = ..." line in slsh's config (~/.config/slsh/config) with {app} {uri} {first} {last} {password} where those belongslsh · Linux

    Why

    viewer --launch has defaults on macOS only. On Linux, viewer_launch is empty until you set it.

    Fix

    Set viewer_launch to the command that starts your viewer, with placeholders where its login arguments go: {app}, {grid}, {uri} (slgod's viewer login address), {first}, {last} and {password}. On Linux {app} and {grid} are empty unless you also set viewer_app and viewer_grid. Use --grid {grid}, as the macOS default does, and name the grid you added in the viewer; on macOS a viewer given --loginuri came up on whichever grid it had used last. The lines below are an example that has not been tried on Linux: the path is wherever you unpacked the Firestorm OpenSim build (see Starting a viewer).

    ~/.config/slsh/config (Linux, not tried)
    viewer_grid    = slgod
viewer_launch  = /opt/firestorm-os/firestorm --grid {grid} --login {first} {last} {password}
viewer_running = pgrep -f /opt/firestorm-os/

    Do not write a real password into this line: slsh fills in {password} with a one-time password when it launches.

    viewer --launch on macOS opens a viewer that does not offer slgod's grid, or says a viewer is already runningslsh · macOS

    Why

    The macOS default runs open -a Firestorm-OpenSim --args --grid slgod --login …. The Second Life build of Firestorm ignores private grids, so it needs the OpenSim build, installed as Firestorm-OpenSim. If a viewer is already open, slsh refuses with a viewer is already running: starting it again would raise its window and log nobody in, …; quit the viewer and try again, because the login goes on the command line and only a new process reads it.

    Fix

    Install the Firestorm OpenSim build, or point viewer_app at the viewer you have. Quit any running viewer first. The viewer also has to trust slgod's certificate (append ~/.config/slgod/viewer-cert.pem to Firestorm's user_settings/CA.pem, or accept its certificate dialog once).

    $ slsh -c 'set viewer_app Firestorm-OpenSim'

    slbotd

    slbotd prints fatal errors as slbotd: … and exits. Everything after startup goes to its log, each line starting with the profile name. Failures also go into a list you can read in-world by sending the avatar :errors.

    slbotd: ~/.config/slgo is mode 0755, wanted 0700: chmod 700 ~/.config/slgoslbotd

    Why

    slbotd.conf lives in the profile directory, and slbotd checks that directory is private before reading anything. The file itself holds no secret.

    Fix

    $ chmod 700 ~/.config/slgo
    slbotd: open ~/.config/slgo/slbotd.conf: no such file or directoryslbotd

    Why

    slbotd has no config file where it looked. The next line is see slbotd.conf for what goes in it. It looks at -config PATH, then $SLBOTD_CONFIG, then slbotd.conf in the profile directory.

    Fix

    Create it. The smallest useful file names one avatar and one person it takes commands from:

    ~/.config/slgo/slbotd.conf
    avatar  = example
trusted = Quark Idlemind

    See Adding slbotd.

    slbotd: ~/.config/slgo/slbotd.conf: line 7: unknown setting "llm-ulr"slbotd

    Why

    An unknown key stops slbotd, so a misspelt setting cannot quietly do nothing. Keys are not case-sensitive, and most accept - or _.

    Fix

    Correct the key; the list is in the reference. Then check the whole file without connecting anywhere:

    $ slbotd --check
    no avatar lines: name at least one profile to hold or no trusted lines: nobody could send a command, …slbotd

    Why

    slbotd needs at least one avatar and one trusted line. It also refuses an alias that points at no command (alias "x" points at "y", which is no command) and a backstory for an avatar it does not hold (backstory names "x", which is not an avatar this daemon holds).

    Fix

    Add the missing lines. A uuid is safer than a name for trusted.

    slbotd takes no arguments; the avatars are named in the configurationslbotd

    Why

    Unlike slgod, slbotd takes no profile names on its command line.

    Fix

    Put avatar = example in slbotd.conf and run slbotd with flags only.

    The log repeats example: cannot host: cannot reach slgod at HOST:7807: …slbotd

    Why

    slbotd is a client of slgod, like slsh, and fails for the same reasons. The text after cannot reach slgod at …: is the same as slsh would print: connection refused, no secret, secret modes, wrong secret. slbotd keeps trying, waiting longer each time, up to 2 minutes.

    Other forms: cannot host: rpc error: … no agent named "x" (slgod has no such profile) and x failed to log in (…); not trying again for 1m0s (read slgod's log).

    Fix

    Check slgod is running and slbotd has the right addr and the same secret. Profiles belong on the slgod machine; slbotd never reads the password. The quickest test is slsh with the same address, on the slbotd machine:

    $ slsh --addr server.example:7807 -c agents
    The bot ignores a command, and the log says refused a command from X: …slbotd

    Why

    The sender is not on a trusted line. Names are matched against the legacy name the grid sends (such as Example Resident), not the display name. By default a stranger is told nothing.

    Fix

    Add the person, by uuid if you can, and restart slbotd: it reads the file once, at startup. Set answer-strangers = yes if refused senders should be told I only take commands from people I have been told to trust.

    example is already running 4 commands; try again when one has finished.slbotd

    Why

    Each avatar runs at most jobs commands at once (4 by default).

    Fix

    Wait, or raise jobs in slbotd.conf and restart.

    cannot run slbench (<path>): <err> when slbotd runs as a serviceslbotd

    Why

    The built-in slbench and slrun programs are looked up on PATH. We expect launchd and systemd to give services a short PATH that leaves out ~/go/bin (not measured here). Programs run on the slbotd machine, so they must be installed there.

    Fix

    Name each program by its full path. Naming any program replaces the built-in pair, so name both.

    ~/.config/slgo/slbotd.conf
    program = slbench /home/you/go/bin/slbench
program = slrun   /home/you/go/bin/slrun
    CHAT IS OFF: chat names somebody to talk to but no llm-url says where a model is, so nothing will be answeredslbotd

    Why

    Conversation needs both an llm-url and at least one chat line. slbotd logs this at every start when the setup is half done, then CHAT IS OFF: everything else works; slbotd --check says what the file means. Commands keep working. The other forms are:

    • CHAT IS OFF: llm-url names a model but no chat line says who may be answered, so nothing will be answered
    • CHAT IS OFF: chat-summary is 200 tokens and chat-context only 256; the summary has to be well under the budget or there is no room left to talk

    In-world, :chat says no model is configured; this avatar answers commands only.

    Fix

    Add the missing line, and keep chat-summary under half of chat-context. Then restart.

    ~/.config/slgo/slbotd.conf
    llm-url = http://127.0.0.1:8080
chat    = *
    The bot answers commands, but someone who talks to it gets no replyslbotd

    Why

    Only one-to-one instant messages are answered. Local (nearby) chat and group IMs never are. A message that starts with the prefix (:) is a command, not conversation. The person who wrote never sees an error: when something fails they get silence, and the reason goes to the log and :errors. Look in the log for:

    • not answering X: not in the chat list: adjust the chat lines.
    • too busy talking to answer X: raise chat-jobs, or llama-server's -np.
    • not answering X: that is builder, which this daemon drives as well, and they have said 8 things to each other already, and will not until they have said nothing for 30m0s: two of the daemon's own avatars, or one and a chat-bot ("which another program's model drives"), reached chat-own.

    A reply can also just be slow. slbotd waits as if reading and typing: with the defaults, a long reply takes minutes.

    Fix

    Send a one-to-one IM with no prefix, and read the log. To shorten the wait, lower chat-max-tokens or set pace-max.

    :errors shows could not answer X: the model at http://127.0.0.1:8080: …slbotd

    Why

    slbotd could not reach llama-server at llm-url. The rest of the line is Go's network error, which for a server that is not running should end in connect: connection refused (expected from Go's format, not captured). slbotd asks nothing of the model at startup, so this shows only when someone talks to the bot.

    When the model was reached, the log line model <alias> (<ftype>), N slots of M tokens, build B appears on the first reply.

    Fix

    Start llama-server and check the port. Give the base URL without /v1.

    $ curl -s http://127.0.0.1:8080/props | head -c 300
$ llama-server -m model.gguf -c 8192 -np 4 --slot-save-path /var/lib/slbotd/slots

    A model that is too slow gives an error mentioning a deadline or timeout (wording not captured). Raise llm-timeout, use a smaller model, or lower chat-max-tokens.

    slbotd pointed at Ollama, OpenAI or another hosted API never answers: could not answer X: GET /props: …slbotd

    Why

    slbotd works only with llama.cpp's llama-server. Before its first reply it asks the server for /props, and it keeps conversations in llama-server's slots. Other servers do not have these, so every message fails and is logged as an error. The exact status text depends on the server and has not been captured. slbotd also sends no API key, so a hosted service would refuse it anyway, and so would a llama-server started with --api-key.

    This is slbotd only. slsh's how does work with Ollama.

    Fix

    Run llama-server, without --api-key, on loopback or a network you trust. See Bot + LLM.

    could not answer X: the model said nothing at allslbotd

    Why

    The model returned an empty reply. the model answered with no choices at all is the same trouble. A "thinking" model can spend its whole token allowance reasoning, and slbotd has no way to pass extra request fields, unlike slsh's how_extra. That cause is our reading of the code and slsh's measurements, not something measured with slbotd.

    Fix

    Use an instruct model that does not reason first, or turn reasoning off on the server. Raising chat-max-tokens gives more room.

    Chat works, but every reply adds could not keep the context for X: POST /slots/0?action=save: …slbotd

    Why

    slbotd saves each conversation's model state between turns, and llama-server was started without --slot-save-path. Replies still go out, but each one adds an entry to :errors (up to 50) and trusted residents get the trouble notice.

    Fix

    Restart llama-server with --slot-save-path DIR. If slbotd can see that directory too, set slot-save-path in slbotd.conf so :forget can delete the saved state.

    :errors shows no backstory: …, and the avatar answers out of characterslbotd

    Why

    The backstory file or directory could not be read, or an include in it is missing or loops. The avatar still answers, with no character. The avatar name in backstory = … must be written exactly as in its avatar line, including case. The startup check ignores case, but the lookup does not (read in the code).

    Fix

    slbotd --check prints one line per backstory with its size, or BROKEN: …. Backstories are re-read on every turn, so a fix takes effect without a restart.

    Collecting information

    When the list above does not settle it, gather these before you change anything.

    slgod's log

    slgod writes to standard error, or to the file given with -log. Each line starts with the time of day only, with no date, so note the date when you copy lines out. Every login, retry, disconnect and reconnect is there, prefixed with the profile name. -v adds every grid message slgod has no handler for; that is mostly useful when reporting a bug.

    $ tail -n 50 ~/.local/log/slgod.log
    $ journalctl --user -u slgod -n 50
    $ tail -n 50 ~/.local/log/slgod.stderr

    The macOS path is whatever StandardErrorPath names in your LaunchAgent; the one above matches the example on Linux & macOS.

    What slgod holds

    agents lists the sessions slgod holds and the profiles it could start, each with its state: configured, connecting, failed or stopped. status shows the avatar's own session.

    $ slsh -c agents
$ slsh -c status

    Which address a client used

    Every client picks slgod's address in this order, and stops at the first that gives one:

    1. --addr HOST:PORT on the command line (slbotd: -addr).
    2. addr = in slsh's config, or in slbotd.conf.
    3. sl-host, if it is on $PATH: the address it prints, with :7807 added unless it names a port. The client tells it which profile it wants in SLGO_AGENT. If it fails, the client stops here.
    4. localhost:7807.

    slrun and slbench have no config file, so they skip step 2. To see what sl-host decides and why:

    $ slsh -c 'set addr'
$ which sl-host
$ sl-host -v
$ sl-host -l
$ sl-host -v -a dev

    sl-host -v prints the address, and explains on standard error which rule matched. sl-host -l lists every rule and marks each one that matches; the first MATCH wins. Add -a and the profile name to ask what a client using that profile would be told.

    Versions

    Every program prints its build, and client and daemon should come from the same commit. The line names the release it follows, the date and the commit.

    $ slsh --version
$ slgod -version
$ slbotd -version

    slbotd

    slbotd --check reads the config, prints what it means and exits without connecting. It shows the slgod address, the avatars, who is trusted, whether chat is on (and a PROBLEM: line if it is half set up), each backstory's size or BROKEN:, each program's path, and whether each avatar's profile loads. It checks profiles on the machine it runs on, so on a separate slbotd machine the profile lines report errors that do not matter.

    $ slbotd --check

    In-world, send the avatar an IM:

    :errors
    The last 50 failures for that avatar, each shown like 3 hours ago: …. Kept in memory only, so lost on restart. :errors clear empties it.
    :status
    Whether the avatar is attached, its position, and the commands running.
    :agents
    slgod's list, with * on the avatars this slbotd attends.
    :chat
    The model, its slots, the backstory and the conversations, or why the model is not answering.

    A trusted resident's first message after an hour of quiet (error-gap) gets one line first, such as (3 things have gone wrong since we last spoke -- say :errors).

    Careful

    Logs and transcripts name avatars and hold what other residents said. Before you paste one anywhere public, replace every name, region and uuid. Never share a log made with -log-secrets or a trace made with -trace-bodies: they hold live session credentials.
