Linux & macOS

Every program here runs on both, from the same source, with the same files in the same places. This page covers the handful of places where the two systems still part ways, and what to check when slsh and slgod run on different ones.

The short version

The code is the same on both systems. There is no cgo and no native library, and nothing is installed outside your home directory. The things that are the same:

  • Every file lives under ~/.config, ~/.local/share or ~/.local/state, on macOS too. Nothing goes in ~/Library/Application Support. That is deliberate.
  • Nothing uses the macOS Keychain or the Linux secret service. Passwords and the shared secret are plain files, protected by Unix permission bits, and the programs check those bits the same way on both systems.
  • slgod listens on TCP port 7807 on both. No Unix socket is used anywhere.
  • A Linux slsh talks to a macOS slgod, and the other way round, with nothing special set up. What they need is the same shared secret and a build from the same source tree.

What differs:

  • How you keep slgod running: a launchd agent on macOS, a systemd unit on Linux.
  • The firewall you may have to open, if clients connect from other machines.
  • slsh viewer --launch knows how to start Firestorm on macOS. On Linux you tell it how.
  • Which operating system the Second Life login server is told about. slgod reports the system it runs on.

Building, and building for the other system

You need Go 1.26.1 or newer. With Go's default setting, an older Go fetches the right version by itself. Build from inside the git checkout, so that --version can say which commit you have:

$ cd slgo
# every program, into ~/go/bin
$ go install ./cmd/...

That is the same on both systems, and in every shell. ~/go/bin (or whatever go env GOBIN says) must be on your PATH; Shells says how to put it there in yours. In csh or tcsh, run rehash afterwards, or the shell will not see the new programs. rehash in zsh and hash -r in sh make a shell forget an older copy it ran before.

Careful

go install ./cmd/... also installs sl-host. Once sl-host is on your PATH, every client asks it where slgod is, and fails if it has no rules file. On a machine that runs slgod itself, delete ~/go/bin/sl-host (then rehash in csh or zsh, hash -r in sh), or see the fix in Troubleshooting.

Building for the other system

Because the code is pure Go, one machine can build binaries for the other. Set GOOS and GOARCH for the one command, with env in front so that it reads the same in sh, zsh and csh, and write the result outside the source tree. From a Mac, Linux builds of slsh (amd64 and arm64), slgod (amd64) and slbotd (arm64) were tried, and each built cleanly. Building is not running: nobody has yet run a cross-built slgod against the grid.

Target machineuname -m saysSet
Linux on a PC or most cloud serversx86_64GOOS=linux GOARCH=amd64
Linux on ARM (a Raspberry Pi with a 64-bit system, ARM cloud servers)aarch64GOOS=linux GOARCH=arm64

For example, to build the Linux slgod on a Mac and copy it to the server:

$ env GOOS=linux GOARCH=amd64 go build -o ~/build/linux-amd64/slgod ./cmd/slgod
$ scp ~/build/linux-amd64/slgod server.example:go/bin/slgod

Or every program at once; this was tried in sh, zsh and csh, and gave all seven. With more than one package, go build -o takes a directory, written with a slash at the end, and puts each program in it under its own name:

$ env GOOS=linux GOARCH=amd64 go build -o ~/build/linux-amd64/ ./cmd/slgod ./cmd/slbotd ./cmd/slsh ./cmd/slrun ./cmd/slbench ./cmd/sl-host ./cmd/slhash

Keep the output out of the checkout. A binary built inside cmd/<name> must never be committed.

Whichever way you build, build every machine's programs from the same commit. A client older than slgod is refused with "this client is older than slgod". Run slgod -version and slsh --version on each machine to compare.

Keeping slgod running

slgod is meant to stay up while clients come and go. Started in a terminal, it stops when that terminal closes. Nothing handles the hang-up signal, so the avatars are not logged out cleanly then. For anything longer than an afternoon, run it under the system's service manager. The repository ships no service files. Setups has a template for each: the systemd unit has been run on Ubuntu 24.04, and the launchd plist has not been tested.

Linux

A systemd user unit in ~/.config/systemd/user/slgod.service. It runs as you, so it finds ~/.config. To keep it running when you are not logged in, run loginctl enable-linger $USER once; on Ubuntu 24.04 that needed no sudo. systemd stops it with SIGTERM, which slgod handles by logging every avatar out. Checked on Ubuntu 24.04 with systemd 255, September 2026.

macOS

A LaunchAgent plist in ~/Library/LaunchAgents. It runs as you while you are logged in. launchd does not expand ~, so every path in the plist is spelled out in full. launchd stops it with SIGTERM too, and by default gives it about 20 seconds before killing it, which is less than the 30 seconds slgod allows for logging out.

Either way, the service's PATH is short. slgod does not care, but slbotd runs slbench and slrun by name unless its program lines give full paths. Give full paths.

Firewalls

You only need to think about a firewall when a client on another machine connects to slgod. If everything runs on one machine, start slgod with -listen 127.0.0.1:7807 and no firewall rule is needed.

slgod does not configure any firewall. The commands below are ordinary use of each system's tools, shown as a starting point. Allow TCP 7807 only from the networks your clients are on. None of them has been run for this handbook, because each changes the machine's rules and needs root. On Ubuntu 24.04 the ufw lines match the forms in ufw 0.36.2's manual (man ufw); firewalld was not installed there, so its lines are unchecked.

# ufw (Ubuntu, Debian): only the home LAN
$ sudo ufw allow from 192.0.2.0/24 to any port 7807 proto tcp

# or only over a WireGuard interface
$ sudo ufw allow in on wg0 to any port 7807 proto tcp

# firewalld (Fedora, RHEL)
$ sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="192.0.2.0/24" port port="7807" protocol="tcp" accept'
$ sudo firewall-cmd --reload
# is the application firewall on?
$ /usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate

# let slgod accept connections
$ sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add ~/go/bin/slgod
$ sudo /usr/libexec/ApplicationFirewall/socketfilterfw --unblockapp ~/go/bin/slgod

Linux vs macOS

The macOS application firewall works per program, not per port, and cannot limit which addresses may connect. If it is on, macOS may ask whether slgod may accept incoming connections the first time a client connects from another machine. A rebuilt slgod is a different binary and may be asked about again. We have not watched either happen; both come from how that firewall generally behaves. To limit who can reach port 7807 on a Mac, bind slgod to a specific address with -listen, such as a tunnel address.

A firewall that silently drops the connection shows up in slsh as a wait of up to 30 seconds and then an error, rather than an immediate "connection refused". See slgod unreachable.

Never forward port 7807 from your router to the internet. See Security for what to do instead.

Starting a viewer

slsh viewer --launch starts a real viewer and logs it into the session slgod already holds (slgod must be started with -viewer; see Setups). The command it runs comes from slsh's viewer_launch setting, and that has a default only on macOS.

SettingmacOS defaultLinux default
viewer_appFirestorm-OpenSimempty
viewer_gridslgodempty
viewer_launchopen -a {app} --args --grid {grid} --login {first} {last} {password}empty
viewer_runningpgrep -f {app}.app/Contentsempty, so no check is made

On Linux, with nothing set, viewer --launch says so and stops, before it asks slgod for anything. Seen on Ubuntu 24.04:

$ slsh -c "viewer --launch"
slsh: viewer: nothing here knows how to start a viewer on linux; put a "viewer_launch = ..." line in slsh's config (~/.config/slsh/config) with {app} {uri} {first} {last} {password} where those belong

So write one. The template is split into words and run directly, with no shell. The placeholders are {app}, {grid}, {uri}, {first}, {last} and {password}. Use --grid {grid} rather than {uri}, as the macOS default does: on macOS, a viewer given --loginuri came up on whichever grid it had used last. The line below is only a shape to adapt. No viewer has been started this way on Linux. The path is wherever you unpacked the Firestorm OpenSim build, and the flags are the ones that work on macOS.

~/.config/slsh/config (Linux, an example to adapt; not tried)
viewer_grid    = slgod
viewer_launch  = /opt/firestorm-os/firestorm --grid {grid} --login {first} {last} {password}
viewer_running = pgrep -f /opt/firestorm-os/

Both systems

Use the OpenSim build of Firestorm. The Second Life build cannot be pointed at a private grid at all: on macOS it was seen to ignore the grid and go to the normal Second Life login screen. The grid has to be added in the viewer once by hand (Preferences, then OpenSim), with the login URI slsh viewer prints and the nickname viewer_grid names.

Terminals

slsh has its own line editor, history, completion and pager, so it needs no readline, $PAGER or $EDITOR, on either system. It uses a few common VT100 sequences, never clears the screen, and never moves the cursor to a fixed position, so your scrollback stays intact. Terminal.app, iTerm2 and the usual Linux terminals all speak those sequences.

  • Window resizes are followed. With no size available, slsh assumes 80 by 24.
  • NO_COLOR, set to anything, turns colour off.
  • With input from a pipe rather than a terminal, slsh reads plain lines, with no editing and no colour. -c and -f read nothing from the terminal.
  • ESC leaves chat mode. If your terminal or a multiplexer holds on to ESC, choose another key with --escape.
  • set map_ratio auto measures the font by asking the terminal. A terminal that does not answer needs the ratio set by hand (man set in slsh).
  • slsh never touches the clipboard, on either system.

To keep slgod running in a terminal you might close, use tmux or screen, or better, a service.

Shells: sh, zsh and csh

The commands in this handbook are written for three families of shell: sh (with bash, dash and ksh), zsh, and csh (with tcsh). slgo has no preference among them. macOS starts zsh for a new account and many Linux distributions start bash, but any of the three will do.

Where a command can be written to run unchanged in all three, it is, and it is shown once. Where it cannot, it is shown once per shell, each labelled; the shell switch in the top bar hides the ones that are not yours. Whichever shell you use, the prompt in the examples is always shown as $. Type what follows it. Lines starting with # are notes, not commands, and they sit on lines of their own because at a prompt zsh and csh do not take # as the start of a comment: pasted after a command, it would reach the program as more words.

To put ~/go/bin on your PATH for good, add one line to the file your shell reads, then open a new terminal or read the file again. If you set GOPATH or GOBIN, use that directory instead.

# add to ~/.profile (bash: ~/.bash_profile or ~/.bashrc)
export PATH="$PATH:$HOME/go/bin"

# then, in this terminal
$ . ~/.profile
# add to ~/.zshrc (or ~/.zprofile)
export PATH="$PATH:$HOME/go/bin"

# then, in this terminal
$ . ~/.zshrc
# add to ~/.cshrc (or ~/.tcshrc, if you have one)
set path = ( $path ~/go/bin )

# then, in this terminal
$ source ~/.cshrc

csh and tcsh keep a list of the programs on the PATH, made when the shell starts or the path is set. A program installed after that is Command not found. until you run rehash. All three shells also remember where they last found a program, so after installing a second copy earlier on the PATH, they go on running the old one until rehash (csh, zsh) or hash -r (sh, bash). Troubleshooting has both.

To set a variable for one command only, put env in front. That form is the same in every shell, and it is the one this handbook uses:

$ env NO_COLOR=1 slsh

slsh on macOS, slgod on Linux

This is the most common mixed setup: a Linux server holds the avatars and you drive them from a Mac. Nothing about it is special to the two systems, but these are the things that trip people. Tick them off as you go.

  1. Same source, both machines

    Build slgod on the server and slsh on the Mac from the same commit, or cross-build the Linux one on the Mac (above). Compare slgod -version and slsh --version.

  2. Profiles on the server only

    Profiles live in ~/.config/slgo on the Linux machine, mode 700 for the directory and 600 for each file. The Mac needs none unless you use --direct.

  3. Choose what slgod listens on

    On a trusted LAN the default :7807 works. Through an SSH tunnel, use -listen 127.0.0.1:7807. Over WireGuard or Tailscale, use the server's tunnel address. Security compares them.

  4. Open the firewall on Linux

    Only for the LAN or tunnel your Mac is on, as in Firewalls. Not needed for an SSH tunnel.

  5. Copy the secret to the Mac

    Over SSH, into a directory of mode 700:

    $ (umask 077; mkdir -p ~/.config/slgod)
$ scp server.example:.config/slgod/secret ~/.config/slgod/secret
$ chmod 600 ~/.config/slgod/secret

  6. Tell slsh where slgod is

    One of: slsh --addr server.example:7807 each time; set addr server.example:7807 once in slsh; or sl-host rules if the Mac moves between networks (sl-host).

  7. Check for a stray sl-host

    If you ran go install ./cmd/... on the Mac, sl-host is on your PATH and will be asked first. With addr set it is not asked. Without addr, give it a rules file or delete it (fix).

  8. Try it

    $ slsh -c agents

    It lists the sessions slgod holds. If it fails, Troubleshooting has each error.

  9. A viewer on the Mac, if you want one

    slgod's -viewer address must be one the Mac can reach, and in practice that means a tunnel address. The Mac's Firestorm-OpenSim must trust the Linux slgod's ~/.config/slgod/viewer-cert.pem: copy that file to the Mac and add it to Firestorm's user_settings/CA.pem, or accept the certificate dialog once. viewer_launch already has a default on the Mac.

Remember where files end up: get, put, > redirection, -f files and the transcript all read and write on the Mac, where slsh runs, not on the server.

And the other way round: slgod on a Mac

Everything above applies with the systems swapped. The differences:

  • A LaunchAgent runs only while you are logged in to the Mac. For a Mac that nobody logs in to, a LaunchDaemon run as your user is the usual answer; that is general macOS practice and has not been tried here.
  • A sleeping Mac holds no sessions. When it wakes, the connection to the grid will have ended, and slgod retries a dropped connection by itself. Keep a Mac that serves slgod awake, in System Settings or by running slgod under caffeinate -i.
  • The application firewall cannot limit by address. Use -listen with a specific address instead.
  • On the Linux client, slsh viewer --launch needs viewer_launch set (see Starting a viewer).
  • The login server is told the avatars are on a Mac. If you move slgod between systems later, see Moving slgod.
