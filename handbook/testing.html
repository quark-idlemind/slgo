Testing · Slate

Test your product with Slate

Slate is a test language for Second Life products. You write down what to touch, say or wear, and what the product must do in answer, and the slate command drives an avatar through it and tells you which steps held. This page sets it up and runs a first test.

product creators~30 min

What Slate is, and what it is not

A Slate file names the objects it will drive, then holds one test or several. A test is a list of steps. A step is one thing the tester does (a touch, a chat line, a drag, a dialog answer) and the effects that must follow. The effect is often on another object from the one touched: a button on a HUD changes a face on a sign, and the test says so.

The slate command takes one avatar, the tester, from a slgod that is already running, finds each object by its name, does the steps as that avatar, and prints what it saw. A missing effect fails its test when its time is up. A run does not hang.

Experimental

Slate, imgfind (the picture reader behind button touches) and the slate command are experimental in 1.0. They are not covered by slgo's compatibility promise and may change in any release, the language included. A file that works today may need editing after an upgrade. Keep your tests in a place where you can read them again when slgo changes.

Slate is not a viewer. It draws nothing. It reads what the region sends the tester (chat, dialogs, object updates, inventory) and what the product's faces carry, and compares that with what your file says. A button is found by reading the picture a face shows, not by looking at a screen.

What it does not do, in a few lines:

  • It drives the tester, and a second avatar only when you hand it one by name. It never picks another avatar for itself.
  • It does not walk, teleport or move the camera. Put the tester next to the product before a run.
  • It does not check particles, read the product's inventory or edit its scripts. It does not delete objects, except those its own rez steps made, and it does not refund a payment.
  • A script's permission request is refused with nothing granted, so the product's script is not left waiting, unless the file names the permission and the object with allow permission.
  • It reads animations and sounds. It does not play or stop either, and it does not read what is in them.

The full list, and every word of the language, is in doc/slate-language.md (its Goals and non-goals and Known limitations). How the runner is built, and what was measured on the grid, is in doc/slate-runner.md. This handbook points at both rather than copying them.

Set it up

You need slgod running with an avatar to test as. That is the same slgod the quick start sets up, or one of its own (see A daemon held for testing). slate is one of the programs go install ./cmd/... builds.

The tester

The tester is the avatar the run acts as. slate asks the same questions every client does:

  • -addr HOST:PORT says where slgod is. When it is empty, $SLGO_ADDR says. With neither, sl-host is asked if it is installed, and otherwise the answer is localhost:7807 (the order).
  • -agent NAME says which avatar: the profile's name, not the avatar's. When it is empty, $SLGO_AGENT says, and otherwise it is the session slgod has held longest.
$ slate -addr 127.0.0.1:7807 -agent example lamp.slate

Put the tester within reach of the product, in the same region. An object is found by name within draw distance, and a say is ordinary chat, which carries 20 m (doc/slate-language.md, The 20 m rule).

What a button test needs

A button is found by reading the picture on a face (Button text). Reading a word or a pattern uses the tesseract program, which has to be installed on the machine that runs slate. A circle, an arrow or a box is read from the pixels and needs nothing installed (doc/imgfind.md). A file that never touches by button needs neither.

The bridge, once

Most files need nothing more. A file that uses probe (to read link messages) or listen (to hear a channel the viewer is never sent) needs a small helper object, the bridge, which the tester wears on a HUD point for the run. It is an item called slate bridge in the tester's inventory, and you make it once for each account:

$ slate -make-bridge -agent example
slate: make-bridge: "slate bridge" is in the Objects folder

Making it rezzes a prim at the tester's feet and takes it into the Objects folder, so the tester needs build rights where it stands, this once. A run needs none: nothing is rezzed in the region for the bridge, which is worn and taken off. Run again with the item already there, the command says so and makes nothing, so it is safe to repeat.

A file that only touches, sits and reads public chat does not wear the bridge. One that does takes it off at the end and keeps it in inventory for the next run. If a run was killed, the bridge may be left worn and a probe left in the product; the next run reuses or replaces them.

A second avatar

Some products need two: a public mode and a private one, a visitor and an owner. A file declares one with a header, and the run is given the profile that drives it:

$ slate -agent example --avatar visitor=example-two lamp.slate

A second avatar is never chosen for you. Slate does not read what slgod holds to find one, because a daemon may hold avatars lent by other people, and each is the owner's to allow, one flag at a time. A declared avatar with no flag, a flag for a name the file does not declare, a profile that is the tester's own, and a profile the daemon does not hold are each a setup error (exit 3) before any step runs. What it can do, and how it is left as found, is in the recipes.

A daemon held for testing

An avatar can be in one session on the grid, and a login from anywhere else ends the one that is there. slgod takes that as a decision and does not log back in (doc/guide.md, Starting it twice). So the tester, and any second avatar, should be avatars that nothing else logs in:

  • Not an avatar an everyday daemon holds. A test daemon that logs it in ends the everyday one's session, and the everyday one stays down. Give the test daemon its own config directory, port and accounts: A second slgod beside the first.
  • Not one you also use in a viewer. Logging in from a viewer without logging out first ends slgod's session, and slgod stays down (the other way). To watch a test in a viewer, let the viewer take the session slgod already holds (Letting a viewer take a session) instead of logging in a second time.

slgod's own protection against two daemons is a lock on a config directory and on its ports. Two daemons with the same account in different directories are not caught by it.

When one avatar has to move between daemons

Sometimes one avatar is the only one that has the right to build or the right group, and it must be held by the everyday daemon at some times and the test daemon at others. slgo does not arrange that, so it is yours to arrange, with a guard: one small script that is the only way either daemon is started or stopped for that avatar. It checks that the other daemon has let go of the avatar before it starts this one, and refuses otherwise. Nothing is more costly to find out later than that two daemons each thought the avatar was theirs. This is advice for a setup, not a feature of slgo.

A first test

An invented product: Example Lamp, one prim with a script. Touched, it switches its point light on and says lamp on in public chat. Touched again, it puts the light out and says lamp off. The lamp is on the ground next to the tester. The file, lamp.slate:

lamp.slate
slate 1
timeout 10s

object lamp is "Example Lamp"

test "touch lights the lamp" {
  touch lamp anywhere
  expect light lamp becomes on within 5s
  expect say "lamp on" on public from object lamp within 5s
}

The file, line by line

slate 1
Every file begins with this. A file that does not is rejected.
timeout 10s
How long a step waits when an expectation has no within of its own. Without the line it is 10 seconds anyway. It is at least 100 ms and at most 120 s.
object lamp is "Example Lamp"
lamp is the name the file uses. "Example Lamp" is the prim's name in the region, matched exactly, capital letters and all. It must find one prim: none, or two with that name, is a setup failure before any step runs. (Two objects of one name are told apart with a description; the recipes page says how.)
test "touch lights the lamp" { ... }
One named test. A file may hold several, with before each and after each blocks to reset the world around them. A file with only steps and no test is one test named after the file.
touch lamp anywhere
The stimulus. It touches face 0 at its middle; the simulator does not check that the point is on the shape. The touch is a click: a press and a release at once.
expect light lamp becomes on within 5s
An expectation: the lamp's point light reads on, after reading off. becomes proves a change, because it needs an earlier reading that was not on. is on would also pass if the lamp were already lit, so it cannot show that the touch did anything. within 5s replaces the 10 seconds for this line.
expect say "lamp on" on public from object lamp within 5s
A chat line. The text is matched exactly and capital letters count; matching "RE" would make it a pattern. public is a whisper, say or shout. from object lamp takes any prim of the lamp's linkset.

The touch and the two lines after it are one step. The two expectations are a set: they may arrive in either order, and both must arrive before their time is up. A new stimulus, or then, starts the next step.

Run it

$ slate lamp.slate

The run goes to standard output as it happens, so one capture is the whole run. Only a usage error and a failed dial go to standard error.

Reading the transcript

A passing run prints lines like these. The lines are the runner's own, with the times invented.

slate: test "touch lights the lamp"
07:25:16.512 light lamp off
07:25:16.671 light lamp on
07:25:16.712 chat public from lamp: "lamp on"
slate: pass step 1
slate: pass test "touch lights the lamp"
slate: passed 1 tests
  • slate: test "..." says a test is starting.
  • light lamp off and light lamp on are readings of the lamp, each stamped with the time it arrived (UTC). The first, off, is the reading the step started from. A reading is printed whenever it differs from the last one printed.
  • chat public from lamp: "lamp on" is a line of chat. The speaker is your file's name for the object (lamp), not the name in the world. Anybody else is printed by name, and an object's name is marked [Object], so no object can pass for one of your names.
  • slate: pass step 1 comes when every expectation of the step has matched.
  • slate: pass test and the last line, slate: passed 1 tests, are the verdict. The last line of a run that finished is always its verdict.

When the lamp lights and says nothing, the same file fails like this:

slate: test "touch lights the lamp"
07:25:16.713 light lamp off
07:25:16.869 light lamp on
slate: fail lamp.slate test "touch lights the lamp" step 1 lines 7-9
  stimulus: touch lamp anywhere
    touched lamp anywhere
  expectations:
    matched light lamp becomes on within 5s at 07:25:16.869: light lamp on
    unmatched say "lamp on" on public from object lamp within 5s
  waited: 5s
  heard during the step:
    07:25:16.869 light lamp on
  seated: no
  dialog left unanswered: no
  payment: none
  captured: none
slate: failed 1 of 1 tests
  • The fail line names the file, the test, the step's number and the lines of the file it came from. Steps are numbered through before each, the test and after each together.
  • stimulus: is your line, and under it what was sent.
  • expectations: lists each as matched (with when, and the reading) or unmatched. Here the light came on and the chat line did not.
  • waited: is how long the step took. heard during the step: is the transcript lines printed while the step ran, which is the quickest way to see what the product did say.
  • seated, dialog left unanswered, payment and captured are always printed, so a failure says whether the avatar was sitting, a dialog was open, money moved, or a value was captured.

A step that fails stops its test. after each still runs, and the run goes on to the next test, with the world as the failure left it. Slate does not retry.

To watch what a product says with nothing to expect yet, touch it and wait 6s: a wait prints every line the run hears while it lasts, on every channel (Waits).

Where these lines come from

The two transcripts above are what the runner prints for this file, run against a test double of the grid, with the times invented. They are not a capture of the grid. The formats are the ones doc/slate-language.md lists under Reading the result, which also gives the sentence for every failure.

The exit codes

A script can act on the exit code. The code is 3 if setup failed, else 1 if any test failed, else 0.

CodeMeaning
0Every test passed. Cleanup warnings may still be printed.
1A test failed: a step missed an expectation, a stimulus could not be done, or a rule of the runner stopped it (not the owner, a button the finder cannot match, an ambiguous match).
2The file did not parse or failed a check. Nothing was dialled and nothing was done in the region.
3Setup failed: the dial, an object or an item that could not be found, a second avatar not given, the bridge or a probe. Setup outranks a failed test.
4The command was used wrongly: a missing file, an unknown flag, a -run pattern that does not compile or matches no test. Nothing was dialled.

Code 2 says where, to the line and column. With expect lite lamp becomes on on line 4 of a file:

$ slate bad.slate
bad.slate:4:8: expected an expectation, found lite
$ echo $?
2

Code 3 names the thing that was missing, for instance slate: setup: "Example Lamp" is not in the region, or is beyond the draw distance (looked up for 30s), or, for a file that wears the bridge before you made it, slate: setup: no "slate bridge" in inventory; run slate -make-bridge once where the tester may build. A failed dial is slate: dial: ... on standard error. -run REGEX runs only the tests whose names match, each with its before each and after each.

What a run leaves behind

A run puts the tester back as it found it, as far as it can, and says each thing it does. In short:

  • Offers. At the end of each test, an inventory offer an object made to the tester that is still waiting is declined, and printed. An offer from a person is left waiting, and printed. An offer your expect give accepted stays accepted, and the item stays in inventory.
  • Dialogs. A dialog or text box to the tester that is still open is ignored (nothing is sent to the grid) and printed. Only what arrived after the run began is touched; what was already waiting is left.
  • What the runner made. An object a rez step made is deleted to the tester's Trash when its test ends. What a drop step put into an object, or onto a face, is taken out or put back. A second avatar's group a group step changed is put back at the end of the run.
  • The probe and the bridge. The probe scripts are removed and the bridge is taken off, keeping it in inventory. A 20-prim object can spend about two minutes at this, after the verdict is known and before the run's last line.

What it does not undo is yours to undo in after each: an item wear put on stays worn until a take off; a seat stays taken until a stand; an object your product rezzed stays in the region until a delete step takes it; money paid and items received are not undone. A killed run can leave an item worn, and the next run's wear then fails with "Example Hat" is already worn on HUD top; take it off first.

The details, and the lines each cleanup prints, are in doc/slate-language.md (The tester is left as found and What a run leaves behind) and in doc/slate-runner.md (Cleanup and what a failure leaves behind).
