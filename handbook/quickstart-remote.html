Quick start · two machines

slgod on a server, slsh on your computer

Keep your avatar logged in on a machine that is always on, and drive it from your laptop. The example is the common one: slgod on a Linux server, slsh on a Mac. Other pairings work the same way.

~30 min

The picture

What each machine needs:

Server (slgod)Your computer (slsh)
Programsslgod, slhashslsh; sl-host only if the laptop moves between networks
Built fromThe same commit of the source, on both ends
Profile~/.config/slgo/exampleNone
Shared secret~/.config/slgod/secret, the same bytes on both, mode 600 in a directory of mode 700
NetworkAccepts TCP 7807 (or SSH, for the tunnel)Can reach it

No certificates to copy. The connection is TLS with a certificate slgod makes fresh at each start and the client deliberately does not check. Both ends prove they hold the secret instead, and the secret itself never crosses the wire.

Choose a route

Routeslgod listens onGood for
A. Directthe server's LAN or VPN address, port 7807A home network or a VPN you trust (WireGuard, Tailscale and the like). Least to set up.
B. SSH tunnel127.0.0.1:7807 onlyThe locked-down choice. Nothing but SSH is open on the server, and you already trust SSH.
C. sl-hostas AA laptop that reaches the server at one address at home and another away. An add-on to A.

If you are unsure, take B. It needs no firewall change and cannot be reached by anyone who cannot already log in to the server.

Steps for both routes

  1. Build the same tree on both machines

    slsh and slgod must come from the same source. The handshake between them has changed shape before, and a client older than its daemon is refused. The simplest way is to clone and build on each machine, at the same commit:

    $ git clone https://github.com/quark-idlemind/slgo.git && cd slgo
$ go install ./cmd/slgod ./cmd/slhash
$ git rev-parse --short HEAD
    $ git clone https://github.com/quark-idlemind/slgo.git && cd slgo
# COMMIT is the one the server printed
$ git checkout COMMIT
$ go install ./cmd/slsh

    Both need Go 1.26.1 or newer and the Go bin directory on PATH; the one-machine guide shows how for each shell. If a program you have just installed is not found although the directory is on PATH, run rehash in csh or zsh, or hash -r in sh or bash. Afterwards slgod -version and slsh --version each print a line that includes the commit they were built from. The two should match.

    Install only what each machine needs. go install ./cmd/... would put sl-host on the laptop, and slsh would then ask it for the server's address and fail until it has a rules file (details).

    Or cross-compile on the Mac

    slgo is pure Go with no cgo, so a Mac can build the Linux programs and copy them over. Ask the server what it is first: uname -m printing x86_64 means amd64, and aarch64 means arm64. Build inside the checkout, so the version line knows its commit, but write the binaries outside it:

    $ cd slgo
$ mkdir -p ~/slgo-linux
$ env GOOS=linux GOARCH=amd64 go build -o ~/slgo-linux/ ./cmd/slgod ./cmd/slhash
$ ssh server.example 'mkdir -p ~/go/bin'
$ scp ~/slgo-linux/slgod ~/slgo-linux/slhash server.example:go/bin/
$ go install ./cmd/slsh

    The server's ~/go/bin then has to be on its PATH, and a shell already open on the server needs rehash (csh, zsh) or hash -r (sh, bash) to see the new programs. The same works the other way round, with env GOOS=darwin on Linux. Cross-building slsh and slgod for Linux from a Mac has been tried, and both build.

  2. Put the profile and the secret on the server

    These are the same commands as on one machine; steps 3 and 4 there explain each part.

    $ (umask 077; mkdir -p ~/.config/slgo)
$ (umask 077; printf 'first = Example\nlast = Resident\nstart = last\npassword = %s\n' "`slhash`" > ~/.config/slgo/example)
$ chmod 700 ~/.config/slgo; chmod 600 ~/.config/slgo/example
$ (umask 077; mkdir -p ~/.config/slgod; openssl rand -hex 32 > ~/.config/slgod/secret)

    The secret goes in place before slgod starts. slgod reads it when it starts, before any avatar logs in, and stops if it is missing.

  3. Copy the secret to your computer, safely

    The client needs the same secret, byte for byte, at the same path. Copy it over SSH. Do not paste it into chat, mail or a notes app: anyone holding it can drive every avatar slgod holds.

    $ (umask 077; mkdir -p ~/.config/slgod)
$ scp server.example:.config/slgod/secret ~/.config/slgod/secret
$ chmod 700 ~/.config/slgod; chmod 600 ~/.config/slgod/secret

    The chmod lines matter: slsh refuses a secret whose directory is not 700 or whose file is not 600, on the laptop just as on the server. The path is ~/.config/slgod/secret on both; XDG_CONFIG_HOME does not move it.

    To check the two copies match without showing the secret, compare a checksum on each end:

    $ sha256sum ~/.config/slgod/secret
    $ shasum -a 256 ~/.config/slgod/secret

    (sha256sum is the Linux name, shasum -a 256 the macOS one. Either machine may be either system; use the one that exists. Ubuntu 24.04 has both, and they print the same line.)

    Note

    If your computer already has a different shared secret, for a slgod of its own, or the server is to have a secret of its own, do not overwrite yours. Keep the server's copy under the address slsh will dial instead: ~/.config/slgod/secret.HOST.PORT. Clients look for that file before the shared one. For route A that is secret.192.0.2.20.7807. For route B, slsh dials localhost:7807 unless told otherwise, so it is secret.localhost.7807; with --addr 127.0.0.1:7807 it is secret.127.0.0.1.7807. When separate secrets are worth it, and the full rules.

    $ scp server.example:.config/slgod/secret ~/.config/slgod/secret.192.0.2.20.7807
$ chmod 600 ~/.config/slgod/secret.192.0.2.20.7807

Now follow one route.

Route A: direct, over a LAN or VPN

  1. Start slgod on the address your computer will use

    Give -listen the server's LAN or VPN address. The examples use 192.0.2.20; ip addr on Linux, or ifconfig on macOS, shows the real one.

    $ slgod -listen 192.0.2.20:7807 example

    With no -listen at all, slgod listens on port 7807 on every interface, IPv4 and IPv6. That works too, but naming the one address keeps slgod off networks you did not mean, such as a public interface. Keep this terminal open; stopping and restarting covers running it for good.

  2. Open port 7807 on the server's firewall

    Only the server needs a change; your computer only connects out. These are ordinary firewall commands, nothing slgo sets up for you. Narrow the rule to your own network where you can. They have not been run for this handbook; the ufw line matches the forms in ufw 0.36.2's manual on Ubuntu 24.04, and the firewalld lines are unchecked.

    $ sudo ufw allow from 192.0.2.0/24 to any port 7807 proto tcp
    $ sudo firewall-cmd --permanent --add-port=7807/tcp
$ sudo firewall-cmd --reload

    macOS server

    With the macOS firewall turned on, expect to be asked whether slgod may accept incoming connections the first time it listens, and answer Allow. That is how the macOS application firewall normally treats a new program; it has not been watched with slgod. If no prompt appears (slgod started from SSH, say), allow it by hand:

    $ sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add "`which slgod`"
$ sudo /usr/libexec/ApplicationFirewall/socketfilterfw --unblockapp "`which slgod`"

  3. Tell slsh where slgod is

    Save the address once, in slsh's config file. It is plain text, one key = value a line:

    ~/.config/slsh/config
    addr = 192.0.2.20:7807
    $ mkdir -p ~/.config/slsh
$ echo 'addr = 192.0.2.20:7807' >> ~/.config/slsh/config

    For a single run, slsh --addr 192.0.2.20:7807 does the same without saving anything. Inside a running slsh, set addr 192.0.2.20:7807 writes the file for you, and takes effect from the next slsh you start.

    The address needs its port. A host name works in place of the number (addr = server.example:7807), and an IPv6 address goes in brackets ([2001:db8::20]:7807). How slsh picks an address, and what beats what, is below.

Security

Direct traffic is encrypted, and both ends prove they hold the secret. What is left is the chance of someone guessing it. slgod slows repeated wrong guesses, and a 64-character random secret is far beyond guessing. Still, do not forward port 7807 from the internet on a whim; read Security first. Never start slgod with -no-auth here. slsh cannot talk to such a daemon anyway, and on the default -listen it would let anyone on the network drive the avatar.

Route B: an SSH tunnel to a loopback-only slgod

slgod listens only on the server's own loopback address, so no other machine can reach it at all. Your computer forwards a local port to it through SSH. The secret is still checked end to end inside the tunnel. Nothing in slgo sets this up; it is ordinary SSH port forwarding, and the steps below are how the pieces fit rather than a recipe that has been watched end to end.

  1. Start slgod on loopback

    $ slgod -listen 127.0.0.1:7807 example

    No firewall change is needed. The server only has to accept SSH: on Linux that is sshd; on macOS turn on Remote Login in System Settings, under General, Sharing.

  2. Open the tunnel from your computer

    $ ssh -N -L 7807:127.0.0.1:7807 you@server.example

    This forwards port 7807 on your computer to port 7807 on the server's loopback. -N runs no remote command; the terminal just holds the tunnel open until you press Ctrl+C. To have it open whenever you connect, put the forward in ~/.ssh/config:

    ~/.ssh/config (on your computer)
    Host slgod-tunnel
    HostName server.example
    User you
    LocalForward 7807 127.0.0.1:7807

    and run ssh -N slgod-tunnel.

  3. Run slsh with no address

    $ slsh

    With no --addr, no addr = and no sl-host, slsh connects to localhost:7807, which is the tunnel. If you have set addr for route A, clear it with set addr "", or pass --addr localhost:7807.

Check it works

$ slsh -c agents

This lists the sessions the server's slgod holds, with their states, and exits. If you see your profile, everything is in place: run slsh and try the first ten commands. If slsh prints an error instead, find it below.

How slsh finds slgod

slsh settles the address in this order, and stops at the first that gives one:

  1. --addr HOST:PORT on the command line.
  2. addr = HOST:PORT in slsh's config file. server = means the same. The file is ~/.config/slsh/config, or $SLSH_CONFIG_DIR/config, or $XDG_CONFIG_HOME/slsh/config when those are set.
  3. sl-host, if it is on your PATH: slsh runs it, telling it which profile it is about to ask for, takes the first word it prints as the address, and adds :7807 unless that names a port. If sl-host fails, slsh stops and says so. It does not fall back to localhost.
  4. localhost:7807, when none of the above applies.

An address from the flag or the file is used as given; sl-host is never asked. Some details:

  • addr is read when slsh starts. set addr ... inside a running slsh saves the new value and says it is for the next slsh.
  • Do not put a # comment after the value on the same line. It becomes part of the address, silently. Comments go on a line of their own.
  • If slgod listens on anything but 7807, use --addr or addr = with that port, or put the port in the sl-host rule (192.0.2.20:7808). An sl-host rule can also be kept for one profile; see sl-host.
  • Only slsh reads this file. slrun and slbench take --addr, or ask sl-host, or use localhost. slbotd spells the flag -addr and has addr = in its own slbotd.conf.
  • Which avatar you get is a separate question: --agent, then $SLGO_AGENT, then agent =, then slgod's default. The name is a profile name on the server.

A laptop that moves between networks

Suppose the laptop reaches the server at 192.168.1.20 at home and through a VPN address elsewhere. A fixed addr = is right in one place and wrong in the other. Leave addr empty, install sl-host on the laptop, and give it a rules file saying which address to use on which network. slsh, slrun, slbench and slbotd all ask it.

~/.config/sl-host (on your computer)
192.168.1.0/24   192.168.1.20   home
0/0              10.8.0.1       anywhere else, over the VPN

The sl-host page has the rule format, a tester, and what to do when it fails.

What changes when slsh is remote

  • Files are on your computer. get and put, > redirection, -f command files and the transcript all read and write on the machine slsh runs on. This is read from the code.
  • Profiles are on the server. login NAME starts a profile that is in the server's ~/.config/slgo.
  • viewer --launch starts the viewer on your computer, but the viewer connects to the address slgod's -viewer listener gave. A slgod started with -viewer 127.0.0.1:9000 cannot be reached by a viewer on your Mac. See Setups.
  • If your computer drops off the network, slgod notices within about half a minute and releases what that slsh held. The avatar stays logged in.

What you now have

  • slgod on the server, holding your avatar, reachable only on the address you chose (or only through SSH).
  • slsh on your computer, built from the same commit, with the same secret in the same place.
  • An address slsh finds on its own: addr = in its config, the tunnel on localhost:7807, or sl-host.
  • The avatar's password only on the server.
