Recipes for what comes after the quick starts: keeping slgod running, holding several avatars, moving it, handing a session to a viewer, and upgrading without surprises. Each one starts with when you would want it.

Running slgod as a service

When you want this: slgod should keep its avatars logged in for days, start when the machine does, and not depend on a terminal staying open.

The repository ships no service files. Replace example with your profile names, and the path to slgod if go install put it somewhere other than ~/go/bin.

  • The systemd unit was run. Checked on Ubuntu 24.04 with systemd 255, September 2026: systemd-analyze --user verify passed, and every command below it did what it says, with slgod logging its avatar out and in each time.
  • The launchd plist has not been tested here. It is written from general knowledge of launchd and from what slgod does on start and stop. Read it before you use it.

Two things to settle first:

  • Set up the shared secret before the first start. slgod reads it before it logs any avatar in, and stops if it is missing or its modes are wrong.
  • Make the log directory: mkdir -p ~/.local/log && chmod 700 ~/.local/log. slgod refuses a log directory other users can enter.

The OS picker in the top bar chooses which one you see.

~/.config/systemd/user/slgod.service (Linux, checked on Ubuntu 24.04)
[Unit]
Description=slgod

[Service]
ExecStart=%h/go/bin/slgod -listen 127.0.0.1:7807 -log %h/.local/log/slgod.log example
Restart=on-failure
RestartSec=60
TimeoutStopSec=45

[Install]
WantedBy=default.target
~/Library/LaunchAgents/local.slgod.plist (macOS, untested template)
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>             <string>local.slgod</string>
  <key>ProgramArguments</key>
  <array>
    <string>/Users/you/go/bin/slgod</string>
    <string>-listen</string>  <string>127.0.0.1:7807</string>
    <string>-log</string>     <string>/Users/you/.local/log/slgod.log</string>
    <string>example</string>
  </array>
  <key>RunAtLoad</key>         <true/>
  <key>KeepAlive</key>
  <dict><key>SuccessfulExit</key><false/></dict>
  <key>ThrottleInterval</key>  <integer>300</integer>
  <key>ExitTimeOut</key>       <integer>45</integer>
  <key>StandardOutPath</key>   <string>/Users/you/.local/log/slgod.stderr</string>
  <key>StandardErrorPath</key> <string>/Users/you/.local/log/slgod.stderr</string>
</dict>
</plist>
$ systemctl --user daemon-reload
$ systemctl --user enable --now slgod
$ loginctl enable-linger $USER
$ systemctl --user status slgod
$ systemctl --user restart slgod
$ systemctl --user stop slgod
$ launchctl bootstrap gui/`id -u` ~/Library/LaunchAgents/local.slgod.plist
$ launchctl print gui/`id -u`/local.slgod
$ launchctl kickstart -k gui/`id -u`/local.slgod
$ launchctl bootout gui/`id -u`/local.slgod

After the first two lines start it, enable-linger keeps it running when you log out, and the last three show its state, restart it and stop it. enable also starts it whenever your user's service manager starts. On Ubuntu 24.04, enable-linger for your own user worked without sudo; loginctl show-user $USER -p Linger then prints Linger=yes. Other distributions may ask for sudo. slgod kept running after the ssh session that started it had closed; other logins of the same user were open at the time, so a full logout and a reboot were not tried.

The lines load and start it, show its state, restart it, and stop and unload it.

Why the templates are the way they are:

  • Full paths. launchd does not expand ~, so the plist spells out /Users/you. systemd's %h is your home directory.
  • -listen 127.0.0.1:7807 suits a machine whose clients all run on it. Change it to a LAN or tunnel address if clients connect from elsewhere (see Security).
  • Restart slowly. If slgod exits because no avatar could log in (a wrong password, say), a service manager that restarts it at once will log in again and again. The login server slows down clients that hammer it. Hence RestartSec=60 and ThrottleInterval.
  • Time to log out. On stop, both send SIGTERM. slgod then logs every avatar out, allowing itself 30 seconds. The stop timeouts give it a little more than that. Under systemd, with one avatar, stop returned within the same second, after slgod had logged logging out... and done, and systemd recorded a clean exit, so Restart=on-failure did not start it again.
  • Both log files. -log is slgod's own log. launchd's StandardErrorPath, or systemd's journal, catches what slgod cannot log itself, such as a crash. With -log set, systemctl --user status slgod and journalctl --user -u slgod showed only systemd's own starting and stopping lines; slgod's lines were all in the file.
  • No After=network-online.target. The user service manager has no such unit (systemctl --user list-units --all lists none on Ubuntu 24.04), so the line would do nothing. From reading the code, not from a test: if the network is not up when slgod starts, a login slgod counts as worth retrying is retried, and if no avatar comes up at all slgod exits with an error, and Restart=on-failure starts it again a minute later.

Check it is up with slsh -c agents. A restart is a fresh login for every avatar, which takes a few seconds each.

slbotd as a service

The same pattern works for slbotd: its own unit or plist with -log ~/.local/log/slbotd.log (spelled out in full for launchd), and no other arguments, because slbotd reads everything from slbotd.conf. On Linux, After=slgod.service is tidy but not needed: slbotd keeps retrying slgod by itself. It does not need llama-server to be up at start either. Use full paths in its program lines, because a service's PATH is short.

Several avatars in one slgod

When you want this: you have more than one account, or you want a second avatar (a bot, a builder) held beside your own.

One slgod holds as many avatars as you name. Each is a profile file in ~/.config/slgo on the slgod machine:

$ slgod -log ~/.local/log/slgod.log example builder

Flags come before the profile names. slgod example -v takes -v for a profile.

A profile you did not name can be started later, from any client:

$ slsh -c "login builder"
$ slsh -c agents

agents lists every session and configured profile with its state, and marks the default with *. The default is the session slgod has held longest.

Choosing the avatar in a client

Strongest first:

HowExampleGood for
--agent / -aslsh -a builderone run
SLGO_AGENTexport SLGO_AGENT=builder sh, zsh setenv SLGO_AGENT builder cshone terminal, and every program started from it (slsh, slrun, slbench)
agent = in slsh's configset agent builderslsh from now on (takes effect at the next start)
nothingslshthe daemon's default

The name is the profile name, the file name on the slgod machine, not the avatar's name. slbotd takes its avatars from avatar = lines in slbotd.conf instead.

Each account can be in only one session on the grid. Do not name the same profile to two slgods, and do not start a second slgod with the same settings while one is running: the second logs the same accounts in, which ends the first one's sessions, and then fails to get port 7807 (port busy). Both end up without their avatars. A second slgod with its own directory, its own port and its own accounts is fine: see A second slgod beside the first.

To stop one avatar and keep the rest: slsh -c "logout builder". slgod remembers that and will not bring it back until you say login builder.

A second slgod beside the first

When you want this: you want a daemon for development or testing, with accounts of its own, that can be started and stopped without touching the slgod you use every day.

-config DIR tells slgod to keep everything in one directory: the profiles it logs in, which are otherwise in ~/.config/slgo, and its own files (machine identity, seats, viewer certificate), which are otherwise in ~/.config/slgod. Give the second daemon its own directory and its own port, and the two read none of each other's files.

  1. Make the directory

    It must exist before slgod starts and be mode 700, like the profile directory; slgod refuses anything looser, and does not create it for you.

    $ mkdir -m 700 ~/.config/slgod.dev

  2. Put a profile in it

    A profile here has the same format as one in ~/.config/slgo, mode 600. Use an account the first slgod does not hold. This one is called dev:

    ~/.config/slgod.dev/dev
    first    = Example
last     = Tester
start    = last
password = $1$<the md5 of the password, from slhash>
    $ chmod 600 ~/.config/slgod.dev/dev

    If you want the second daemon to present the same computer to the login server as the first, copy the machine identity across before its first start. Otherwise it invents one of its own.

    $ cp -p ~/.config/slgod/config ~/.config/slgod.dev/config

  3. Start it on another port

    $ slgod -config ~/.config/slgod.dev -listen 127.0.0.1:7808 -log ~/.local/log/slgod.dev.log dev

    Leave a space between -config and the path: with -config=~/... no shell expands the ~. The first log line names the directory in use.

  4. Point clients at it

    $ slsh --addr 127.0.0.1:7808 -a dev

    A client with no --addr still goes to the first slgod. slbotd takes the address from addr = in its own config.

  5. Or let sl-host send dev there

    To type slsh -a dev with no --addr, give sl-host a rule kept for the dev profile, with the port in the address, above the general rules. The clients tell sl-host which profile they are about to ask for, and the first matching rule wins. With sl-host installed every client asks it, so the file needs a rule for the first slgod too:

    ~/.config/sl-host (where the clients run)
    0/0    127.0.0.1:7808   @dev   the development slgod
0/0    127.0.0.1               this machine
    $ sl-host -v -a dev
$ slsh -a dev

    The @dev must be spelled exactly as you give it to -a, which is the profile's file name. A client that names no profile, or another one, skips that rule and gets 127.0.0.1:7807. Clients on another machine use that machine's address for the server in both rules. Build sl-host and the clients from the same checkout: an older client adds :7807 to an address that already has a port. The rules need a network to match, so on a machine with no network up at all this fails; see the sl-host page.

Unless you give it one, the second daemon uses the shared secret, ~/.config/slgod/secret, like the first. Every client that can reach one can then reach the other, and the clients need nothing beyond the address.

A secret of its own

If the second daemon holds accounts that the first one's clients should not reach, give it its own secret. Put a file called secret in its -config directory before it starts, and slgod uses that instead of the shared one. (-secret FILE names any other file.) Its log says which it took, in a secret: line.

$ (umask 077; openssl rand -hex 32 > ~/.config/slgod.dev/secret)

Each client then keeps a copy named after the address it dials, here 127.0.0.1:7808. On the same machine:

$ cp -p ~/.config/slgod.dev/secret ~/.config/slgod/secret.127.0.0.1.7808

A client on another machine copies it over SSH, names it after the address that machine dials (through a tunnel on local port 7808, secret.127.0.0.1.7808 again, if it dials 127.0.0.1:7808), and sets it to mode 600. The name has to match the address as dialled: --addr localhost:7808 looks for secret.localhost.7808, finds nothing, uses the shared secret and is refused (details). The other clients, dialling 7807, go on using the shared secret. The full rules are in the reference.

Two clients on one avatar

When you want this: you want slsh in two terminals, or slsh open to watch while slbotd or slrun works through the same avatar.

Nothing to set up. Any number of clients can attach to one session. Start them with the same -a (or none, for the default). Type this in one terminal, and again in another, or on another machine:

$ slsh -a example

What to expect:

  • Each client sees what the grid sends. slgod also passes what one client says (chat, instant messages) to the other clients of that session, so a slsh watching beside slbotd sees both sides of the bot's conversations.
  • logout refuses while other clients are attached, and names them, in the form example is in use by slsh[1234]@198.51.100.7; use force to log out anyway.
  • slrun and slbench borrow worn objects ("slots") from slgod. Several runs at once are safe; slgod shares them out. More avatars in slgod means more runs at once.
  • A client machine that vanishes lets go of what it held after about half a minute.

Moving slgod to another machine

When you want this: slgod has been on your laptop and should live on a server, or you are replacing the server.

What moves: the profiles, and slgod's own directory, which holds the secret, its machine identity, seats and viewer certificate. The machine identity matters most. slgod invents it on its first run, and it is what makes the login server see the same computer each time. A new one looks to Linden Lab like the accounts moved to a new machine.

This order is our suggestion, pieced together from how each part works; it has not been run end to end.

  1. Build on the new machine

    From the same commit as everything else. See Linux & macOS for building on one system for another.

  2. Stop the old slgod

    Ctrl-C, or stop the service. Wait for done in its log: that means every avatar has been logged out. Disable the service so it does not come back.

  3. Copy the two directories, keeping their modes

    $ tar -C ~ -czf - .config/slgo .config/slgod | ssh server.example 'tar -C ~ -xzpf -'

    .config/slgo also holds slbotd.conf, if you have one. If slgod was started with -secret FILE, or with -config DIR, copy that file or directory too. Check the modes on the new machine: 700 on each directory, 600 on the profiles and the secret.

  4. Start it on the new machine

    Only now, and only there. Check its -listen address suits where the clients are.

  5. Point the clients at it

    Change addr in slsh and slbotd.conf, or the rules in each client's ~/.config/sl-host. The secret is unchanged, so nothing else on the clients needs to change. The exception is a client that keeps this slgod's secret under its address, as ~/.config/slgod/secret.HOST.PORT or secret.HOST: rename that file for the new address, or the client falls back to the shared secret.

  6. Re-trust the viewer certificate, if you use one

    If -viewer now names a different address, slgod replaces its certificate and logs that the viewer must be told about the new one.

Linux vs macOS

Moving between systems keeps the machine identity, but slgod reports the operating system it runs on (mac or lnx), so that part of the login changes. Profiles can override what is reported, with the platform keys, for an account that has to look like something in particular. Most people do not need to.

A laptop that moves between networks

When you want this: your laptop reaches slgod at one address at home and a different one elsewhere (a VPN address, a port forward, a tunnel).

Install sl-host on the laptop and give it a rules file. Every client then asks it for slgod's address when you have not given one. The full guide, with the rules format and its checks, is sl-host.

~/.config/sl-host (on the laptop)
192.0.2.0/24   192.0.2.20      home
0/0            198.51.100.7    anywhere else, over the VPN

The first rule that matches wins, so the catch-all goes last. A rule's address with no port gets :7807. If slgod listens on another port, put it in the rule, as in 192.0.2.20:7808, and build the clients from the same checkout as sl-host.

slbotd on a third machine

When you want this: slgod runs on a small always-on server, and slbotd (perhaps with llama-server) belongs on a machine with more memory or a GPU.

slbotd is just another client of slgod. It holds no passwords and logs nobody in; slgod does that. So the bot machine needs:

  • slbotd, built from the same commit as slgod.
  • The shared secret, copied from the slgod machine, mode 600 in a 700 directory. If that slgod has a secret of its own, keep the copy under the address slbotd dials instead, here ~/.config/slgod/secret.server.example.7807 (why).
  • ~/.config/slgo/slbotd.conf, in a directory of mode 700, with addr pointing at slgod.
  • The backstory files, and room for the conversation store.
  • slrun and slbench, if the bot runs them. They run on the bot machine, find slgod the same way any client does, and need the secret too.

The profiles stay on the slgod machine. An avatar in slbotd.conf must have its profile there, not on the bot machine.

~/.config/slgo/slbotd.conf (on the bot machine)
avatar  = builder
trusted = c75d7e57-7e57-c0de-b372-000000000001

addr = server.example:7807

program = slrun   /home/you/go/bin/slrun   --addr server.example:7807
program = slbench /home/you/go/bin/slbench --addr server.example:7807

Putting --addr in the program lines saves the programs from asking sl-host. Naming any program replaces the built-in pair, so name both. That the fixed --addr works this way follows from how program lines are built; it has not been tried here.

$ slbotd -check

-check reads the file and says what it means without connecting. On a separate machine it reports the profiles as missing, because it looks for them locally. That line is harmless here.

The full walk-through is Adding slbotd, and the model side is Bot + LLM.

Letting a viewer take a session

When you want this: you want to see the avatar in Firestorm for a while, without logging it out of slgod or stopping the programs attached to it.

slgod can serve a login endpoint of its own. A viewer that logs in there is given the session slgod already holds. The avatar does not leave the grid, and the attached programs carry on.

  1. Give the profile a viewer password

    Only a profile with viewer_password can be handed over. It is a password for this endpoint only, never sent to Linden Lab. Make its $1$ form with slhash (it asks without echoing) and add the line:

    ~/.config/slgo/example (on the slgod machine)
    first           = Example
last            = Resident
password        = $1$<the md5 of the account password>
viewer_password = $1$<the md5 of a second one, for viewers>

  2. Start slgod with -viewer

    $ slgod -viewer 127.0.0.1:9000 -log ~/.local/log/slgod.log example

    The address needs a port. On first use slgod writes a self-signed certificate to ~/.config/slgod/viewer-cert.pem and logs the login URI.

  3. Make the viewer trust the certificate

    In Firestorm, accept the certificate dialog once, or append viewer-cert.pem to Firestorm's user_settings/CA.pem. Adding the grid by hand needs the second way, because the grid manager's check of a new address shows no dialog.

  4. Add the grid

    Use the OpenSim build of Firestorm; the Second Life build cannot use a private grid. In Preferences, then OpenSim, add the login URI that slsh viewer prints, with the nickname slgod.

  5. Log in

    Either log in from the viewer as the avatar with the viewer password, or let slsh do it:

    $ slsh -c "viewer --launch"

    That uses a fresh password from slgod that works once and expires after a few minutes. It has a default on macOS only; on Linux, set viewer_launch first (how).

A wrong name, a wrong password and a profile with no viewer password all get the same answer in the viewer, on purpose: That name and password do not match a session here. slgod's log says which it was.

Security

Keep -viewer on 127.0.0.1, or on a WireGuard or Tailscale address for a viewer on another machine. -viewer :9000 listens on every interface. The viewer's UDP circuit uses a port the system picks, which no firewall rule can name and no TLS covers. More in Security.

The other way: log out, use a normal login, take it back

Without -viewer, you can let slgod go of the avatar, log in with any viewer as usual, and take it back afterwards:

$ slsh -c "logout example"

Use the avatar in a viewer, then quit the viewer, and take it back:

$ slsh -c "login example"

Logging in from a viewer without logging out first also works: the grid ends slgod's session, and slgod stays down rather than taking it back. Logging out first is tidier.

Upgrading

When you want this: you have pulled new commits and want every machine on them.

The rule is one tree for everything. Clients and slgod talk a protocol that changes between versions, and a client older than slgod is refused with "this client is older than slgod".

  1. Update and rebuild

    $ cd slgo && git pull
$ go install ./cmd/...

    On every machine: the slgod machine, each computer you run slsh on, and the bot machine. Or cross-build from one (how). If you remove sl-host from machines that run slgod, remove it again after go install ./cmd/.... After installing or removing a program, csh, tcsh and zsh need rehash to see the change; in sh or bash, hash -r.

  2. Restart slgod

    Stop it, wait for done, start it. Every avatar logs out and in again, a few seconds each. With a service: systemctl --user restart slgod, or launchctl kickstart -k gui/`id -u`/local.slgod.

  3. Restart slbotd

    It keeps running across a slgod restart and reattaches, but it is running the old binary until you restart it.

  4. Compare versions

    slgod -version, slsh --version, slbotd -version. Each names the commit it was built from.

Logs and rotating them

When you want this: slgod or slbotd runs for weeks, and you want a log that is kept somewhere safe and does not grow for ever.

$ mkdir -p ~/.local/log && chmod 700 ~/.local/log
$ slgod -log ~/.local/log/slgod.log example

What to know about these logs:

  • The file is appended to and kept at mode 600. The directory must be 700; slgod refuses to start otherwise and says what to chmod.
  • slgod's lines carry the time of day, with no date. Over a long run, the date has to come from context.
  • They are safe to read but not to publish. They hold avatar names and ids, and slbotd's log holds what people said to the bot (-q leaves conversation out). Session ids and capability URLs are cut short.
  • -log-secrets writes those in full. Use it only while debugging, and delete the log afterwards.

Neither daemon rotates its log or reopens it on a signal, and a hang-up signal stops slgod without logging out. Because the file is opened for appending, truncating it in place works, so copy-and-truncate is the way to rotate while it runs. Moving the file aside does not work, because slgod keeps writing to the moved file until it restarts; that last part is inferred from the code, not tried.

/etc/logrotate.d/slgod, or ~/.config/logrotate/slgod (Linux; change the paths)
/home/you/.local/log/slgod.log /home/you/.local/log/slbotd.log {
    weekly
    rotate 8
    compress
    missingok
    notifempty
    copytruncate
    su you you
}
$ cd ~/.local/log
$ cp -p slgod.log slgod.log.`date +%Y%m%d` && cp /dev/null slgod.log
$ gzip slgod.log.`date +%Y%m%d`

In /etc/logrotate.d it needs root, and the system's own logrotate run picks it up; su you you makes it work as you. That way has not been tried here. Without root, keep the file in your home and run logrotate yourself, with a state file of your own:

$ mkdir -p ~/.config/logrotate ~/.local/state
$ logrotate -s ~/.local/state/logrotate.state ~/.config/logrotate/slgod

Add -f to rotate now, whatever the date. Running it on a schedule, from cron or a systemd timer, is up to you and has not been tried here. Checked on Ubuntu 24.04 with logrotate 3.21.0, September 2026, with -f, as the user, on slgod's log while slgod ran under systemd: the log was copied to slgod.log.1.gz and emptied, slgod kept the same file open, and its next lines went to the start of the emptied file. slbotd's log was not tried.

Or rotate when you restart anyway, such as at an upgrade: stop slgod, move the log aside, start it.

For a live view without the log file, slsh watch shows what the session sees.

slrun and slbench, in brief

When you want this: you write LSL and want to run scripts, or measure their memory, from the command line.

slrun
Runs LSL scripts on the grid and prints what they say, each line prefixed with its file name. It exits non-zero if a script failed to compile, faulted, or never said DONE. Scripts run in objects the avatar wears, or in --object NAME, or in a throwaway prim with --rez. Four run at once by default (-j).
slbench
Measures how much script memory an LSL construct costs, by finding the 512-byte block boundary it crosses. Input comes from --code, --statement, a file, or standard input.
$ slrun --object "Test HUD" a.lsl
$ slbench --statement "llSin(1.0);"

Both connect to slgod the way slsh does, with --addr, sl-host or localhost:7807, -a for the avatar, and the same secret. They do not read slsh's addr setting, so on a remote setup give them --addr or sl-host. --backend HOST:PORT talks to a different script service over a connection with no encryption or authentication; keep that on machines you control. The full guides are in the repository's doc/guide.md.
