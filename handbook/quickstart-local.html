Quick start · one machine

Everything on one machine

Build slgo, give slgod an avatar to hold, and drive that avatar from slsh, all on the computer in front of you. At the end your avatar stays logged in while you come and go.

new users~20 min

What you are setting up

slgod is a daemon. It logs your avatar in to Second Life and keeps it logged in. slsh is a shell that attaches to slgod, lets you look around and act, and leaves again. Quitting slsh does not log the avatar out.

On one machine you need three things besides the programs:

  • a profile: one small file per avatar, holding its name and password, which slgod reads;
  • a shared secret: one file that slgod and every client read, so they can prove to each other who they are;
  • no sl-host. That helper is for a client whose slgod is on another machine. Installed here by accident, it stops slsh from finding slgod. Step 2 covers it.

Everything lives under ~/.config on Linux and on macOS alike. slgo does not use ~/Library, the macOS Keychain or a Linux keyring. The files are plain text, protected by their permissions.

Before you start

Go 1.26.1 or newer
The version comes from go.mod. With an older Go, the default setting GOTOOLCHAIN=auto downloads 1.26.1 for you. If you have set GOTOOLCHAIN=local, the build refuses instead. (That is Go's standard behaviour, not something slgo does.)
git
To fetch the source. Build inside the git checkout: that is how each program's --version learns which commit it came from.
openssl
Only to make the shared secret. Any tool that prints 32 random bytes as hex will do.
A Second Life account
Its name and password. The examples use the avatar Example Resident and the profile name example; put your own in their place.

There is no C compiler to install: slgo is pure Go, with no cgo. Windows is not supported; slsh does not build there.

$ go version
# Distribution packages are often older than 1.26.1. If so, get Go from https://go.dev/dl/
$ go version
# No Go yet? Use the installer from https://go.dev/dl/, or: brew install go

The steps

  1. Get the source and build

    Install only the three programs this setup uses: the daemon, the shell, and slhash, which turns a password into the form a profile stores.

    $ git clone https://github.com/quark-idlemind/slgo.git
$ cd slgo
$ go install ./cmd/slgod ./cmd/slsh ./cmd/slhash

    go install puts the programs in the directory go env GOBIN prints, or, when that is empty, in the bin directory under the one go env GOPATH prints. That is usually ~/go/bin, and it has to be on your PATH. The line that puts it there goes in your shell's start-up file, which depends on the shell and not on the system: macOS starts new accounts in zsh, and many Linux systems start them in bash, one of the sh family, but either may run any of the three.

    $ echo 'export PATH="$PATH:$HOME/go/bin"' >> ~/.profile
$ . ~/.profile
$ slsh --version
    $ echo 'export PATH="$PATH:$HOME/go/bin"' >> ~/.zshrc
$ . ~/.zshrc
$ slsh --version
    $ echo 'set path = ( $path ~/go/bin )' >> ~/.cshrc
$ source ~/.cshrc
$ slsh --version

    bash reads ~/.profile only when ~/.bash_profile does not exist, and a terminal that starts bash as a non-login shell reads ~/.bashrc instead. If either of those is the file your bash reads, put the line there.

    tcsh reads ~/.tcshrc in place of ~/.cshrc when there is one; if you have a ~/.tcshrc, put the line there and source that.

    If you have set GOBIN or GOPATH, use that directory in place of ~/go/bin. slsh --version prints one line naming the build and the commit. If the shell says it cannot find slsh, the directory was already on your PATH before the programs arrived and the shell has not looked again: in csh or zsh run rehash, in sh or bash hash -r, or open a new terminal. Do the same whenever you install or remove one of these programs later.

  2. Make sure sl-host is not installed

    The README's shortcut, go install ./cmd/..., installs every program here, and sl-host is one of them. Once sl-host is on your PATH, slsh stops assuming slgod is on this machine and asks sl-host instead. With no rules file for sl-host to read, every slsh then stops at once with:

    slsh: cannot find the host slgod is on: sl-host failed: exit status 2: sl-host: cannot read ~/.config/sl-host
	--addr HOST:PORT overrides

    Check, and remove it if it is there:

    $ which sl-host
# Prints a path, such as /home/you/go/bin/sl-host: remove that file.
# Prints nothing, or says it is not found: you are fine, and done here.
$ rm ~/go/bin/sl-host
# or whichever path which printed

    After removing it, run rehash in csh or zsh, or hash -r in sh or bash, so the shell forgets where it was.

    Note

    If you would rather keep sl-host, the other ways out are to put addr = localhost:7807 in ~/.config/slsh/config, or to give sl-host a rules file. Removing it is the simplest, and the sl-host page explains when you do want it.

  3. Write a profile for your avatar

    A profile is a file in ~/.config/slgo, and its file name is the profile's name. It looks like this:

    ~/.config/slgo/example
    first    = Example
last     = Resident
password = $1$<the md5 of the password, from slhash>
start    = last

    Accounts made in recent years have the last name Resident. start is where the avatar arrives: last, home, or a region name.

    The password line holds the password's md5 digest, written $1$ and hex. slhash makes it and asks for the password with echo off, so the password lands in neither your screen nor your shell history. These make the directory and write the whole file, private from the start:

    $ (umask 077; mkdir -p ~/.config/slgo)
$ (umask 077; printf 'first = Example\nlast = Resident\nstart = last\npassword = %s\n' "`slhash`" > ~/.config/slgo/example)
$ chmod 700 ~/.config/slgo; chmod 600 ~/.config/slgo/example

    slhash prints its Password: prompt straight to the terminal, so it still asks you even though its output goes into the file.

    Security

    The digest is enough to log the account in. It keeps your plain password from being reused on other sites; it does not protect the Second Life account. Treat the profile like the password itself. slgod refuses a profile directory that group or others can open, and a profile file they can read, which is what the two chmod commands are for.

    Other settings (group, neighbours, viewer_password) are in the reference. An unknown key stops the profile from loading, so check spelling.

  4. Make the shared secret

    slgod and every client prove themselves to each other with one secret, in one file. Make it before you start slgod:

    $ (umask 077; mkdir -p ~/.config/slgod; openssl rand -hex 32 > ~/.config/slgod/secret)

    That is the command slgod prints when the file is missing, with your home directory written out in place of ~. The directory must be mode 700 and the file 600; anything looser is refused. The path is always ~/.config/slgod/secret: unlike the other files, no environment variable moves it, not even XDG_CONFIG_HOME.

    Why before

    slgod reads the secret as it starts, before any avatar logs in, and stops at once if it is missing. Nothing starts until it is there.

  5. Start slgod

    Use a terminal you can leave open. Options go before the profile names; slgod example -v would treat -v as a second profile.

    $ slgod -listen 127.0.0.1:7807 example

    -listen 127.0.0.1:7807 keeps slgod to this machine. Without it, slgod listens on port 7807 on every network interface, which you only want when other machines will connect (see the remote quick start).

    slgod logs to the terminal. For each profile it says example: logging in..., then a line naming the avatar and the region it arrived in. The line to wait for begins serving gRPC on 127.0.0.1:7807: from then on clients can connect. The log shows the time of day and no date.

    If a login fails for a reason that may pass (the grid is slow, the network blipped), slgod says not up yet and keeps trying on its own. A wrong name or password gives NOT hosted instead; fix the profile and start again.

    Careful

    Hold each avatar in only one slgod. One slgod normally holds every avatar you use: name them all when you start it. A second slgod started for a profile the first already holds logs that avatar in again, which ends the first one's session, and then fails to get port 7807, so both end up without it. A second daemon with its own accounts and port is fine; see A second slgod beside the first.

  6. Attach with slsh

    In a second terminal:

    $ slsh

    With no --addr, no addr = setting and no sl-host, slsh connects to localhost:7807. It prints a banner that names the avatar, the region, and the address it came through, and then a prompt. If it prints an error instead, look it up in troubleshooting.

  7. Try the first ten commands

    These are safe to run anywhere. None of them changes anything in the world.

    TypeWhat it does
    whereThe region, your position, and the group you are acting as.
    whoAvatars in the region, nearest first.
    agentsThe sessions slgod holds. * marks the default and <- this shell marks yours.
    helpCommands by group. Then help inventory for one group, man ls for a full page, ls --help for the flags.
    cd ObjectsInventory is a filesystem. The prompt becomes /Objects$.
    ls -lWhat is in the folder you are in.
    chatChat mode: the prompt becomes Local>, and what you type is said aloud. Press Esc to come back.
    waitingOffers, dialogs and teleports waiting for an answer. The prompt shows a count, like (2) /$, when there are some.
    how do I make where I am standing my homeFinds the command for a job in your own words. It never runs anything. It works without any set-up, and understands far more ways of asking with a language model beside it: slsh with a language model.
    setLists slsh's settings. set NAME VALUE changes one and saves it.

    Then leave with quit, exit, or Ctrl+D on an empty line. The avatar stays logged in. Run slsh again and you are back at once, with no login wait.

    For one command without the prompt, use -c: slsh -c "ls -l /Objects". The slsh guide is the full account of the shell.

Stopping and restarting

To stop slgod, press Ctrl+C in its terminal (or send it SIGTERM). It logs logging out..., logs every avatar out, and logs done. That can take up to 30 seconds.

To restart, stop it and start it again. Every avatar logs in afresh, which takes a few seconds each. slgod keeps a made-up machine identity in ~/.config/slgod/config, written on its first run, so each restart looks to Linden Lab like the same computer. Leave that file alone.

To log one avatar out and keep slgod running, use logout example in slsh. slgod remembers that you did it on purpose and will not bring the avatar back until you run login example.

Viewers and slgod can each take the avatar from the other, and which one ends up with it depends on who logs in last:

  • A viewer logs in while slgod holds the avatar. The grid ends slgod's session. slgod takes that as your decision and stays logged out: it does not take the avatar back from the viewer. The one exception is a region restart, which puts everyone out; slgod comes back once the region does.
  • slgod starts, or you run login example, while a viewer has the avatar. slgod logs in, and the viewer is the one put out.

So after using a viewer, login example in slsh brings the avatar back to slgod. This is how slgod's code decides; it is described from the code rather than watched on the grid. To hand a session to a viewer without logging out at all, see Letting a viewer take a session.

If the grid connection drops on its own (a region restart, a network outage), slgod reconnects by itself and keeps trying for as long as it takes.

Careful

Closing the terminal slgod runs in stops it without logging the avatar out. slgod handles only interrupt and terminate; the hang-up a closing terminal sends is not one of them. (This is read from the code, not watched.) To keep slgod running after you close the window, start it inside tmux or screen, or run it as a service. Setups and Linux & macOS cover services.

To write the log to a file instead of the terminal, give -log a file in a directory only you can open:

$ mkdir -p ~/.local/log && chmod 700 ~/.local/log
$ slgod -listen 127.0.0.1:7807 -log ~/.local/log/slgod.log example

What you now have

  • slgod, slsh and slhash on your PATH, and no sl-host.
  • A profile, ~/.config/slgo/example, mode 600 in a directory of mode 700.
  • A shared secret, ~/.config/slgod/secret, that slgod and slsh both read.
  • slgod listening on 127.0.0.1:7807 only, holding your avatar in world.
  • slsh, which attaches in an instant and leaves the avatar where it is when you quit.
