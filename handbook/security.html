Guide · before you put slgod on a network

Security_

slgod holds live Second Life sessions, and whoever can talk to it can drive them. This page says in plain words what is worth protecting, what the programs already do about it, and what is left to you. It ends with a self-check.

What you are protecting

Two files matter more than anything else.

~/.config/slgod/secret
The shared secret drives every avatar slgod holds. Every client proves it knows this secret, and nothing else. Anyone with a copy who can reach slgod's port can do anything you can: move the avatars, empty their inventory, speak as them. Every machine that runs a client has a copy, so each one extends that trust. A slgod can have a secret of its own instead; see one secret, or one per slgod.
~/.config/slgo/<profile>
A profile is enough to log the account in, from anywhere. The $1$ value in it is an MD5 digest of the password, and that digest is the form that goes to the login server. It keeps the plain password from being reused on other sites. It does not protect the Second Life account.

The programs refuse to use either file if other users could read it: the directories must be mode 700 and the files 600. That covers other people on the same machine. It does nothing about backups, copies you make, or a machine that is lost.

Also sensitive, in descending order:

  • A profile's viewer_password, which hands the live session to a viewer. It cannot log the account in anywhere else.
  • ~/.config/slgod/viewer-key.pem, the viewer endpoint's private key.
  • Records of what people said: slsh transcripts, slbotd's conversation store and log, and packet traces. See What gets written down.

Not secret, but keep it: ~/.config/slgod/config, slgod's machine identity. Losing it makes the accounts look to Linden Lab as if they moved to a new computer.

slgod on the network

Security

slgod listens on every interface by default. -listen defaults to :7807, which accepts connections on all of the machine's addresses, IPv4 and IPv6. On a machine whose clients all run locally, start it with -listen 127.0.0.1:7807.

What protects the port:

  • TLS 1.3. slgod makes a new self-signed certificate at every start and clients do not check it. That is by design: the certificate provides encryption only, and there is nothing to distribute, pin or rotate.
  • A mutual handshake over the secret. The client proves it knows the secret, and slgod proves it back. A client refuses to talk to a server that cannot. The proofs answer random single-use challenges and are tied to the TLS session, so they cannot be replayed or relayed by a man in the middle. The secret itself never crosses the network.
  • Throttling. After three failures from one address, every answer to that address is delayed by half a second, then 1, 2 and 4 seconds. Failures from everywhere count at a tenth of the weight. Past a limit, logins are refused with too many failed logins lately; try again in a few minutes.
  • One error for every failure. A wrong guess learns nothing from the reply.

With a secret made by openssl rand -hex 32, guessing it is hopeless. A short, hand-typed secret is guessable over time, and every program warns about one under 16 bytes with a line starting WARNING: the shared secret in.

What is left: anybody who can reach the port can make slgod do the work of refusing them. By our reading of the throttle, someone flooding it with failures could trip the limit for everyone, you included. That has not been tested. Not exposing the port is the answer.

-no-auth

-no-auth turns TLS and the handshake off. slgod then serves plain, unauthenticated connections, on whatever address -listen says; nothing checks that it is loopback. With the default :7807, anyone who can reach the machine can drive the avatars.

It is not useful either: slsh, slbotd, slrun and slbench cannot connect to a -no-auth slgod at all (what that looks like). slgod's own message when the secret is missing suggests it. Make the secret instead.

The viewer endpoint

With -viewer ADDR, slgod serves HTTPS logins that hand a held session to a real viewer (how to set it up). There is no way to serve it without TLS, and a profile can be handed over only if it has a viewer_password. A wrong name, a wrong password or an unhandable profile all get the same answer, so the endpoint does not tell a stranger which avatars are there. Nothing is opened until the password matches.

Still, slgod's own guide says none of that makes the endpoint safe to put on a network. The viewer's UDP circuit uses a port the system picks, which no firewall rule can name and no TLS covers.

  • Bind it to 127.0.0.1 when the viewer runs on the slgod machine.
  • For a viewer on another machine, bind it to a WireGuard or Tailscale address.
  • -viewer :9000 listens on every interface. Do not use it.

slsh viewer --launch does not use the profile's viewer password. slgod makes a fresh one that works once and expires after a few minutes, because it has to go on the viewer's command line, where other processes can read it. On Linux, other users' processes can usually read command lines too; the single use and the expiry are what limit that.

Model servers

Neither slbotd nor slsh sends an API key. They talk plain HTTP to a server you run, and neither the server nor the connection is authenticated.

  • llama-server for slbotd receives every resident's words, the backstories, and each person's memory note. Anyone who can reach it can also use it, and, by our reading, reach the saved conversation caches in its --slot-save-path. Keep it on 127.0.0.1, or on a network only you are on. slbotd cannot send a key, so a llama-server started with --api-key would refuse it.
  • how_url for slsh receives only the question you typed and excerpts from slsh's own manual pages. No avatar, region, inventory or chat is sent. Over http:// to another machine, the question travels unencrypted.

Details are in Bot + LLM.

slbotd: trusted people, programs and strangers

Trusted means everything

A resident on a trusted line has full control of every avatar slbotd holds, by instant message. They can delete inventory, take objects out of the world, give things away, make the avatar say anything, teleport it, and run the configured programs. There is no partial trust and no confirmation step. Through :as and a program's --agent flag, that reaches other avatars slgod holds too.

Name trusted people by uuid where you can. A name matches the account's legacy name, not its display name.

Programs run as you

A program line lets trusted residents run that executable on the slbotd machine, as slbotd's user, with slbotd's whole environment, and with whatever arguments they type. There is no shell, so no pipes or expansion, but also no sandbox. The only limits are the run timeout and the output cap.

Security

Never point a program line at a shell, an interpreter or a general tool (sh, python, curl and the like). That turns "trusted in-world" into "a shell on your machine". Anything the named program can do with its flags, a trusted resident can do, including naming local files for slrun to read.

Prompt injection from chat

Anyone on a chat line (everyone, with chat = *) can write whatever they like to the model. From reading the code: the model has no tools and no way to run commands, its reply goes back only as an instant message to the person who wrote, and it is never read as a command. So an injected instruction can only change what the avatar says. The realistic harms:

  • The avatar reveals its backstory, including anything a per-person file says about someone else.
  • It reveals that person's own memory note.
  • It says something offensive under the avatar's name. You answer for that under the grid's rules.

Each person's conversation is kept apart from everyone else's, so one resident's memory is not in another's prompt. Only one-to-one instant messages are answered; local chat and group messages never reach the model.

Other residents' words

When slbotd chats, what residents write is sent to the model and kept on disk indefinitely: in the conversation store (~/.local/state/slbotd/<avatar>/<their-uuid>.json), in slbotd's log unless you pass -q, and in llama-server's slot caches. Nothing expires it. :forget NAME deletes one conversation.

Residents are not told they are talking to a model. Nothing in the code does that; it is up to you.

Other people on the same machine

On a machine other people also log in to:

  • They can connect to slgod's port, even on 127.0.0.1, like anyone else. They still need the secret.
  • Every file that holds a secret is checked or created private: profiles, the secret, slgod's directory, seats, the viewer key, logs and traces. A log path planted by another user, or a symbolic link, is refused.
  • slsh's settings file is readable by others (mode 644). It holds no secrets; keep it that way, and never put a password in viewer_launch. slsh fills the password in itself.
  • An administrator, or anyone with root, can read everything. If you do not trust the people who run the machine, do not keep your profiles or secret on it.

Notes on the table:

  • Never forward port 7807, or the viewer port, from a router to the internet. The handshake would hold, but it would leave you depending on the secret alone, and open to the flooding described above.
  • The SSH tunnel is general practice rather than something slgo documents, but it fits: TLS and the handshake run end to end inside it, so clients still need the secret. If sl-host is on the client's PATH, set addr = localhost:7807 so it is not asked.
  • A remote viewer over an SSH tunnel will not work, as far as we can tell: an SSH forward carries TCP, and the viewer's circuit is UDP. Use WireGuard or Tailscale for that.
  • With a tunnel address, slgod must start after the tunnel is up, or it cannot bind to the address.
  • A "Home LAN" you share with people you do not trust, such as a shared house or an office, is closer to "Away".

One secret, or one per slgod

One shared secret is the simple case, and the right one for most labs: one file, the same on every machine, and every client can reach every slgod. It also means that anyone holding it can drive every avatar in every slgod that uses it.

A slgod can keep a secret of its own instead. Reasons to want that:

  • It holds accounts that are not yours. A slgod for someone else's avatars, or one somebody else runs and lets you use, should not accept every client your lab's secret is on. Its owner then only has to trust the machines that hold its own secret.
  • It runs somewhere you trust less, such as a rented server. If that machine is lost, you replace its secret and the slgods at home are untouched. With one shared secret, every slgod would need the new one.

What a secret reaches is every slgod that uses it. Separate secrets make that smaller. They do not help on a client machine that holds copies of several: whoever gets that machine gets all of them.

How it is set up:

  • On the slgod machine, name the file with -secret FILE, or put it in the -config directory as secret. slgod logs secret: PATH when it starts, so you can see which one it took.
  • On each client machine, keep a copy as ~/.config/slgod/secret.HOST.PORT, named after the address that client dials. Clients look for that file first, then secret.HOST, then the shared secret. The full rules are in the reference.

The costs: every extra secret is one more file on each client to copy and to rotate. The file name follows the address as dialled, so a client that reaches the same slgod another way (a different tunnel port, localhost instead of 127.0.0.1, a new server address) needs the file under the new name. Without it the client falls back to the shared secret and is refused (what that looks like).

Backing up and rotating the secret

Backing up

The secret itself does not need a backup. If it is lost, make a new one and copy it to your machines. What does deserve a backup:

  • ~/.config/slgo/: your profiles. They are credentials, so the backup must be as private as the machine.
  • ~/.config/slgod/config: slgod's machine identity. Keep it so a rebuilt machine looks like the same computer to Linden Lab.

Rotating the secret

Do it when a machine that held the secret is lost or given away, when it was copied somewhere it should not be, or when slgod warns that it is short. slgod's own warning says what to do: make a new one, and restart slgod and its clients. slgod reads the secret when it starts. The order below is our suggestion.

# 1. make a new secret on the slgod machine
$ (umask 077; openssl rand -hex 32 > ~/.config/slgod/secret)

# 2. restart slgod; every avatar logs out and in again
$ systemctl --user restart slgod
#    on macOS: launchctl kickstart -k gui/`id -u`/local.slgod
#    in a terminal: Ctrl-C, then start it again
# 3. copy it over SSH
$ scp server.example:.config/slgod/secret ~/.config/slgod/secret

# 4. restart anything long-running there, such as slbotd

A client that still has the old secret gets authentication failed, and the message names the file it used. That is how you find the one you forgot.

Rotating a slgod's own secret

For a slgod with a secret of its own, the steps are the same, with that slgod's file on the server and the per-address copy on each client. Only that slgod and its clients are affected. For a second slgod started with -config ~/.config/slgod.dev and reached as 127.0.0.1:7808:

$ (umask 077; openssl rand -hex 32 > ~/.config/slgod.dev/secret)

Restart that slgod, then on each client that uses it:

$ scp server.example:.config/slgod.dev/secret ~/.config/slgod/secret.127.0.0.1.7808
$ chmod 600 ~/.config/slgod/secret.127.0.0.1.7808

When a lost machine held several secrets, rotate every one: the shared secret, and the slgod behind each secret.HOST.PORT or secret.HOST it had.

If a profile leaks

Rotating the secret does not help. The $1$ value logs the account in on its own. Change the account's password with Linden Lab, run slhash to make the new $1$ value, put it in the profile, and restart slgod.
