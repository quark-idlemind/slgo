Designing a product to be tested

A product is easy to test when a test can find its buttons, read its state and leave it as it was. This page is advice for the creator: textures made to be read by a machine, a record of what each one holds, and a few habits in the scripts. It is advice, and where it asks for something slgo does not do yet, it says so.

product creators~15 min

Why design for it

A test finds a button by reading the picture on a face, the way button text does. A picture made for people (soft gradients, a glow, a label sitting on a busy background) is hard for a machine to read, and a test that cannot read it either fails for no fault of the product or passes by luck. What follows is the advice to make a second, plain version of each texture for testing, and to keep a record of what is in each one, so that a test looks things up instead of reading them each time.

Slate is experimental in 1.0 (what that means). This advice does not depend on any one release: a plain texture and a record of its elements are useful to whatever reads them.

Textures that test easily

  1. Wear a test version of each texture

    A test build of the product wears a test version of every texture: near monochrome, high contrast, no glow and no gradients. Dark type on a light button, thin plain outlines, nothing behind a label. The aim is that reading it is easy.

    The docs give the reason in what the finder was tried on. It was tuned on dark type on a lighter button. Drawing test pictures for buttons on 1 October 2026, a word inside a 4 px outline was not read and one inside a 2 px outline was; a solid filled rectangle was not an outlined box; a pale ellipse with a word in it was read as both the word and a box (doc/imgfind.md, Limits found drawing test pictures for buttons). Those were drawn pictures, not a product's interface, so they say what the finder does on those and not on yours; the reliable way to know is to try it on your own texture (below).

  2. Work each texture out once

    For each test texture, write down what is in it: its elements (buttons, a slider, a panel), their borders, and their text. A test then looks the answer up and does not run the reading each time.

  3. Key the record by the texture's id

    The record for a texture is filed under the texture's uuid. That key does not go stale: a texture asset never changes, so a picture that is edited is a new texture with a new id, and the old record still describes the old asset exactly. A record needs updating only when the product starts to wear a different texture, and then the new id has no record yet, which is easy to see.

    Slate already uses a texture's id as a key in one place. touch hud showing UUID finds the one face of a linkset that shows that texture (Touch).

  4. Make a colour-keyed map, if you can

    The most reliable record is a second picture the same size as the texture, where each element is one flat colour, with a short legend saying which colour is which element. Export it from the designer's layers, where each element already is a layer, and it is exact by construction. Looking up the colour at a point answers "what is here" with no reading of text at all, so it removes OCR altogether.

  5. Keep elements in texture coordinates

    Write an element's position in the texture's own coordinates (U and V, each from 0 to 1 across the whole texture), not in the coordinates of one face. A face shows the texture turned, tiled and slid by its rotation, repeats and offset, and the same texture on two faces, or on one face after a script moved it, has the element in two places on the face. Apply the face's repeats, offset and rotation at test time, when you know them. That is the mapping the viewer uses: a touch's texture coordinate is worked out from the point on the face with those three settings, and the picture a face shows is built with them (doc/face-pictures.md).

  6. Keep the record in a plain file

    A plain file is one a designer can open, read and correct by hand, without a program of yours. If the colour map is exported wrongly, or a button moved by a pixel, the fix is a line of text. This is the record Slate reads. One line for an element area: the texture id, the element's name, its box as u0 v0 u1 v1, and optionally its text.

    test-textures.tsv · an invented example, in the format slgo reads
    # texture id               element       u0    v0    u1    v1    text
1b2b7e57-7e57-c0de-e90f-3d68ad60c7a8  open-button   0.10  0.62  0.45  0.78  Open
1b2b7e57-7e57-c0de-e90f-3d68ad60c7a8  close-button  0.55  0.62  0.90  0.78  Close
1b2b7e57-7e57-c0de-e90f-3d68ad60c7a8  status-strip  0.05  0.05  0.95  0.20

    And, for a colour map made of that texture, its legend:

    1b2b7e57.legend · an example
    # colour   element
ff0000      open-button
00ff00      close-button
0000ff      status-strip

    The rules, exactly as Slate reads them:

    • A line has 6 or 7 fields, separated by any run of spaces or tabs: the texture id, the element name, u0 v0 u1 v1, and the text when there is one. A person's spaces and a tool's tabs read the same.
    • U and V run from 0 to 1 across the whole texture, with the origin at the bottom left, the way a touch's texture coordinate (llDetectedTouchUV) does, so v0 is the lower edge. u0 is less than u1 and v0 is less than v1.
    • The name and the text are one field each. A field that holds a space, a double quote, a backslash or a # is written in double quotes, with \" and \\ the only escapes inside: "Left Arrow". Any other field is one word. The text is for people and tools; Slate does not use it.
    • A line whose first non-blank character is # is a comment; blank lines are ignored. The texture id may be in either case. One file may hold several textures.
    • A name may repeat within a texture. A texture that carries several versions of one panel, an atlas, has an ok-button area in each version. The face shows a window onto one version, and Slate touches the area of that name that is inside the window.
    • An element's point is the centre of its box, which is inside every shape a template uses, so the record has no shape.
    • The record can be written by hand or by a tool. A line that cannot be read stops the run at setup and names the file and the line.

What slgo does today

This is the part of the advice slgo can use now, and the part it cannot.

PieceToday
The picture a face showsFacePicture builds it: the texture, turned, tiled and slid as the face says, and cropped to the face. It refuses a face with planar mapping, one with a running texture animation, and one with no texture. The docs say none of this was measured against a face on the grid; the tests check the mapping against the viewer's (doc/face-pictures.md). slpic faces OBJECT DIR writes each face's picture as a PNG.
Finding a label or a figure in a pictureimgfind finds a word, a pattern, a circle or ring, an arrow and its direction, and an outlined box, and gives each one's place and centre, which is where a click goes. Text is read with the tesseract program; a drawing or a box is read from the pixels and needs nothing installed. Every threshold was measured on one sample image, and the docs say the first thing to doubt on a picture unlike it is the thresholds (doc/imgfind.md). slpic find IMAGE text TEXT asks it from a shell.
A button touch in SlateUses the two above: the face's picture, then imgfind, then a click at the centre of the match (Button text).
A lookup by texture idtouch OBJ showing UUID finds the face that shows a texture. That is all: the id finds a face, not an element on it.
An element-map lookupProvided. An elements "PATH" header names a record in the format above, a file or a directory of .tsv files beside the Slate file, and touch hud element "Open" touches the area of that name on the face that shows a recorded texture (Touch an element). Slate maps the area's centre through the face's repeats, offset and rotation, so one name can have an area on each version of an atlas and the face picks one. It refuses a face whose repeat is larger than 1 in size (2, -1.5; -1 and -0.5 are accepted), a planar face and one with a running texture animation. It reads no colour-keyed map and makes no record; the record is yours, by hand or from a tool (doc/slate-language.md). An image match (a picture template) and a finder for tiles are in the runner's list of things proposed and not adopted (doc/slate-runner.md, Open questions).

So write the record, point the file at it with an elements header, and touch by name; the button search stays for a product whose labels are better read than listed. Both are in the same file, and the record is the more reliable of the two because nothing is read from a picture.

Before you write a button test, try the finder on your own test texture. Write the face pictures out with slpic faces, run slpic find on one for a label, and see whether it finds exactly one. If it does not, the texture is the thing to change (step 1 above), and that is cheaper than a test that is flaky.

Habits in the scripts

These follow from what a test can and cannot see. Each is a thing the docs say about how Slate reads a product.

Say your state where a test can hear it

A test cannot read a script's variables. It can read what the region sends: chat, dialogs, a face, a light, floating text, a prim's size and position. So let the product say what state it has reached, in a place a test can listen:

  • Owner chat. llOwnerSay is read with expect say ... on owner, and a test that wants to read it runs as the owner.
  • A channel of its own. A line on a positive channel is heard through the bridge, with listen N in the file, and is matched on that channel only (the bridge). A channel that nobody else listens on keeps a product's debugging out of public chat.
  • Floating text. llSetText is read with expect text, byte for byte. Measured on 3 October 2026, it was in the store 96 to 171 ms after the touch.
  • A word for "ready". A product that says ready once it has finished starting lets a test wait for the word and not for a guess. The reference's HUD example does: it says ready about two seconds after it is worn.

Name your prims, and address them by name

A test binds an object by its exact, capital-sensitive name, and the name must find one prim among everything the runner can see. Give the product's root, and every child a test must touch or read, a name no other object near it has. A child with its own name is bound by that name and needs no link number, no script dropped in and no setup. A link number is the object store's best reading of the order the region sent the prims in, unless a test pays for the object's own count (Link numbers). If two objects must share a name, give each a different description, so a test can tell them apart.

Where you can, give a button a label a machine can read (text and not only a drawing), keep each label unique on its face, and avoid planar mapping and texture animation on a face a test has to read, since the finder refuses both.

Think before resetting on CHANGED_INVENTORY

A product that resets, reloads its configuration or re-reads a notecard whenever its inventory changes is hard to test, because a test can cause the event without meaning to. A drop step puts a script or an item into the product, and takes it out when the test ends. A linkmap drops a script in and removes it. Each is a change of the product's inventory, and every script in the object gets changed() with CHANGED_INVENTORY for each. The test is then run from a state it did not ask for, with nothing in the file to show it.

So: do not reset on CHANGED_INVENTORY unless you mean to. If the product must react to what is put into it (a notecard for configuration, say), compare what it holds with what it held, and throw its state away only if something it cares about changed. If it does reset, say so where a tester will see it, so they know that linkmap and drop cost a reset, and bind by name instead.
