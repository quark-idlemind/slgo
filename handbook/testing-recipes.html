Testing · recipes

What a product tester reaches for

Short recipes, one for each thing a product test does: touch a button, drag a HUD, answer a dialog, wear and rez, read a face or a light, wait. Each says what to write, points at the section and worked example in the language reference, and says what spoils it.

existing userspick what you need

How to use this page

You have run a first test (A first test). These recipes are for the next ones. The full grammar, every word and every sentence a failure prints are in doc/slate-language.md; each recipe names the section to open and the worked example near the end of that file. How the runner does it, and what was measured on the grid, is in doc/slate-runner.md.

Where a recipe says something was measured, the docs record a run on the grid, with its date. Where it says inferred or not measured, the docs read it from the viewer's source or the protocol and nobody has watched it happen. Slate is experimental in 1.0, so every recipe here may change in a release.

The examples use invented names (Example Remote, Example Banner) and invented texture ids, as the reference does.

Touch a button, or a place on a face

Reach for it when the product is driven by touch: a HUD with buttons, a sign, a vendor. Read Stimuli and Buttons in the language reference, and the worked examples A HUD button that changes another object's face, Anywhere, a link and a face and A combination button.

WriteWhat is touched
touch sign anywhereFace 0, at its middle. The simulator does not check that the point is on the shape.
touch sign face 2
touch sign face 2 at 0.9 0.5		Face 2 at its middle, or at the point S T on it, each from 0 to 1. at 0 0 is refused, because a zero point is taken as the middle.
touch sign link 3The prim at link number 3 (see Link numbers). A face or a button may follow.
touch remote button text "Open"The button whose picture reads Open. See below.
touch remote showing 5c2d7e57-7e57-c0de-66cc-c66a140e5295The one face of the linkset that shows that texture, at its middle. For a palette with a picture on each face and no label to read.

Button text

A button touch is a picture match, then a click at the match's centre. You write no pixels. Slate reads the picture on every face of the prim, looks for the parts you wrote, and clicks once:

excerpt
touch remote button text "Open" box
expect texture sign face 0 becomes 47227e57-7e57-c0de-1611-3fe69d620af1 within 8s

The parts are text "Menu" (exact, capital letters count), pattern "^Menu$", symbol "left arrow", circle and box. Several parts match one button only when their rectangles overlap, so an arrow inside a circle is one button and a label beside another button's outline is not. Exactly one match must exist: none fails the step and says which part was missing; two or more fail it and list each centre, and Slate never clicks the first. A number before the parts (button 2 text "Open") picks the second match, and face N after them limits the search to one face. image and oval are accepted and always fail, because the finder has neither.

It reads the face's picture as the face shows it, with the face's repeats, offset and rotation applied. A face with planar mapping, or a running texture animation, cannot be read: the step fails before the touch and names the face. When a button step fails after a search, the pictures it searched are written to the system temp directory and their paths printed, so you can look at what Slate saw.

What the finder reads well

The finder was tuned on dark type on a lighter button, and every threshold was measured on one sample image (doc/imgfind.md). A word inside a dark outlined frame is not read, and a solid rectangle is not a box. A small round letter was once found as a box, so a count of boxes is not a count of buttons. Prefer text alone when the label is unique on the face. On one live face a label was misread that the whole texture read correctly. If buttons are hard to find, design the textures to be read.

A button that may be absent can be pressed only if it is there, in before each or after each: touch remote button text "Close" box if shown, followed by a then expect that names the state you are driving to (worked example A guarded touch that converges on a known state). To see whether a button is there without touching it, expect button remote text "Close" box becomes gone. Write becomes gone and not is gone: a label the finder cannot read counts as zero buttons, so is gone can pass without anything having changed.

Where on a face

A touch on a face sends both of the viewer's coordinates. at S T is the point on the face. The texture coordinate is worked out from it with the face's repeats, offset and rotation, as the viewer does. A product that reads the texture coordinate on a prim whose texture is scaled, offset or turned is therefore touched where S T says. Measured on 5 October 2026 on a HUD prim whose script moves its own texture when touched: a plain touch arrived with the coordinate the face's mapping gave at that moment, and once the script had moved the texture, the same point arrived with a different one. A product that moves its own texture moves the coordinate of a point with it, so write the test from the state the product set up.

Pitfall: two touches too close together

The region takes a release and a press of one linkset that come within about a frame of each other for one touch, and the product's script then sees the first touch_start and the second touch_end. Measured on 5 October 2026 on an invented box: with no gap, the second start reached the script in 0 of 5 tries; with a gap of 10 ms in 3 of 5; with 30 ms or more, always. It merges within one linkset, whichever prims are touched, and not across objects. A touch and then a drag of the same object in the next step went about 20 ms apart, and the drag's start was lost. Slate keeps 90 ms between the release of a linkset and the next press of any prim of it, so a test needs no wait between touches. If a product still ignores a second touch, it is the product's own timing, and a wait is how a test gives it time. See doc/touch-spacing.md.

Drag a slider, or a HUD on the screen

Reach for it when the product reads a drag: a slider on a face, a HUD that moves or resizes with the mouse. Read Stimuli (Drag and Drag on the screen), and the worked examples Drag a slider, Move and resize a HUD by its glass and A HUD dragged and dragged back. The screen geometry is in doc/hud-screen.md.

excerpt
drag slider face 0 from 0.1 0.5 to 0.9 0.5 over 500ms
expect offset slider face 0 is 0.4 0 within 10s

A face drag presses at the first point, moves to the second over the time you give (500 ms if you leave over out) and releases. The release is always sent. The expectation is on what the product did, here the offset it set, and not on the drag's own coordinates. A script that reads a drag from its touch events, as many that move or stretch a picture do, sees the cursor stop only if you add dwell 300ms; without it the last updates can be lost to the release and the amount comes up short. press D holds still at the start first.

On the screen

A HUD that moves by the mouse is dragged on the screen. The HUD must be worn on a HUD point (a wear step puts it there):

excerpt
drag hud on screen from face 0 at 0.5 0.9 by 300 200 over 800ms settle
expect position hud changes near 0.005 within 10s

The start is a point in the world view in pixels from its top left corner, or a point on a face of the HUD (face 0 at 0.5 0.9), which Slate turns into pixels, so you need not know where the HUD sits. The end is to X Y or by DX DY, a distance from the start. The pixels belong to a virtual world view that the run states, not the file: --screen WxH (1920x1025 unless you say) and --hud-zoom Z (1). settle waits up to 5 seconds after the press for the region to say the pressed prim changed, for a HUD that grows a transparent prim to keep the cursor on it. After the release the step waits until the prim has kept one size for a second; one still changing after 5 seconds fails with the HUD was still changing.

The move can only be changes, because where the HUD ends depends on where it stood when it was worn, which the file does not know. Do not write a position nobody measured. And when you drag and drag back, put in near: measured on 5 October 2026, a HUD dragged and dragged back by the same pixels came back exactly on one try and a few millimetres off on another, and one resized and resized back came to about 1 percent from its size. The default is a millimetre (near and tolerances).

Pitfall: a drag that starts or ends off the view

A mouse held down cannot leave the window, so Slate refuses a start or an end that is off the world view, before anything is sent, and does not clamp it: the drag would start at 390,3745, off the 1920x1025 view; nothing was sent. A drag that works on one screen size can fail on another, so say the size you tested on with --screen. A drag has to fit its step's time, too: over, press and dwell together (and 5 seconds more for settle) must not be longer than the longest within in the step, or the timeout. That is refused when the file is checked, with exit 2.

Chat, dialogs and text boxes

Reach for it for a product that talks, offers a menu or asks a question. Read Speakers and channels, Stimuli (Choose, Answer) and Expectations (Say, Dialog, Text box); the worked examples are Owner chat, a dialog, a give, A dialog button, chosen and then said, A sorted dialog, A text box, Patterns and A channel the viewer does not deliver.

excerpt
say "menu" on -7 as owner of vendor
expect dialog from vendor text "Choose a colour" button "Red" button "Blue"

choose "Red" on vendor
expect say "red" on public from object vendor
  • Say. say "..." on N is ordinary chat on channel N. A negative channel is sent as a dialog reply, up to 254 bytes, and is the better choice for menus because a person cannot type it. as owner of OBJ is legal only if the tester owns the object.
  • The 20 m rule. Before a say, Slate measures the tester's distance to every object the step names, to the root of its linkset. More than 20 m fails the step before the say. The radius was measured (heard at 19.5 m and not at 20.5 m).
  • Hearing. expect say "red" on public ... is a whisper, say or shout, matched exactly. matching "RE" makes it a pattern (unanchored; ^ and $ to anchor). on owner is llOwnerSay, on debug the debug channel. A number other than 0 needs listen N in the header, and so the bridge, because the viewer is never sent those lines.
  • Dialogs. A dialog is matched by its text and by button clauses, and can be held to only those buttons, ordered, sorted, or a count. The buttons are counted in the order the script gave llDialog, measured to be the order the simulator sends them in, and not the order a person sees on screen.
  • Answering. choose presses a button of the dialog matched earlier: by its label, matching, button N, or a captured label. The choose is its own step. answer "text" on OBJ types into a text box, and a text box is matched by expect textbox, not expect dialog. A dialog nobody answers is ignored at the end of the test.
  • Listening. To see what a product says, touch it and wait 6s (Waits).

Wear, rez, drop and delete

Reach for it when the product is something the tester puts on, rezzes or feeds. Read Stimuli (Wear, Rez, Take off, Delete, Drop into, Drop onto), and the worked examples A HUD worn for each test, A vendor's balloon, deleted afterwards and An item dropped into an object, and a texture onto a face. The item comes from a top-level folder of the tester's inventory, named in the header: item hat is "Example Hat" in "Objects".

Wear and take off

excerpt
before each {
  wear hat on "HUD Top Left" as hud
  expect attached hud on "HUD Top Left" within 10s
  expect say "ready" on public from object hud within 10s
}

after each {
  take off hud
  expect attached hud off within 5s
}

The point is named in full, in either case; a name that only begins several points' names is refused with the choices. hud is bound to the worn object when wear returns. Put the take off in after each: the runner never takes off what a test wore, because the test may have failed before its own, and a killed run can leave the item worn, so that the next wear fails with is already worn. Measured (eighth round, doc/slate-runner.md): wear returns after about 0.2 s, and the product's own on_rez and attach arrive about 2 s after that, so the default 10 seconds covers it and within 1s does not.

Rez a copy

rez crate at 130 128 25 as made rezzes an item at a region position, and rez crate by 1 0 0 as made at an offset from the tester. The object is deleted to the tester's Trash when the test ends, whatever the outcome, and the transcript says so. Measured on 3 October 2026: where the parcel does not let the tester build, the grid makes nothing and sends an alert about 1.2 s after the request, which Slate quotes as the step's failure; where it does, a rez returned after about 2.1 s.

Delete what the product rezzed

A product that rezzes (a vendor that makes a balloon) is tested with expect rez name "Example Balloon" from vendor as balloon. That claims a new root prim near the vendor (within 10 m, which is the old llRezObject limit used as a guess, not a rule the region is known to enforce). What the product rezzed is not deleted for you. A runner that cleaned up everything would hide a product that forgot to clean up after itself, or one meant to leave its object, and deleting only what a test names is the safer default in somebody else's region. A test that wants a clean region says so:

excerpt
after each {
  delete balloon
}

delete sends the object to the tester's Trash, and only an object the tester owns: one that is not the tester's fails the step before anything is sent. In after each it may name a binding the test body made; if the test never made it, the step says so and passes. An object the product has already removed is not a failure. Measured on 6 October 2026: a worn HUD's button rezzed an object from its contents, a test claimed it with expect rez ... as, and delete in after each took it to the Trash.

Drop an item into an object

drop card into box puts a copy of an inventory item into an object's contents, as a viewer does when you drag it on. drop card onto panel face 2 puts a texture on one face. Both are the tester's alone and both are put back at the end of the test: the copy is removed, the face's old texture is restored, and a line says so. An item the tester may not copy is refused, because the drop would move it out of inventory and the run could not give it back. A script dropped in this way runs: measured on 5 October 2026, a full-permission script ran about a second after the drop (doc/scripts.md).

Pitfall: a script or an item dropped into a product changes its inventory

A product sees changed() with CHANGED_INVENTORY when a drop puts something in, and again when the end of the test takes it out. A product that resets, reloads its configuration or re-reads a notecard on that event is then in a state your test did not ask for, and nothing in the file shows it. If the product reacts to its inventory, expect that reaction in the same step as the drop, and write the later steps knowing it happened. The same event is the price of linkmap (Link numbers), and a reason for a product not to reset on it unless it means to.

Read what the product set

Reach for it to check the effect of a touch on a face, a light, a sound or an animation. Every reading is an expect in one of three forms: is X (a reading equals X, even if it already did), becomes X (it equals X and an earlier reading in the step did not) and changes (it differs from the baseline). Use becomes or changes to show that the stimulus did something. A value may be original (what it was when the test began), a capture ($x bound by an earlier step), or any with as $x to capture whatever it is. A reading can arrive late: a texture changed by a script can read old for several seconds, which Slate meets by asking the region again about once a second.

To say that something did not happen, write expect no ... within 2s. A negative still needs a real reading: no reading at all is a failure, not a pass. Silence is the pass for chat, dialogs, gives and rezzes.

near and tolerances

Reach for it when a number is worked out, or a drag came back almost where it started. The docs list the default tolerance of each reading: offset within 2/32767, repeats 1e-4, rotation 2/32768 of a turn, position and size 0.001 m on each axis, turn 0.007 degrees of angle, glow, colour and alpha 1/255, and a texture, a click, full-bright, an alpha mode and the maps exactly. A difference smaller than the tolerance is not a change.

excerpt
expect position hud becomes original near 0.005 within 10s
expect size hud link 3 is 0.8 0.4 0.016 near 2 percent within 5s

near N is a margin in the reading's own unit: metres for position and size, a fraction of a turn for rotation, degrees for a turn, 0 to 1 for glow, colour and alpha. near N percent is a share of the wanted value, of each component by itself, and does not apply to a rotation or a turn. Each component is compared alone; they are not combined, except that a turn is one angle. A share is no help for a component at or near 0.

A near never makes the test stricter than the reading can be: one below the least the grid reports is judged by the least, and the transcript says so. A passing line says how far off the reading was, and a failing line how far the nearest reading was, so the test tells you how much slack it needed. Only numbers take near: a texture, a map, a click, text, an alpha mode, chat, a dialog, a give or a count refuses it when the file is checked.

Waits, within, then and the arm point

Reach for it whenever a step has to be told when to look. Read Steps and timing in the language reference and the worked examples A toggle, A suite with before and after, A negative check and Listening to what a product says.

  • within D is how long one expectation may take. Without it the step takes the file's timeout, or 10 seconds. An expectation still unmatched when its own time is up fails the step at that moment.
  • A step is a set. The expectations after one stimulus may arrive in any order, and all must arrive. An event can satisfy only one expectation, so two expectations for the same chat line need two chat lines.
  • then means "after what the previous set matched". Use it only for a real sequence, because the grid does not preserve the order of reports from two prims, or of a texture change and a chat line from a script. Otherwise put the expectations in one step.
  • wait 4s sends nothing for four seconds and listens. It is for a product that ignores a touch that comes too soon, a script that has to finish something, or a run that only wants to see what a product says: every line the run hears while it lasts is printed with its time, on every channel, whether or not anything expects it. A wait is at most the step's time, which is at most 120 seconds.

The arm point

A step sees only events at or after its arm point. A step that starts with a stimulus arms just before the stimulus is sent, so nothing the product does in answer is missed, even if it answers before the stimulus returns. A step after a then, or with no stimulus, arms when the previous step passed.

Pitfall: a wait is armed after it, not before

wait is the one stimulus that arms when it returns, because its effect is time and what you say after it is about the state it ended in. Expectations in a wait's step read the world as it is when the wait ends. A line or a dialog heard during the wait is not the step's, and a change that happened during it is not a change after it. So wait 4s then expect colour sign face 2 is 1 1 1 passes only if the face is white after four seconds, and not if it was white when the wait began; and becomes and changes take their baseline from the end of the wait. To catch something a product does while you wait, write the expectation in the step before the wait, or in a step of its own:

excerpt
touch hud button text "Scan"
expect say "scanning" on owner from object hud within 3s

wait 6s

The first step of each test arms when that test starts, and events from an earlier test are never eligible, so a before each that sets up state is not satisfied by what the previous test left behind.

A second avatar

Reach for it when the product behaves differently for a visitor, a member of a group or an owner. Read A second avatar in the language reference, and the worked examples of that name and A second avatar in a group. Setting the run up is on the first page.

excerpt
object sign is "Example Sign"
avatar visitor

touch sign anywhere as visitor
expect dialog from sign to visitor text "Pick one" button "Red" within 5s
choose "Red" on sign as visitor

A second avatar touches, drags on a face, says, chooses and answers, and has its active group set with group visitor "Example Group". It does nothing else: it never pays, sits, wears, rezzes or deletes, and as visitor on those is refused when the file is checked. It must be in the same region as the tester and near what it touches; Slate does not move it. What it says is heard by the tester and is matched with from avatar visitor. Its inventory offers are declined the moment they are seen, a permission request to it is always refused, and a group a step changed is put back at the end of the run. Its name and profile never appear in the transcript, only its binding.

Link numbers, linkmap and probe

Reach for it only when a product's behaviour is on a child prim you cannot name any other way. Read Objects, names and link numbers in the language reference, and doc/objects.md for how the store numbers links.

  • Prefer names. A prim with its own name is bound by that name (object lid is "Example Jar Lid") and needs no number and no setup. Two objects of one name are told apart with a description: object north is "Example Sign" description "north" (worked example Two objects of one name).
  • Without anything extra, link N is the object store's order. The store's order is its best reading from the packets, in the order the region sent the set, not the script's own count. The transcript says so once per object: link order of box is the store's best reading from the packets (no linkmap header for it). When the store cannot vouch for an order (a set several prims joined in one update while it watched, or a child the region described only as an answer to a request) link N fails with a sentence that offers the other ways: the link order of "Example Tip Jar" is not known; bind the prim by its own name instead of link N, give the object a probe (the tester must own it), or take it and rez or wear it again.
  • linkmap OBJ makes it the object's own count. A small script is dropped into the root, says each link's number, key and name to the owner, and removes itself; the store then takes those numbers. The transcript says what came of it: link order of hud corrected by its own script: the store had other prims at links 2 and 3 (7 links).
  • probe OBJ gives the order too, from a script in every prim, and is what send and expect link (link messages) need. A probe and a linkmap on one object is refused. The tester must own an object that gets either, may modify it, and the parcel must run scripts.

Pitfall: linkmap changes the product's inventory twice

That is two changes of the object's inventory, the script going in and the script going out, and every script in the object gets changed() with CHANGED_INVENTORY for each. A product that reloads its configuration, resets, or re-reads its notecards on that event is tested from a state the file did not ask for, and no step is there to show it. That is why nothing is dropped unless the file says linkmap: you have chosen to risk it for the certainty. A probe also puts a script in each prim and takes it out at the end; the docs record the two events for linkmap only. If your product resets on CHANGED_INVENTORY, bind by name instead, or let the store's order stand. A worn or rezzed object bound by wear or rez cannot have a linkmap and keeps the store's order.

Not covered here

Some things a product test does are in the reference and not repeated:

  • Pay. pay vendor L$5 reason "tip" needs allow pay in the file and --pay on the command line. Either alone does not pay.
  • Sit and stand, and gives. Sit and stand, Give and A folder given. The runner never stands the avatar up or takes an item back.
  • Permission requests. Refused unless the file names them with allow permission; debit is never one of them.
  • Link messages with send and expect link, which need a probe.
  • Sequences, before each and after each, -run. Tests, sequences, before and after.
