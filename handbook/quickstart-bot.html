Quick start · a bot

Adding slbotd

slbotd gives an avatar that slgod holds a set of orders it takes from inside Second Life. At the end of this page you can IM the bot :where from a viewer and get the answer back as an IM.

~20 min

What slbotd is

slbotd is a second daemon. It sits on the far side of slgod from slsh. It attends one or more avatars at once and does two things with them:

  • It takes commands by instant message from people you have told it to trust. A command is an IM that starts with a colon, like :where or :status.
  • It can hold conversations through a language model with anyone you list. That part is optional and has its own page. This page sets up commands only.

slbotd logs nobody in and holds no passwords. For each avatar it asks slgod to host the session, then attaches to it, the same way slsh does. If you kill slbotd, every avatar stays logged in.

slbotd listens on no port. It has no socket, web page or admin shell. You control it in two ways only: by IM from inside Second Life, and by editing its configuration file and restarting it.

Before you start

  • A running slgod. If you do not have one yet, do One machine or Remote slgod first. slbotd needs slgod up and holding at least one avatar.
  • A profile for the bot's avatar, on slgod's machine. slbotd can attend the same avatar you drive with slsh, but most people give the bot an avatar of its own. This page uses a second profile called builder, whose avatar is Builder Resident. slgod reads the password, so the profile lives where slgod runs, not where slbotd runs.
  • Your own avatar's name, to put on the trusted list. This page uses Example Resident. The avatar you send commands from has to be in world, in a viewer or through slsh.
  • Go 1.26.1 and the same slgo checkout slgod was built from, on whichever machine runs slbotd. An slbotd built from an older tree is refused with this client is older than slgod.

Careful

An avatar can be in only one session on the grid. If you log a viewer in as an avatar slgod is holding, the viewer takes the session and slgod stays logged out. Send your commands from an avatar slgod is not holding, or use slsh.

Pick one. Every command block below says which machine it belongs on.

On the same machine is simpler, and it is what you want unless you have a reason. A reason might be that slgod runs on a small always-on box and you want the bot, and later its model, on a bigger one.

In the steps, blocks marked on the slgod machine go where slgod runs. Blocks marked on the slbotd machine go where slbotd runs. If that is the same machine, run them all there.

Set it up

  1. Give the bot an avatar

    Make a profile file for the bot's avatar on the slgod machine, the same way you made the one for your own avatar. The file name is the profile name. The password line takes the $1$ value that slhash prints.

    ~/.config/slgo/builder (on the slgod machine, mode 600)
    first    = Builder
last     = Resident
password = $1$<the md5 of the password, from slhash>
start    = last
    $ chmod 600 ~/.config/slgo/builder

    You do not have to restart slgod. When slbotd asks slgod to host builder, slgod reads that profile and logs it in. That is how the code reads; it has not been watched end to end here. If you want to be sure first, bring it up by hand:

    $ slsh login builder

  2. Build slbotd

    From the checkout slgod was built from:

    $ go install ./cmd/slbotd
$ slbotd -version

    The binary goes to ~/go/bin (or the bin directory under your GOPATH, if you set one; go env GOPATH prints it), which has to be on your PATH. If the shell cannot find slbotd straight after installing it, csh, tcsh and zsh need rehash to see a new command; in sh or bash, hash -r. If you ran go install ./cmd/... instead, you also got sl-host. That matters in step 4.

  3. Own machine only: copy the shared secret

    Skip this if slbotd runs on the slgod machine. Otherwise the bot machine needs the same secret file as slgod, with the same modes. Copy it by a secure route, for example with scp:

    $ mkdir -m 700 -p ~/.config/slgod
$ scp server.example:.config/slgod/secret ~/.config/slgod/secret
$ chmod 600 ~/.config/slgod/secret

    Anyone holding this file can drive every avatar slgod holds. A secret that differs from slgod's gets login refused: … authentication failed (the secret used was PATH) (fix). If that slgod has a secret of its own, store the copy under the address slbotd dials instead, such as ~/.config/slgod/secret.server.example.7807 (rules).

    slgod listens on port 7807 on every interface unless it was started with -listen. If yours listens on loopback only, see Remote slgod for your choices, including an SSH tunnel.

  4. Write slbotd.conf

    The configuration is one file, ~/.config/slgo/slbotd.conf. Its directory must be mode 700, or slbotd refuses to start. On the slgod machine that directory already exists and holds the profiles.

    $ mkdir -p ~/.config/slgo
$ chmod 700 ~/.config/slgo

    The smallest useful file names one avatar to hold and one person to trust. Use this on the slgod machine:

    ~/.config/slgo/slbotd.conf (slbotd on the slgod machine)
    avatar  = builder
trusted = Example Resident

# slgod on this machine
addr    = localhost:7807

    Use this on its own machine, with the slgod machine's name or address:

    ~/.config/slgo/slbotd.conf (slbotd on its own machine)
    avatar  = builder
trusted = Example Resident

# where slgod is
addr    = server.example:7807

    Writing addr out keeps sl-host out of it. With addr left out, slbotd runs sl-host if it is on your PATH, and falls back to localhost:7807 if it is not. An installed sl-host with no rules file is fatal. If the bot machine moves between networks, sl-host is the tool; otherwise a fixed addr is simpler.

    The format is key = value, one per line, and # starts a comment. An unknown key stops slbotd at startup, which catches typos. The file holds no secret.

  5. Check the file

    $ slbotd --check

    This reads the file, prints what it means and exits without connecting anywhere. You get the slgod address, the avatars, the trusted list, the prefix and limits, and chat: off, because there is no model yet. Then one line per avatar saying ok or why its profile would not load.

    Own machine

    --check looks for profiles on the machine it runs on. With slbotd on its own machine the profile line reports that the file is missing, because the profile is on the slgod machine. That is expected and does not stop slbotd. (Worked out from the code, not watched.)

  6. Start it

    Run it in the foreground the first time, so you can watch what it says:

    $ slbotd

    Each log line starts with the profile it is about, like builder: …. If slgod cannot be reached, you see cannot host: cannot reach slgod at …, and slbotd keeps trying, waiting longer each time up to two minutes. It takes no arguments; everything is in the file.

    Once it works, give it a log file. Its log names everybody who spoke to the avatars. The directory has to be mode 700:

    $ mkdir -p ~/.local/log && chmod 700 ~/.local/log
$ slbotd -log ~/.local/log/slbotd.log

  7. Send it a command

    Send it an IM from your own avatar. If slgod holds your avatar, as it does after the quick starts, do it from slsh: im Builder Resident opens the conversation in chat mode, and what you type there goes to the bot.

    $ slsh
/$ im Builder Resident

    Then type, one line at a time:

    :help
:status
:where

    Each answer comes back as an IM. If your avatar is one slgod does not hold, you can use a viewer instead: open an IM to Builder Resident and type the same lines.

    If nothing comes back, look at slbotd's log. A line saying refused a command from … means the name on your trusted line is not the name that arrived. See Who it obeys.

Talking to it

Only one-to-one IMs count. Local chat and group IMs are never commands. An IM that starts with the prefix, : by default, is a command. Anything else is conversation, which is ignored until you add a model.

GroupCommands
lookingwhere who look parcel regions objects worn lookup profile friends
movingtp landmark sit stand touch
talkingsay im offers accept decline chat forget
inventoryls cat mkdir rm mv cp give place take wear detach
the daemonhelp agents status as host trusted errors
programsslbench, slrun and their aliases autobench, automate, unless your file names others
:help, :help tp
What the commands are, and what one of them does. A line with only the prefix gives the help too.
:status
Whether the avatar is attached, its uuid and position, the commands running and any dropped relays.
:agents
slgod's list of avatars, with * on the ones this slbotd attends.
:errors, :errors clear
The last 50 things that went wrong for this avatar, each with how long ago. Kept in memory only, so a restart empties it.
:as helper where
With more than one avatar line, run a command as another of them. The first avatar in the file answers commands that name none.
:tp Testville 128 128 25
Words are split on spaces. Quotes group a word only at its start or after =. Nothing is expanded, and nothing reaches a shell.

An answer can take up to reply-limit IMs, 8 by default. A longer one is cut and says so. Each avatar runs up to jobs commands at once, 4 by default.

Who it obeys

Every trusted line adds one person. Repeat the line for more. A trusted person has full control of every avatar this slbotd holds: they can delete inventory, take objects out of the world, give things away, make the avatar say anything, teleport it and run the configured programs. There is no partial trust and no confirmation step.

~/.config/slgo/slbotd.conf
trusted = Example Resident
# a uuid is better where you have it: it cannot change or be taken
trusted = c75d7e57-7e57-c0de-b372-000000000001
  • Names are matched ignoring case, against the legacy name the grid sends, not the display name. For newer accounts the legacy name ends in Resident.
  • A uuid is safer. Write it where you have it.
  • By default a command from anyone else is ignored in silence and logged. answer-strangers = yes tells them I only take commands from people I have been told to trust.
  • Inventory offered by a trusted person is accepted. accept-inventory takes trusted, anyone or nobody.

Security

Trusting someone in the file is giving them your bot's avatars. It also lets them run the configured programs on the slbotd machine with whatever arguments they type. Never add a program line for a shell, an interpreter or a general tool. The security page says more.

When it goes quiet

A bot that has been failing for hours looks exactly like one with nothing to say. slbotd has three ways of telling you.

  • The trouble notice. When a trusted person writes after an hour of silence (error-gap), the first answer starts with one line such as (something has gone wrong since we last spoke -- say :errors). Strangers never see it.
  • :errors lists what went wrong, newest last.
  • The log is the full record. It is stderr, or the file given with -log.

Running it as a service

The repository ships no service files. It gives guidance for launchd on macOS only: pass -log, send stdout and stderr into ~/.local/log, and spell every path out in full, because launchd does not expand ~. The two templates below are worked out from that and from the code. Neither has been run with slbotd here. The systemd unit passes systemd-analyze --user verify on Ubuntu 24.04 with systemd 255 (checked September 2026), and the same commands started, restarted and stopped slgod's unit cleanly there (Setups).

Things that hold for both. A service gets a minimal PATH, so give program lines absolute paths, and set addr rather than relying on sl-host being found. Start order does not matter: slbotd keeps retrying slgod, and asks nothing of a model until the first conversation. It stops cleanly on SIGTERM.

~/.config/systemd/user/slbotd.service (verified, not run)
[Unit]
Description=slbotd

[Service]
ExecStart=%h/go/bin/slbotd -log %h/.local/log/slbotd.log
Restart=on-failure
RestartSec=30

[Install]
WantedBy=default.target
$ systemctl --user daemon-reload
$ systemctl --user enable --now slbotd
$ loginctl enable-linger $USER

The last line keeps it running when you are not logged in. There is no After=network-online.target, because the user service manager has no such unit; slbotd keeps retrying slgod by itself.

~/Library/LaunchAgents/example.slbotd.plist (not tested here)
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>example.slbotd</string>
  <key>ProgramArguments</key>
  <array>
    <string>/Users/you/go/bin/slbotd</string>
    <string>-log</string>
    <string>/Users/you/.local/log/slbotd.log</string>
  </array>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
  <key>StandardOutPath</key><string>/Users/you/.local/log/slbotd.stderr</string>
  <key>StandardErrorPath</key><string>/Users/you/.local/log/slbotd.stderr</string>
</dict>
</plist>
$ launchctl bootstrap gui/`id -u` ~/Library/LaunchAgents/example.slbotd.plist

Replace /Users/you with your home directory. With the OS switch in the top bar you see one of the two; flip it to see the other.

Stopping it

Press Ctrl-C, or send SIGTERM (which is what systemctl --user stop slbotd and launchctl bootout do). slbotd logs stopped; the avatars are still logged in and exits. It is telling the truth: slgod still holds them.

To log the bot's avatar out as well, ask slgod:

$ slsh logout builder

slgod remembers that you logged it out on purpose. A running slbotd stops asking for it, and checks every 30 seconds whether someone brought it back. slsh login builder brings it back. From in world, :host --force does the same; check nobody else is using that avatar first.

To change a setting, edit slbotd.conf and restart slbotd. The file is read once, at startup.

What you now have

  • slbotd attending Builder Resident through slgod, on the slgod machine or its own.
  • Commands by IM from the people on your trusted list, answered by IM.
  • :errors and the trouble notice, so a quiet bot can tell you why.
  • Plain IMs without the prefix are ignored for now.
