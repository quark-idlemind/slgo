# slgo -- handover

A Second Life client in Go, split into a long-lived server that holds
the grid session and short-lived clients that attach to it over gRPC.

This document is for whoever picks the project up next.  It covers what
is here, how to run it, what has been established about the protocol by
testing against the live grid, and -- at least as importantly -- what
has *not* been established and should not be trusted.

Written 2026-08-02, at commit `2402347`, 42 commits in.


## Why it is shaped this way

The one design decision everything else follows from:

> The server owns whatever breaks if a client restarts, and nothing
> else.

A Second Life session is expensive to establish and cannot be paused.
Logging in takes seconds, the simulator throttles repeated attempts, and
several things are said exactly once and never again.  Meanwhile the
interesting work -- the part being actively written and rewritten -- is
all client side.  So the session lives in a daemon that stays up, and
clients come and go against it without the avatar ever logging out.

That principle is not decoration.  It has decided, in order, that the
server owns:

- the **circuit** -- sequence numbers, acknowledgements, retransmission
- the **capabilities** -- URLs handed out once at login
- the **event queue** -- a long poll that must not lapse
- the **camera** -- `AgentUpdate` must keep being sent, and the
  simulator computes its interest list from the camera, so a client
  that owned it would empty the interest list for everyone else by
  exiting
- the **object cache** -- a region describes itself once, on arrival
- the **region description** -- `RegionHandshake` happens once, before
  any client is listening

Each of those was moved server-side only after a client-side attempt
failed in a specific, recorded way.  The commit messages say which.

Everything else is client side, including all of the interesting bits:
inventory, asset upload, script compilation, building, chat.  The
server relays bytes it does not understand and makes HTTP requests
against capabilities without knowing what any of them mean.


## Layout

```
msg/        the wire protocol.  Generated message types plus a
            reflection and struct-tag codec.  20k lines, of which
            14.7k are generated from message_template.msg.
agent/      one avatar's grid session: handshake, circuit, caps,
            event queue, presence, object cache, region.  5.5k lines.
server/     hosts agents, serves gRPC, relays by subscription.  1.7k.
client/     the other end of the link: Conn, xfer, asset transfer.  1.2k.
world/      the functional API most work should be written against.
            3.3k lines.
llsd/       LLSD decode and encode.  0.5k.
proto/      the gRPC service definition and generated code.
cmd/        the daemon, a CLI, and one command per experiment.
```

`go.mod` needs Go 1.26.  The only dependencies are `google.golang.org/grpc`
and `google.golang.org/protobuf` and their transitive `golang.org/x`
packages.  Nothing else.

`msg/messages_gen.go` is generated by `cmd/msggen` from
`../message_template.msg` (the parent directory, outside this module --
it belongs to the older C client this grew out of).  **Bring that file
with you.**  483 messages, 905 blocks, 2985 fields.  Regenerate with
`go generate ./msg/`.

`proto/slgov1` is generated by `protoc`; see `proto/generate.go` for the
invocation.  You need `protoc`, `protoc-gen-go` and `protoc-gen-go-grpc`
only if you change the service.


## Running it

Credentials live in `~/.config/slgo/<name>`, with the directory mode
700 and the file mode 600.  The code refuses to read anything looser.
Format:

```
first    = Firstname
last     = Lastname
password = secret
start    = last
channel  = slgo
version  = 0.1
```

Then:

```
go build -o /tmp/slgod ./cmd/slgod
/tmp/slgod -listen 127.0.0.1:7807 example
```

It logs in and stays up.  Login takes about five seconds; capabilities
another moment.  Clients attach with `world.Dial`:

```go
w, err := world.Dial(ctx, "127.0.0.1:7807", "example")
defer w.Close()
```

`cmd/slgo status` is the quickest health check.  Watch the "no handler
for" list at the bottom: it is how a protocol change announces itself,
and it is how `ImprovedTerseObjectUpdate` was noticed to be arriving 239
times between two calls while being ignored entirely.


## The world package

This is the API to write against.  Everything in it returns when the
thing has been observed to happen, or reports why it could not be
confirmed.  That is the whole point of it, because almost nothing in
this protocol answers the question it was asked.

```go
b, err := w.Build(ctx, []world.Prim{        // rez and link, first is root
    {Name: "base", Position: p, Size: sz},
    {Name: "top",  Position: p2},
})

res, err := w.Run(ctx, world.Script{        // compile, run, collect output
    In: b.Root, Name: "test", Source: src,
    Done: "SLGO-DONE", Timeout: 20 * time.Second,
})
// res.Compiled, res.Errors, res.Fault, res.Lines, res.Finished

ch := w.Chat(world.ChatFilter{Source: id}, 32)   // buffered, non-blocking
w.StopChat(ch)

w.Where(ctx)                    // position, camera, draw distance
w.SetDrawDistance(ctx, 256)
w.Inventory(ctx)                // whole tree over AIS
w.ObjectsNamed(ctx, name, t)    // what is nearby, by name
w.ObjectByID(ctx, id, t)
w.Region(ctx)
```

Concrete examples: `cmd/slgo-try` (four script experiments in a dozen
lines each), `cmd/slgo-look` (all the queries), `cmd/slgo-build2`
(multi-prim build).

The older commands -- `slgo-asset`, `slgo-hud`, `slgo-hudscript`,
`slgo-script`, `slgo-move` -- predate `world` and talk to the message
layer directly.  They were deliberately left alone: they are the record
of how each protocol answer was arrived at, and rewriting them would
lose that.  Do not treat them as examples of how to write new code.


## What has been established about the protocol

These were all measured against the live grid, not taken from
documentation.  Several contradict what the obvious guess would be.

**Almost nothing confirms itself.**  Rezzing a prim produces no reply
naming the prim.  Taking one into inventory produces no reply at all --
the item appears over AIS seconds later.  `ObjectName` and
`ObjectDescription` have no reply; the only way to know they took is to
read them back.  `world` does all of this for you.

**A region describes itself once, on arrival.**  A client attaching a
minute later is told none of it.  This was found by writing the object
query client-side and getting 7 objects where there were 195.

**Attachments are described once too, when attached.**  There is no way
to ask again.  Taking one off and putting it back on is how you learn an
attachment's local id.  Match it by the `AttachItemID` in its
`NameValue` -- the object id is new every attach.

**Scripts run per parcel, not per region.**  the no-script parcel has
`ALLOW_OTHER_SCRIPTS` off; eleven of the test region's fourteen parcels have it
on.  Attachments are *not* exempt: the same HUD with the same script is
silent on one parcel and runs on the next.  This is the single most
common reason a script "does not work".

**Compile errors come back in the upload reply**, not over UDP:
`compiled` is the verdict, `errors` holds *one* error (the first; the
compiler stops there), and `state` is `"complete"` and a new asset id is
issued *whether or not it compiled*.  The error position is a
**zero-based line and a one-based column** pointing at the *end* of the
failing token.

**Saving a script to agent inventory compiles it** -- same verdict, same
message, same position as compiling it inside a prim.  Nothing has to be
rezzed to find out whether source is good.

**Run-time errors come as chat on the debug channel**, and split into
two kinds that behave differently:

| kind | form | script |
|---|---|---|
| VM fault (Math Error, Stack-Heap Collision) | two messages, first names object and script | stops |
| library complaint (missing texture, missing sound) | one message, names neither | carries on |

The complaint arrives *in line*, before the next statement runs, so the
simulator knows which script is executing and chooses not to say.  The
debug channel is also **flood limited: eight errors, then it gags itself**
with `Too many errors... dropping further messages until the flood stops`
and sends no more.  Debugging by watching that channel past the ninth
error is watching silence that means nothing.

**A tab in an LSL string literal becomes four spaces.**  The asset store
keeps tabs byte for byte -- a save-and-read-back round trip is identical
-- but the compiler expands them, so `llStringLength("A\tB")` is 6.
`llUnescapeURL("%09")` is the workaround.

**`llSetTexture` sleeps 0.2 s per call** whether or not the texture
changes; `llSetLinkPrimitiveParamsFast` does the same work in 0.36 ms,
about 590 times faster.  The fast call is also **completely silent about
a missing texture** -- no error, no delay, no effect.  It drops the
diagnostic along with the sleep.

**`ChatFromSimulator` identifies the object, not the script inside it.**
With more than one script in an object there is nothing in the protocol
to say which spoke.  Have scripts name themselves with
`llGetScriptName()`.

**Objects: destruction is reported, proximity is not.**  Deleting or
taking an object removes it from the cache within seconds via
`KillObject`.  Teleporting away from one reports nothing at all -- the
cache grew 217 to 247 and never shrank.  So the cache is trimmed by
distance from the camera (draw distance plus a 32 m margin), which is
what it is actually being asked, and not by age: an object sitting still
is never mentioned again either, so ageing would discard the quiet ones
and keep the distant ones.

**The draw distance works one way.**  Raising it brings more in over the
following seconds (128 to 256 m took 195 objects to 217); lowering it
takes nothing away (32 m left 193).  It is a floor on what can be found,
not a filter.

**`TextureEntry` is packed by exception, not per face**: eleven sections
in a fixed order, each a default value then `(which faces, value)` pairs
ended by a zero.  The face set is a varint, seven bits per byte.
Colours are **stored inverted** -- opaque white travels as four zero
bytes.

**`CreationDate` is microseconds.**  Read as seconds it dates a fresh
prim to the year 56 million.

**`LLQuaternion` is 12 bytes on the wire** -- three floats, W recovered
by normalising -- and 16 in memory.

**`ParcelProperties` arrives over the event queue**, and the stream
subscription gates events by name as well as UDP messages.  Forgetting
to subscribe makes a parcel survey silently find nothing.  Some LLSD
integers arrive as `<binary>` rather than `<integer>`; `llsd.Int`
handles both.


## What is NOT established

Read this part before trusting anything above it.

**`ObjectUpdateCompressed` has never been seen.**  The decoder is
written, wired into the server and unit tested against hand-built blobs
-- but this simulator sends none: zero compressed objects against 111
full ones over forty seconds.  Everything about that decoder rests on
the format being what it is believed to be.

That matters more than it might because of what happened with the terse
decoder.  `ImprovedTerseObjectUpdate` was first decoded with the
position as quantised sixteen-bit values, the way every field after it
is.  It is three plain floats.  The wrong reading produced positions
that were **in range, stable, and changing plausibly**, while putting a
boat 130 m from where it was.  Nothing failed.  It was caught only by
comparing decoded positions against the same objects in the region
survey.  Assume the compressed decoder has a mistake of that kind in it
until something checks it the same way.

**The exception encoding in `TextureEntry` is untested against the
grid.**  Every capture had all six faces alike, so the face bits could
have been anything.  Setting one face and reading it back through a
script confirmed the change happened, but no updated `TextureEntry` ever
arrived to show it -- not from a later `ObjectUpdate`, not from
`RequestMultipleObjects`, not from leaving and returning.  Those changes
travel by the cached or compressed route.  Hand-built blobs cover it
instead.

**Offsets and rotation in `TextureEntry`, and velocity and acceleration
in terse updates, have only ever been observed holding zero or the
midpoint of their range.**  The scalings in the code are the
conventional ones, not measured ones.

**`ObjectUpdateCached` is not handled** (about 20 per status call).
Responding to it with `RequestMultipleObjects` is the viewer's
cache-miss path and would probably be what makes the simulator send
compressed updates.  That is the obvious next thing to try, and it would
close out the two gaps above at once.

**No region crossing, no cross-region teleport.**  Local teleport works
(`TeleportLocationRequest` with the current region handle).  The object
cache flushes automatically when the region id changes, which is the
hook a real teleport would need, but nothing exercises it.  The user has
said teleport is likely to become a server responsibility.

**No appearance, no avatar animation, no group or friend handling, no
money.**


## Testing

`go test ./...` is fast and needs no network.  The interesting tests are:

- `msg/codec_test.go` -- the wire codec, including zerocoding and
  appended acks
- `msg/compressed_test.go` -- optional-field alignment, which is the
  entire risk in that format
- `msg/placement_test.go` -- a real captured terse blob whose answer is
  known independently
- `world/chat_test.go` -- subscription delivery, dropping and closing,
  under `-race`
- `world/texture_test.go` -- a real 127-byte `TextureEntry` from a
  default box

Anything touching the grid is a command under `cmd/`, run by hand.
There is no automated live testing and probably should not be: the grid
is shared, slow, and not reproducible.


## Working habits that paid off

Offered because they are why the protocol notes above are worth
anything.

**Check against the grid, not against documentation.**  Nearly every
surprising finding here contradicts the reasonable guess.

**Prefer a result you can cross-check against an independent source.**
The terse bug was caught that way and nothing else would have caught it.

**When something cannot be confirmed, say so in the code.**  Several
doc comments say plainly which parts have been measured and which are
conventional readings.  Keep doing that; it is what makes the difference
between this and a library that looks authoritative and is quietly
wrong in three places.

**Use `llOwnerSay`, not `llSay`, in test scripts.**  Open chat reaches
everyone within twenty metres of a shared world.  `llOwnerSay` is just
as observable to a client -- it arrives as chat type 8.

**Clean up after experiments.**  Objects accumulate; an object keeps
every copy of an item put into it and renames the duplicates
(`thing`, `thing 1`, `thing 2`).  Linden land auto-returns, which will
quietly remove your test objects between sessions.
