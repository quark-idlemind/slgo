A user's guide

/$ slsh

said "slush"

A shell for Second Life. Your inventory is a filesystem, the region around you is a set of commands, and the things that want an answer queue up at the prompt. It has no view — which is exactly why it can be scripted, piped and left running. 

/$ cd Objects
/Objects$ ls -l lantern
object     2026-08-02  3ae17e57-…  /Objects/brass lantern
/Objects$ bring "brass lantern"
"brass lantern" 785f7e57-… is at 35, 73, 2001
/Objects$ start "brass lantern"
started    flicker

1Getting connected

There are two ways to be connected and slsh does both. Normally it attaches to slgod, a daemon that holds the session to the grid: the shell starts instantly, several programs can share one avatar, and quitting leaves that avatar logged in. With --direct the shell logs in itself and holds the session for as long as it runs, which needs no daemon but pays for a fresh login every time and logs the avatar out when you leave. 

$ slsh                          attach, and start at a prompt
$ slsh --direct                 log in first
$ slsh -c "ls -l Objects"       run one command and exit
$ slsh -f commands.slsh         run a file of commands and exit

Which daemon

--addr HOST:PORT says where slgod is. Without it the address comes from addr = in the configuration file, then from whatever an sl-host command prints if you have one, then from this machine — which is the ordinary case when you run your own slgod, so usually you pass nothing at all.

Which avatar

A daemon can hold several. In descending order of strength: --agent NAME (-a) for one command, SLGO_AGENT for one shell, agent = in the configuration file for this machine, and otherwise the daemon's own default — the session it has held longest. Whenever a command does not name one it tells you which it used, which is worth reading, since that default depends on the daemon's history and nothing on disk records it.

For --direct, accounts live one file per account in ~/.config/slgo. The directory must be mode 700 and each file 600 — these programs refuse to read credentials anyone else can. Storing a password as its $1$… digest works and is preferred: that is the only form that ever leaves your machine.

2The prompt, and the modes behind it

The prompt is where you are in inventory. Command mode is the outer one, because that is what a keyboard is mostly for; chat goes inward and Escape comes back out. Each mode remembers the line you had half-typed in it, so switching never loses what you were saying. 

/Objects$ chat
Local> hello everyone
(Escape)
/Objects$

Anything said to you is printed as it arrives, above whatever you are typing, in either mode. You never have to leave what you are doing to see chat, and chat never eats your half-typed command. Start in chat mode with --chat; change the key that leaves it with --escape KEY.

A number in front of the prompt is the count of things waiting for an answer — (2) /Objects$. There is a third mode too, for typing an answer several lines long; see Things waiting.

While a command runs there is no prompt. A prompt means the shell is ready for the next line; what you type during a long command waits its turn and arrives when the command is done.

3Inventory is a filesystem

cd, ls, pwd, cat, mkdir, mv, cp, rm and find all work the way you expect them to. 

/$ cd Objects
/Objects$ ls -l                    kind, date and id as well
/Objects$ ls -lt                   newest first
/Objects$ ls -r Textures           descend into subfolders
/Objects$ find lantern             names containing it, from here down
/Objects$ cat "my notecard"
/Objects$ mv "old lamp" sorted     into a folder
/Objects$ mv "old lamp" lamp       a plain name renames instead
/Objects$ rm "old lamp"            permanent; there is no undo

cd with no path goes to the root and .. goes up. Names may contain almost any printable character, so paths escape: / separates, \/ is a slash inside a name, and quotes work too.

Names are not unique — one folder can hold a dozen things with the same name — so mv, rm and cat take an item's id anywhere they take a path. That is what makes a listing of duplicates usable, and what ls -l prints ids for. rm takes the first thing of the name it is given; --remove-all-copies takes all of them and says how many. Two listings of a folder that has not changed are identical, which is what makes them worth diffing and worth editing into commands.

Getting text and pictures in and out

cat prints a notecard or a script; get -o FILE saves a texture as a PNG; put FILE uploads an image as a texture, which costs L$, so -N says what it would do without doing it. new makes an empty notecard or a script, or one from a file, and save FILE PATH writes a local file into a notecard or script that already exists. 

/$ new --kind script --from hello.lsl greeter
greeter 7a887e57-7e57-c0de-afe2-f49e9af56164
/$ save hello.lsl greeter
greeter: 81 bytes written, and it compiled

A script that does not compile is still saved — the save succeeded and the compile failed, in that order — and the compiler's complaint is printed underneath.

4The world around you

wherethe region and position you are at, and the group you are acting as
whowho else is in the region, nearest first
lookwhat the simulator said about the region
objectsthe objects the region has described; -c for the prims inside each
tp X Y Zmove to a position in this region
caps · features · lslwhat this simulator grants, supports and implements

objects, caps, features and lsl all take text to filter by, so lsl llSensor answers what this grid's LSL actually has rather than what the wiki remembers.

tp moves within the region only. Another region is a different simulator needing a new circuit and a new set of capabilities, which slgod does not do yet — so arriving somewhere else is still a matter of logging in there.

What you are wearing

worn lists the attachments, wear puts one on and detach takes it off. A point holds one attachment, so wearing something on an occupied point knocks off what was there — the viewer's Wear, not its Add. With no --at the object goes wherever it says it belongs. 

/$ wear Objects/tape measure
tape measure is worn on left hand
/$ wear --at "HUD top right" Objects/panel
/$ detach "tape measure"
tape measure is no longer worn on left hand

The group you act as

Land usually grants building to a group rather than to people, and a headless login starts with none — so an avatar that cannot rez on land it is entitled to is usually an avatar acting as nobody. group lists what it could act as and marks what it does; group NAME changes it, and group none clears it.

5Objects, and the scripts inside them

take brings a rezzed object into inventory and bring puts one back into the world — the pair is named that way round because rez already means "build what this JSON file describes", which is a different act from "put back what I took".

take · bringbetween the world and inventory; take --copy tries to leave the original standing
place · touchmove a rezzed object; click one, on a named face at a named point
link · unlinkjoin objects into one; take one apart, or free a single prim from it
permswhat the next owner, the group or everyone may do: copy, modify, transfer, move
texturewhat a face looks like, or with no flags, what it looks like now
dump · reform · rezdescribe an object as JSON, change it to match a file, or build one from it
dropput an inventory item inside a rezzed object

link names the root first and everything that goes under it. unlink given a root takes the whole thing apart and given one prim frees just that prim — and it lists what it freed with their keys, because a linkset answers to its root's name while the pieces keep their own, which for anything built by hand is often "Object" for all of them.

Inside an object

An object holds inventory of its own, with its own ids. The same three verbs reach it with --in, and scripts have two more. 

/$ ls --in "brass lantern"
lsltext    flicker
/$ new --in "brass lantern" --from flicker.lsl flicker
flicker is in brass lantern and running
/$ stop "brass lantern"
stopped    flicker
/$ start "brass lantern" flicker
started    flicker

start and stop with no script name mean every script in the object, one line each, and they wait for the object to agree rather than reporting what they merely asked for. A script already in the state you asked for says already and nothing is sent. new --in compiles the script inside the object and starts it, which is what dropping one in does not do.

6People

say TEXTone line to local chat without leaving command mode
chat [WHO]enter chat mode, on local chat or in a conversation
im WHO TEXTsend one message without entering chat mode
talkthe conversations chat mode cycles between with Tab
lookup TEXTsearch the grid for people by part of a name
profile WHOborn, payment, partner, about text, and the groups they list
friends [-a]friends online, or all of them
offer · giveoffer friendship; offer an inventory item

A name is resolved three ways, in order: what this shell already knows, then the avatars in the region, then — for profile alone — a search of the whole grid. The last step is profile's only because reading a profile is public and harmless, while im and give reach out to whoever is found, and a wrong guess there sends something to a stranger. 

/$ profile Torley Linden
Torley Linden
  key       8c717e57-7e57-c0de-6f29-62af189183f7
  born      9/15/2004
  payment   not revealed
  groups    2 listed, which is not every group they are in
  2d837e57-… Weather Nut          Windlight Region Testers

The groups in a profile are the ones somebody chose to publish, so it is what they say about themselves rather than a complete list.

An offer is not a transfer: nothing moves until it is accepted. accept puts what arrives in the folder you are in, so cd there first if that is where it belongs.

7Things waiting for an answer

A script puts up a dialog, somebody offers a teleport, an object asks for permission to animate you. They queue, the prompt counts them, and four commands deal with them: waiting lists, answer says yes, no declines and tells whoever asked, and ignore leaves one waiting but stops counting it. 

(2) /$ waiting
1  dialog      a lamp asks: on or off?
                answer 1 on, answer 1 off, no, ignore
2  teleport    Some Resident offers a teleport: "Join me in Pelmar Reach!"
                answer, no, ignore
(2) /$ answer 1 on
pressed "on"

A number keeps meaning the same thing: answering one does not renumber the rest, so the answer 2 you had already half typed still means what you meant. Numbers start again at 1 once the list is empty.

A text box wants several lines

llTextBox is an editor rather than a field, so answer N with no text starts taking lines. Every line means itself. Ctrl-D ends the answer and sends it, taking a half-typed line with it as mail does; Escape throws away what you have typed and keeps the question; Ctrl-C sends nothing and says which number is still waiting. Ordinary line editing — backspace, Ctrl-U, the arrows — works on the line you are typing. 

(1) /$ answer 1
a sign asks: your name?  — type the answer; ^D ends it, ESC starts again, ^C sends nothing
1 text> Quark Idlemind
1 text> of no fixed abode
(Ctrl-D)
told a sign 2 lines

For a scripted answer, answer --file PATH N sends a file's contents instead. A text box carries 254 bytes; more than that is refused before it is sent rather than truncated on the way.

When money is involved

A group invitation carrying a signup fee is never accepted by a bare answer N. The fee has to be typed back — answer 3 L$50 — and a wrong figure is refused by naming the right one. An invitation whose fee the message did not state is treated as costing something unknown rather than as free.

What is waiting belongs to the shell that saw it arrive. slgod relays these and does not keep them, so a shell started afterwards sees nothing, and slsh -c "waiting" — a shell that attaches, runs and exits — will always say there is nothing.

8The daemon and its avatars

agentsthe sessions slgod holds, then the profiles it could hold
host NAMEbring an avatar up
logout NAMEput one down, and keep it down until asked for by name
statushow this session and its circuit are doing
watchprint grid messages as they arrive, by name or all of them

status is the one to reach for when a session looks idle and you want to know whether it is idle or broken: packet counters, retransmissions, and the messages arriving that this build has no handler for — which is how a protocol change announces itself. watch opens a connection of its own, so watching everything for an hour does not disturb the shell you are typing in.

Both host and logout refuse to be casual. logout will not take a session that clients are attached to and names them instead; host will not restart something that was stopped deliberately. -f overrules either, once you know what you are overruling.

9A viewer, when you want eyes

slgod can hand its live session to a real viewer: the avatar never logs in twice, so the session a script is driving and the session you are looking at are the same one. viewer says where that is offered and whether anybody has taken it; viewer --launch starts one and logs it in. 

/$ viewer
viewer logins at http://127.0.0.1:9000/
  add a grid with that login URI and log in as Quark Idlemind
  no viewer has taken this session
/$ viewer --launch
starting a viewer at http://127.0.0.1:9000/, logged in as Quark Idlemind
  the password it was given works once and expires in 5 minutes

The password is minted by the daemon for that one login and expires. Nothing is stored: the profiles keep only a digest, which is why the launcher cannot simply read one.

Two things have to be true for the launch to land. The daemon must have been started with -viewer ADDR — otherwise viewer says so and names the flag. And the viewer must be one that can be pointed at a private grid: a Second Life–only Firestorm silently ignores the login URI and comes up on the main grid, so the OpenSim build is the one to install, with the login URI added once as a grid in its preferences.

10Files, redirection and settings

Any command's output can be redirected, and a file of commands can be run with . — which together are the point of having a shell at all. 

/$ ls -l /Objects > listing
/$ echo done >> listing

$ awk '{print "mv " $3 " /Objects/sorted"}' listing > moves
$ slsh -f moves
slsh: cd: no folder "sorted"
slsh: moves:1: cd sorted
slsh: stopped; 43 lines were not run

A file stops at the first command that fails, naming the line it gave up on and how much it did not run — which matters because such a file usually begins by changing folder, and carrying on after that failed would run every line that follows somewhere else. A one-shot run exits non-zero when anything failed, so a script wrapping slsh can tell without reading the output.

The configuration file

~/.config/slsh/config, as key = value lines with # for comments. A flag always beats the file, and a misspelled key is an error rather than a setting that silently does nothing. 

addr    = HOST:PORT
agent   = NAME
escape  = ESC

viewer_app    = Firestorm-OpenSim
viewer_grid   = slgod
viewer_launch = open -a {app} --args --grid {grid} --login {first} {last} {password}
