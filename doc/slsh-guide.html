A user's guide

/$ slsh

said "slush"

A shell for Second Life. Your inventory is a filesystem, the region around you is a set of commands, and anything that wants an answer queues up at the prompt. It has no view — which is exactly why it can be scripted, piped and left running.

1Getting connected

Type slsh and you are at a prompt, in a region, as an avatar. The prompt shows where you are in inventory, and the first thing worth typing is where: 

$ slsh
/$ where
Testville at 128, 128, 25
acting as group Example Builders (87f07e57-…)
/$ who
 1  Example Resident                    3.1m  d8467e57-…
 2  Another Resident                   12.4m  7ed37e57-…
/$ quit

Leaving does not log the avatar out. That is the point of the arrangement: a daemon called slgod holds the session to the grid, and slsh attaches to it. The shell starts instantly because there is no login to wait for, several programs can drive one avatar at the same time, and closing the shell leaves the avatar standing where it was.

quit is what leaves, and exit is the same command under a second name, so neither has to be remembered; at an empty prompt ^D does it too — at the end of a line, that is; in front of anything it deletes forward instead. None of them takes a daemon-held avatar down. That is logout, against a named avatar, and it is a separate act on purpose.

The other way is --direct, where the shell logs in itself and holds the session for as long as it runs. It needs no daemon, but every start pays for a fresh login and quitting logs the avatar out. Use it when there is no daemon to attach to.

Running one command, or a file of them

Neither form has to be interactive. -c runs one command line and exits; -f runs a file of them. Both are how slsh ends up inside shell scripts and makefiles. 

$ slsh -c "ls -l Objects"
$ slsh -f tidy-up.slsh
$ slsh --direct -c where            log in, ask, log out

Which daemon, and which avatar

--addr HOST:PORT says where slgod is. Without it the address comes from addr = in the configuration file, then from an sl-host command if you have one, then from this machine — which is the usual case, so most people never pass it.

One daemon can hold several avatars, and four things decide which one a command drives, in descending order of strength:

--agent NAMEthis command and nothing else (-a for short)
SLGO_AGENTevery command in this shell
agent = NAMEin the configuration file, for this machine
nothingthe daemon's default: the session it has held longest

Interactive slsh says at the top which avatar it got, whether or not one was named — worth reading, because the default depends on the daemon's history and nothing on disk records it. It is the avatar's display name rather than the profile handle, and it is the region and the daemon's address beside it. A -c or -f run prints no banner at all, so a script that cares which avatar it drove has to name one.

For --direct, accounts live one file per account in ~/.config/slgo. The directory must be mode 700 and each file 600 — these programs refuse to read credentials anyone else can. A password stored as its $1$… digest works and is preferred: that is the only form that ever leaves your machine.

2Finding your way about

There are seventy-odd commands, and three ways to ask about them. They answer different questions and it is worth knowing which is which.

helpwhat groups of commands exist; help region lists one group
place --helpwhat that command takes: its flags, one line each
man placewhat that command is for, at length, with examples — and the same flags a paragraph each

help is grouped because one list of seventy is a wall rather than an answer. A command can be in more than one group where it belongs in both. 

/$ help
Commands are grouped.  For a group:  help GROUP
For everything:        help all
For one command:       COMMAND --help, or man COMMAND

  avatars     the avatars slgod holds, and how their sessions are doing (7)
  giving      handing items to somebody, and taking what is offered  (6)
  inventory   folders and items: what you have, and moving it about  (14)
  people      finding people, talking to them, friendship            (12)
  region      where this avatar is and what is around it             (30)
  shell       slsh itself                                            (6)
  simulator   what this grid supports                                (3)
  waiting     things that want an answer, and how to give one        (7)

man is the long answer — what a command is for, why it behaves as it does, what it cannot know, and what to type instead when it refuses. Where a page has flags it takes them a paragraph at a time, under Options, saying the part --help's column has no room for. Where this guide is a walk through, a man page is the whole of one command.

Tab completes a command name or an inventory path, and up and down walk through what you have typed before. Both are worth using from the first minute.

3The prompt and its modes

The prompt is where you are in inventory, so it changes as you cd about. Two other things can appear in it, and both mean something.

/Objects$command mode, in the folder /Objects
(2) /Objects$the same, with two things waiting for an answer
Local>chat mode, talking to the region
1 text>typing the first line of a multi-line answer

Command mode is the outer one, because that is what a keyboard is mostly for. chat goes inward and Escape comes back out. Each mode remembers the line you had half-typed in it, so switching never loses what you were saying, and each has a history of its own, so the arrows never offer a command where a remark belongs. 

/Objects$ chat
Local> hello everyone
14:22:07 > [Local] hello everyone
<ESC>
/Objects$

Anything said to you is printed as it arrives, above whatever you are typing, in either mode. You never have to leave what you are doing to see chat, and chat never eats your half-typed command. Start in chat mode with --chat, and change the key that leaves it with --escape KEY.

While a command runs there is no prompt. A prompt means the shell is ready for the next line; what you type during a long command waits its turn and arrives when the command is done.

4Inventory is a filesystem

cd, ls, pwd, mkdir, mv and rm mean what they mean in any shell. Two do not: cp PATH NAME copies an item under a new name rather than to a destination, and find TEXT [PATH] looks for names containing TEXT rather than taking a path and predicates. The tree is the one the viewer shows, and / is the root of it.

Ids are shortened to their first eight characters throughout these transcripts — 40f17e57-… — so the columns are narrower here than on a real terminal. Everything else is byte for byte what the command prints. 

/$ cd Objects
/Objects$ ls
/Objects/lantern
/Objects/sign
/Objects/spares
/Objects$ ls -l                    kind, when, id, path
object     2026-08-02T15:09:30 40f17e57-… /Objects/lantern
object     2026-07-29T09:41:12 91357e57-… /Objects/sign
folder     -                   1ae57e57-… /Objects/spares
/Objects$ ls -lt                   newest first
/Objects$ ls -r spares             and four levels below it
/Objects$ ls -l lantern            not a folder: lists what it names
/Objects$ find lantern             names containing it, from here down

Names are not unique, so ids are accepted everywhere

One folder can hold a dozen things called "lantern" — the grid allows it and viewers do it. So every command that takes a path also takes an item's id, which is what ls -l prints them for. When a name is ambiguous, list, then work by id.

The date column is the whole date, down to the second, because that is the other thing that tells two copies of one name apart — and it is what rm --newest and rm --oldest choose by. Reading commands take the first of several and think nothing of it; rm does not, for the reason below.

A path that is not a folder lists what it names, the way ls of a file reads in any shell — which here is the way to see several of one name by themselves rather than picking them out of a whole folder by eye. A uuid works as the path too, and a folder wins where a folder and an item share a name. 

/$ ls -l /Scripts/greeter
script     2026-08-07T12:06:57 cb567e57-… /Scripts/greeter
script     2026-08-07T11:26:01 e9d97e57-… /Scripts/greeter
script     2026-08-07T11:25:53 7e277e57-… /Scripts/greeter
/$ ls /Scripts/greeter          without -l, three identical lines
/Scripts/greeter
/Scripts/greeter
/Scripts/greeter

Paths escape rather than forbid: / separates, \/ is a slash inside a name, \\ is a backslash, and quoting with " or ' works as well. A name with a space in it wants quoting.

Deleting, which has no undo

rm refuses a name that means more than one thing, and deletes nothing. Deleting here is permanent, and which of a dozen identically named items went is not a thing to work out afterwards. Three flags answer the question of which — and they are one choice, not three options, so any two of them together is refused as well. 

/Scripts$ rm greeter
slsh: rm: "greeter" is 3 things here: say --newest or --oldest to delete one of
them, --remove-all-copies for all 3, or name one by its id, which ls -l prints
beside the date
/Scripts$ rm --oldest greeter
greeter: removed the oldest of 3, acquired 2026-08-07T11:25:53 (7e277e57-…)
/Scripts$ rm --remove-all-copies greeter
greeter: removed 2 copies

--newest and --oldest name what they took — the date they chose by and the id — since a count would not say which one went. They refuse rather than guess when the dates do not settle it: inventory dates are whole seconds, so a folder copied in one go holds items stamped alike, and a folder has no date at all. Either refusal points at the id, and the other end of the pile may still have an answer.

* means every item in the folder — never its subfolders, and it is not a glob — and is refused without --remove-all-copies, so the sweeping form has to be asked for on purpose. 

/Scripts$ rm *
slsh: rm: * means every item in this folder: say rm --remove-all-copies * if that
is what you want
/Scripts$ rm --remove-all-copies *
*: removed 645 items

Each removal is a round trip, so six hundred of them take minutes. The count climbs in place while it works, and is written to the terminal rather than to a file, so a redirect catches the result and not the flicker. Nothing here goes to the trash on its way out: rm deletes at once, and what is in the trash is what a viewer put there. emptytrash throws that away, permanently, and finds the trash by what it is rather than what it is called — so it works on an account whose viewer named it something else.

mv tries its destination as a folder first. A rename to a plain word that happens to be a folder beside the item moves it there instead, and reports success either way. When renaming, it is worth knowing what else is in the folder.

5Where you are, and who else is

wherethe region, the position, and the group being acted as
parcelthe land underfoot: who owns it, and what it permits
whowho else is here, nearest first, with their keys
mapthe same people as a picture, which says which way rather than how far
lookwhat the simulator said about the region when this session arrived
objectsthe objects the region has described; -c for the prims inside each
caps · features · lslwhat this simulator grants, supports and implements

objects, caps, features and lsl all take text to filter by, so lsl llSensor answers what this grid's LSL actually has rather than what the wiki remembers. objects groups what it found by owner.

where and parcel are the two halves of one answer, and everything that puts the avatar somewhere else — a position, another region, a place kept in inventory, a seat — is the chapter after this one.

The land under you, which is the half that decides things

A region is one place to the protocol and several places to everybody standing in it. What decides whether an avatar may build, fly, run a script, hear a stream or stay at all is not the region: it is the parcel, and a region holds dozens of them. So when building stops working for no reason the region explains, parcel is the command that answers it — and where, which names the region and the coordinates, is only half of where you are. 

/$ where
Pelmar Reach at 28, 72, 2001
acting as group Lorn Family (488f7e57-…)
/$ parcel
Thrushmoor
  local    5
  owner    f5d57e57-…  KerraYule Resident
  group    488f7e57-…  Lorn Family
  area     2048 m², within 12,48 to 44,112
  prims    486 of 937  (owner 485, group 1, other 0, selected 0)
  allows   group build, fly, group object entry, scripts, group scripts, landmarks
  refuses  build, object entry, terraform, damage, voice, search listing
  pass     L$10 for 1 hour
  claimed  2024-05-03

The two lists are what the command is for. This parcel allows group build and refuses build, which is one line saying that an avatar acting as Lorn Family may rez here and the same avatar acting as nobody may not — and when the refusal comes it will talk about the land, which sends you looking in the wrong place. That is the same trap as the group below, seen from the other end.

The parcel is asked for rather than remembered, and asking is quick: measured on Agni, every kind of parcel question was answered between 90 and 130 milliseconds. The round trip is worth it, because land is sold, renamed and divided under a standing avatar, and an answer kept from the moment of arrival would be exactly as old as the arrival. If the ask goes unanswered the command falls back to what the session was told when it got there and says so in as many words, so a stale answer can never be mistaken for a fresh one.

A point describes any parcel in this region rather than the one underfoot — parcel 60,60 for the land two parcels over, in metres from the region's south-west corner, the same numbers where prints. The avatar does not move and nothing is asked of it. --region lists every parcel in the region, and --map draws them, one character to a parcel, with a key underneath.

The blanks are Linden's own protected land — the roads and waterways a mainland region is laid out around — and the . is a rez zone inside them. They are drawn as ground rather than as a letter because that land is most of the region by area and none of it is anybody's, so a letter would put the loudest mark in the picture on the one parcel nobody is asking about. Each parcel is a letter and a colour on a terminal: the colour is what tells two apart at a glance, and the letter is what tells them apart at all, since a picture in a file or down a pipe has no colour in it.

Both of those pictures want something the region only ever says once. The overlay carrying the property lines arrives in four packets as the avatar arrives and never again — a request for it is answered with silence, and the only way to fetch it is to arrive again. So they come from whatever held the session at that moment: a shell attached to a daemon that has been up for hours gets them, and a session that has just logged in and not moved may not, in which case the command says so rather than drawing an empty region. The names on top of the shapes are a question apiece, about a tenth of a second each, so fourteen parcels take two seconds.

Asking about a parcel moves the simulator's idea of which parcel this agent has selected. A viewer attached to the same session through slgod will notice: its About Land floater redraws to show the parcel that was asked about, which is not the one under its avatar. That is the grid working as designed, but somebody watching the screen while somebody else types parcel 200,200 sees the panel change under them.

The group you act as

Land usually grants building to a group rather than to people, and a headless login starts acting as nobody. So an avatar that cannot rez on land it is plainly entitled to is usually an avatar with no group active — and the refusal talks about the land, which sends you looking in the wrong place. 

/$ group
active  87f07e57-… Example Builders
        29af7e57-… Testville Gardeners
/$ group testville gardeners     case does not matter
acting as Testville Gardeners (29af7e57-…)
/$ group none
acting as no group, which is what land that grants building to a group refuses

An empty list is not proof of anything: the simulator volunteers the list shortly after login and answers no question about it, so "no groups are known here" means either none joined or none told yet.

invite asks somebody into one of those groups. The person is read off the front of the line and the rest of it is the group, so neither name needs quoting, and the group is named every time — it never means "whichever one I am acting as", because what this does reaches a person who is not at your prompt and no message cancels an invitation. 

/$ invite Example Resident Example Builders
asked Example Resident into Example Builders (87f07e57-…), in its everyone role
nothing answers an invitation, so this says what was sent and not what became of it; they see it as an instant message and it waits for them
/$ invite Example Resident Testville Gardeners   a member, but not one who may invite
slsh: invite: sl: this avatar cannot invite into that group: this avatar is in "Testville Gardeners" (29af7e57-…) and its role there does not carry the power to invite

Nothing answers an invitation. The grid's reply to it is a trusted message that travels between simulators, so the sender sees no acknowledgement, no refusal and no answer — which is why the two things that can be checked are checked before anything is sent: that this avatar is in the group, and that its role there carries the power to invite. Whether the person joined is not visible from this side at all; their answer goes to the group.

The land you are allowed to see

Land is rated general, moderate or adult, and an avatar refused entry to a region is told its maturity rating is wrong. That sentence names two quite different causes and picks neither: the preference, which is the highest rating the account has asked to be shown, and the ceiling, which is the highest it is permitted to ask for. The first is a setting; the second comes from age verification and no client can raise it. 

/$ tp Nightmire Sea 128 128 25
teleporting to Nightmire Sea at 128, 128, 25
slsh: tp: sl: the grid refused the teleport: … RegionTPAccessBlocked: "You aren't allowed in that Region due to your maturity Rating. …"
/$ maturity adult
this avatar is shown land rated adult and below
/$ tp Nightmire Sea 128 128 25
teleporting to Nightmire Sea at 128, 128, 25
Nightmire Sea at 128, 128, 26

maturity asks, and prints what the grid granted, which is the lower of what was asked for and what the account allows. Granted what you asked for, the preference was the whole problem and is now fixed — permanently, since it is an account setting that outlives the session. Granted something lower, that is the ceiling, and the rest of the job is on the account page rather than here.

A bare maturity reads both numbers without asking for anything. They arrive in the login response, the daemon hands them on, and it prints the preference and the ceiling side by side — shown land rated moderate and below, and this account may go as high as adult — which says which of the two a refusal was about before anything is changed. It is what the daemon was last told: a change made through maturity RATING is followed, one made on the account page or in an attached viewer is not seen until the next login.

Who is about, as a picture

who answers half the question and cannot answer the other half: a listing says somebody is twenty metres away and nothing at all about which way, and three people at twenty metres are a crowd in one direction and a scattering in another. map is the other half, drawn as characters on a grid.

North is up and east is right, which is what the region's own coordinates already mean. The star is this avatar, an o is somebody within three metres of its height, a ^ somebody higher and a v somebody lower — three metres being about one storey, so an o is somebody who could be walked over to and a ^ is somebody on the roof. Two or more people in one cell are drawn as the count, and ten or more as a +, because a 9 there would be a lie.

The picture is wider than it is tall on purpose. A character cell is taller than it is wide, so a grid with as many columns as rows comes out taller than it is wide and a square region looks like a doorway. The rows are what is chosen and the columns follow, as many as it takes for a square of ground to look square. How much taller than wide a cell is belongs to the font you read a terminal in rather than to anything here, so it is the map_ratio setting, written height first; 7:3 is what the font this was measured in turned out to be, and set map_ratio 2:1 is how to have the obvious guess back.

--region draws the whole 256 metres rather than the 64 around the avatar, --span changes how much ground the close picture covers, and --rows changes how finely either is drawn — more rows buy detail rather than reach, which is why the size printed under the grid does not change when they do. Somebody on the friend list is drawn in colour and nobody else is, because the question a picture is usually being read for is not "who is here", which who answers, but "where is the person I am looking for". The colour only ever reaches a terminal: a picture written to a file, or one from -c or -f, has no escape sequences in it at all, since that file is usually on its way back through . listing.

The avatars drawn are the ones the simulator has described to this session, which is what is within the draw distance and not everyone in the region. So --region draws the whole region and can still only mark the people this session has been told about: an empty corner is a corner nobody has described, not a corner with nobody in it. Read it with where and the count under the grid rather than reading the blank cells as fact.

6Getting somewhere else

There are four ways for an avatar to end up somewhere it was not, and they are separate mechanisms rather than variations on one another: a position, a region's name, a landmark out of inventory, and a seat. All of them wait for the arrival rather than reporting that the request went out, and what each prints afterwards is where the avatar actually ended up, read back from the session.

tp X Y Za position — in this region, or in whichever region that position is really in
tp REGION [X Y Z]another region, by name, anywhere on the grid
tp homewherever this account’s home is set, which no map lookup is needed for
regions NAMEwhat a name matches on the grid's map, and where each one is
landmarkthe places kept in inventory; --go goes to one, --home goes home, --set-home makes here home
neighboursthe circuits a border crossing needs; on and off change it
sit · standonto a seat and off it again, which moves the avatar several metres

Three numbers, and what they mean past the edge

tp 128 128 25 is a position in this region, in metres from its south-west corner — the numbers where prints. A region is 256 metres square and the grid is regions laid edge to edge, so tp 300 128 25 is neither an error nor a point in this region: it is 44 metres into the region to the east. The shell works out which region owns the point and teleports there, in the way that the twenty-fifth hour of Monday is one in the morning on Tuesday. It generalises as far as the arithmetic does, so an x of 1000 is three regions east and 232 metres in, and costs exactly what 300 does.

A coordinate written with a leading ~ is measured from where the avatar is standing rather than from the region's corner: ~ on its own is that axis left alone, ~10 is ten metres further along it, ~-10 is ten metres back. It is per axis, which is why it is a mark on the number and not an option — an option would make all three relative or none. Two of the same relative teleport go twice as far, where two of the same absolute one go nowhere the second time, and that is the point of it. 

/$ tp 128 128 25              a position in this region
/$ tp ~10 ~ ~                 ten metres east, same y, same height
/$ tp ~ ~ ~50                 fifty metres up, without moving
/$ tp 300 128 25              44 metres into the region east of here
/$ tp -10 128 25              246 metres into the one to the west
/$ tp 128 -1 25               255 metres into the region to the south

The height is the simulator's to settle, and what it does with it was measured rather than guessed: the avatar arrives at whichever is higher of the height asked for and the ground under the point, plus about a metre. A request for 30 came back as 31, one for 2001 as 2002, and one for 0 as the ground. So asking for nothing is asking for ground level rather than for a fall, and asking for a height above the ground is honoured rather than corrected.

A region by name

Anything that is not three numbers is a region's name, joined back up with spaces, so a name with a space in it needs no quoting; and the last three words are a position when all three are numbers. A name with no position arrives in the middle of the region, at 128, 128, which is where a viewer puts somebody who typed a name into the world map and said nothing about where in it. 

/$ tp Example Landing
/$ tp Example Landing 33 73 1000.5
/$ tp --wait 60 Example Shallows

The height asked for by a bare name is nothing, which the simulator reads as ground level — and ground level in the middle of a region is sometimes under water. Sandbox Goguen's water is at 5 metres and its middle is below that, so tp Sandbox Goguen arrives there submerged. Name a height to land somewhere else.

The name goes to the grid's map, whose search matches from the start of a name and ignores case. So one word finds every region beginning with it, and regions is that same search run for its own sake — which is how to find out whether a name is enough before typing it at tp. 

/$ regions Pelmar
Pelmar Reach                      43648, 43648   moderate  47991483540340736
Pelmara                           43712, 43584  general   48061852284502016
Pelmar Bay                        43584, 43584   moderate  47921114796146688

Each line is a region: its name, the square it occupies on the grid, its maturity rating, and its handle — the square's south-west corner in metres packed into one number, which is how every message that names a region names it. Several matches is the ordinary case and not a mistake, and there is no way to ask for an exact name because the map has no such question in it.

A name that matches one of them exactly is that one as far as tp is concerned, even where longer names share its prefix — a name typed in full is not an ambiguous name. Anything else that matched more than once is printed in that same listing, and refused. Refused rather than guessed at, because the guess is not a listing you can read again: it is an avatar somewhere it was not sent, with everything the shell knew about the region it left thrown away on the way.

The map's reply has fields in it for how many avatars are in a region, what the region allows, and how high its water is, and Second Life sends all three as zero for every region every time. So regions cannot say whether a region is up, or busy, or empty. A region listed there is a region that exists; it is not a region that will have this avatar, since an estate can refuse an arrival for reasons the map has no field for.

What a teleport costs, and what it throws away

About four hundred milliseconds, and up to about five seconds. Twenty round trips between Pelmar Reach and Sandbox Goguen — forty moves — were measured end to end at between 355 milliseconds and 4.95 seconds, with a median of 425 and none of them failing. So it is quick, and the slow tail is seconds rather than fractions of one, which is worth knowing before anything treats a teleport as instant. The line saying where it is going is printed before the waiting starts, because a shell that has silently stopped answering is indistinguishable from one that has hung. The wait is thirty seconds, and --wait changes it.

The session goes with the avatar. slgod hands the circuit to the next simulator rather than logging in again, so the avatar that arrives is the same session that left, a viewer that had taken it keeps it, and every shell attached to the daemon carries on as it was. That is a good part of why a teleport is cheaper than the relog it replaces.

What does not go with it is everything the old region said. Local ids are the region's own numbering and the next region hands the same numbers out again, so what the shell knew about objects is not merely stale after a teleport — it would name something here as confidently as it named something there. All of it is dropped: the objects, who owns them, what they are called, what is inside them. Anything a script was holding across a tp has to be asked for again. What survives is what was never a region's to say: who people are, inventory, friends, and the offers and dialogs still waiting for an answer.

A line of notice says so: the avatar is now in Sandbox Goguen -- what the last region described is gone. It comes from the same place arriving chat does, so it appears whoever asked for the move — another client attached to the same daemon, a lure somebody offered and you accepted, a session re-established after the circuit was lost. It appears for your own tp too, alongside the command's own answer. A teleport therefore prints twice, and the two lines say different things: one is the session's news, the other is the answer to what was typed.

A refusal is the grid's and not the shell's, and it arrives in two voices — a key a program could act on and a sentence meant for a person — both of which are printed, because they are not always the same string. The session is left standing where it was: a refusal costs the request and nothing else. Silence is the third answer, and it is why the command waits and reads back at all: a teleport within a region that is refused produces no error and no reply of any kind, so without the reading back a refusal would be indistinguishable from success and every position computed afterwards would be wrong.

Landmarks, which are places said by name

landmark is the command for a place said by name, where tp is the command for a place said in numbers. A landmark is an ordinary inventory item — the grid's own way of writing a place down — and this lists the ones the avatar holds, says where one of them goes, makes one of wherever the avatar is standing, and goes to one. 

/$ landmark
8 landmarks
  /Favorites/Workspace
  /Ravensdon/Ravensdon Boutique Shop
  /Landmarks/stage 0 here
  /Landmarks/stage 0 daskwell
  /Landmarks/stage 3 thrushmoor             3bea7e57-…
  /Landmarks/stage 3 thrushmoor             656a7e57-…
  /Landmarks/stage 3 daskwell hub
  /Landmarks/Workspace
/$ landmark stage 3 daskwell hub
stage 3 daskwell hub
  in       /Landmarks
  region   8cf47e57-…
  at       132.97, 145.62, 76.59
  item     40b37e57-…
  asset    b86e7e57-…

They are listed as paths so that two landmarks of one name can be told apart, and where the path is the same for both — which is the ordinary way to end up with two, since making one twice files both under Landmarks — the id printed beside each is the only thing that does. The avatar moves in --go and --home and in nothing else. That is deliberate: if going somewhere were the bare form, reading a landmark and being somewhere else afterwards would be one typo apart. For the same reason none of the four verbs has a short letter, since -g beside -m is exactly the typo a whole word prevents. 

/$ landmark --make Pelmar Reach Workshop   of where the avatar stands
/$ landmark --go Thrushmoor
/$ landmark --home
/$ tp home                          the same trip, said shorter

Home, and setting it

Home is the one landmark nobody has to own. Going there is the same message with the null id in it, which the grid reads as home rather than as an error, so it costs no inventory lookup and needs no item; tp home is the same trip under a shorter name. landmark --set-home is the other half: it makes where the avatar is standing the place home is. There is no position to give it, because the message carries no region — whichever simulator receives it is the region — so the way to move home somewhere else is to go there and then set it.

Home may be set on land this account controls and at a mainland infohub, and nowhere else. Both answers arrive as an alert rather than as a reply, with no field anywhere saying that home moved, so what is printed is the grid’s own sentence: 

/$ landmark --set-home
setting home to Pelmar Reach at 26, 66, 24
Home position set.
/$ landmark --set-home       a region away, on land this account does not control
setting home to Corvane at 44, 66, 24
slsh: landmark: sl: the grid would not set home here: You can only set your 'Home Location' on your land or at a mainland Infohub.

Where home is cannot be read. Nothing in the protocol answers the question, so the only way to find out is to go there and look: landmark --home, and then where.

What the asset holds is a region and three numbers, and that is the whole of it: 96 bytes of text, with no region name, no parcel, no owner and no description of anything in it. That is why the region line above is a uuid rather than a name — the only way this program has of finding a region is the map's search by name, and a landmark carries no name to search for, so a line that printed something place-shaped beside it would be an invention. Going there needs no lookup at all, because the simulator turns the region id into a handle itself, which is why this is not tp with a map lookup in front of it: three measured trips took 1.0 seconds each.

It is also why a landmark remembers where you stood and nothing whatever about what was there. The parcel may have been sold, the platform stood on taken away, the region emptied — and none of that is in the asset and none of it is said on arrival. A landmark into what is now empty air is an arrival in empty air followed by a fall: one pointed at 1000 metres was measured putting the avatar on the ground a minute later, with nothing reported by anybody. parcel is the command that asks what the far end turned out to be.

Arriving somewhere is not the same as staying there. The command reports the arrival and stops watching. Measured twice on Agni, a landmark into a parcel with a security orb on it succeeded: the avatar arrived, the command printed the position it had arrived at, and about one and a third seconds later the parcel's own object teleported it home. 

/$ landmark --go Ravensdon Boutique Shop
going to Ravensdon Boutique Shop
Dell of Ashes at 113, 109, 1011
/$ where                        one second later
Pelmar Reach at 26, 66, 24

Those two answers are a second apart and they disagree about which region the avatar is in, with nothing between them saying why. What the grid sent afterwards was two alerts and another teleport — "You have been ejected from this land.", then "You have been teleported home by the object … on the parcel …" — and nothing in this command's path reads those alerts, so the ejection is invisible to it. A position printed here can be true when it is printed and false a moment afterwards, with nothing saying so. If a landmark lands somewhere it should not be, run where again.

Every inventory item has an item id and an asset id. ls -l prints the first, and the second is the one every landmark message takes. They are both uuids and nothing about either says which it is — and sent the wrong one, the grid says nothing at all: the item id, and a uuid that was nothing whatever, were each answered with perfect silence, waited out to twelve seconds apiece.

That is why a name is what you type here. A name is looked up in the listing, which is the one place the two ids are told apart correctly; a uuid may be typed and is looked up in that same listing as either of an item's two ids, and one this avatar does not hold is refused rather than sent. The one wrong id the grid is not silent about is the null one, which it reads as home and obeys in about a second — so a landmark with no asset id in it is refused rather than being allowed to become a quiet trip home.

A link to a landmark is not a landmark and is left out of the listing, because a link's asset id is the item id of the thing it points at, so following one would produce exactly that silence. So is anything in the trash — which is what a viewer deleted, since rm here destroys rather than files away. A landmark in the trash still has a name and would still teleport perfectly well, which is the problem. A name whose only answer is in the trash is told so, and told where it is, and mv moves it back out — after which it is a landmark again.

Walking over a border

A teleport crosses the grid; walking crosses a border, and the second needs something the first does not. A simulator will not hand an avatar over the edge of a region to a client that holds no circuit to the region on the other side — it does not refuse, it simply does not do it — so with neighbours off the avatar walks to the border and stops there. Measured: at Pelmar Reach's west edge, pinned at x=0 for twelve seconds, and at x=255 for twenty-four seconds coming the other way. With a circuit open to Pelmar Mill the same walk was over the border in two seconds. 

/$ neighbours
neighbours are off; this avatar cannot walk over a border
/$ neighbours on
neighbours are on; no circuit is open yet, and the first offer can take a minute to come round
/$ neighbours                   a few seconds later
neighbours are on, 3 circuits held
Kelva Sands                       43647, 43647   203.0.113.9:13021     44 heard
Pelmar Mill                       43647, 43648   203.0.113.17:13010    41 heard
Orrick Gate                       43648, 43647   203.0.113.28:12035    100 heard

The middle answer is the ordinary one and not a failure. Turning them on asks for nothing and opens nothing: the simulator offers a neighbour of its own accord and repeats the offer for as long as it goes untaken, so the circuits arrive by themselves and the way to see them is to run neighbours again — which is the third line above, with three of them held. How long that takes varies a great deal. On 2026-08-23 the first circuit opened between twenty and sixty seconds after on, and more followed over the minute after that, so an empty listing straight afterwards is worth waiting out.

The address on each line is the simulator's own, and it is there to say which host that circuit is to. It is not an address to type anywhere: a region moves between machines, so the number is true of that circuit at that moment and of nothing else.

It is off unless somebody asks because each neighbour costs a socket and a share of the traffic for as long as it is held, and the number of them is however many regions surround this one — four around Pelmar Reach, up to eight anywhere on the open grid. A neighbour describes itself fully and unprompted, 59 object updates and 51 pieces of terrain in the first thirty seconds when it was measured, and none of it is kept. That is a price worth paying for an avatar somebody is walking about with and a waste for one running a benchmark in a single region, which is why it is a property of the avatar rather than of the daemon holding it, and why it can be turned over while the session is up.

An empty listing almost always means "not yet" rather than "not near a border", which is what the middle line above is saying. Being in the middle of a region does not empty it: measured on 2026-08-23, standing 128 metres from all four edges of a 256-metre region held four circuits, one across each edge and none across a corner. The set changes as the avatar moves, and a teleport to another region or a crossing throws all of them away and opens the new region's own; a teleport within the region leaves them alone.

It belongs to the session and not to this shell. Turning neighbours on turns them on for the avatar, in whatever is holding the session, and it stays on after this shell exits; another client attached to the same daemon sees the same answer and can change it too. An avatar that is always driven by a person wants neighbours = yes in its profile under ~/.config/slgo, which is the right place for it.

Nothing this shell can ask about lives in another region. What is over the border is not in objects, not in who and not in the object cache, because local ids are each region's own numbering and a neighbour's would name this region's objects. The packet count in the listing is there to say the circuit is alive, and a line reading "(no handshake yet)" a moment after it opened is an offer that came to nothing.

Sitting down, which is also a way of moving

sit is filed here rather than with the furniture because a sit moves the avatar, and that is the part to know before anything else. It is not a request to sit on something already within reach: the simulator picks the avatar up and puts it on the seat, over whatever is in the way, from several metres off. Measured on Agni, a box seven metres away seated the avatar as readily as one half a metre away, in about a tenth of a second, with no walk on the wire at all. Eleven metres was refused. So there is a range, it is somewhere between seven and eleven metres, and the number is not worth pinning down: what matters is that a near thing is sat on and a far one is refused in words.

Standing up afterwards does not undo the journey. That same run left the avatar six metres from where it had been standing when it got up again — 29, 72, 2001 before the sit, 35, 72, 2001 after the stand. Which is why both commands answer with a second line saying where the avatar now is, read back from the session and printed in the words where and tp use, so that where run afterwards agrees with it instead of merely being close. That run is written up in man sit and man stand, which are where the numbers above come from.

An object is named by the word the region calls it or by its key, which is how touch and take name one, and a name that two of them answer to is refused with both keys rather than guessed at — guessing costs more here than it does for touch, because the wrong guess moves the avatar.

A bare sit is the ground, and it is the case that moves the avatar nowhere at all — which is the sharpest way to see what an object sit does, since the position afterwards is the position before: 

/$ sit
sat on the ground
Pelmar Reach at 28, 72, 2001
/$ stand
stood up
Pelmar Reach at 28, 72, 2001

The two position lines are the same, and that is the whole of it: the avatar is exactly where it was standing. The ground is a different mechanism rather than a shorthand somebody thought of afterwards. Sitting on an object is a message, which the simulator answers by sending this avatar's own update back with the seat's id in it; sitting on the ground is a control flag the simulator replies to with nothing whatever, and what says it happened is the animation, which arrived 144 milliseconds after the flag when it was measured — so the shell asks for that animation to be relayed to it for the length of the command, and gives it back afterwards. A ground sit moves nothing, so the position line after one says the avatar is where it was, which is the confirmation and not an oversight: the command has one shape of answer whichever mechanism it used.

stand takes no argument, since an avatar sits on one thing at a time and the simulator knows which, and unsit is the same command under a second name: one is what the world calls the button and the other is what a script calls the function. It may take a moment, and that is the flag being held. A flag is edge triggered and once turned out not to be enough all of the time — a sit, a stand, a ground sit and a stand, each sent as the one before was confirmed, worked three times and then did nothing at all — so this does what a viewer does, which is not to send a stand but to hold the key, half a second at a time until the avatar is up.

A refusal arrives as an alert in about a tenth of a second and is printed in the grid's own words, unreworded, because they are the only part of a refusal anybody can act on — No room to sit here, try another spot. is what eleven metres gets. It is worth knowing that the grid's words are not always accurate: a key naming no object at all is refused with "Try moving closer. Can't sit on object because it is not in the same region as you", which is wrong twice over and is still the only thing said. Nothing answering is a third thing, and is reported as itself in different words again, because a sit is answered one way or the other in about a tenth of a second and silence is neither a yes nor a no.

7Wearing things

worn lists the attachments, wear puts one on, detach takes it off. The argument to wear is an inventory path or an id; the argument to detach is the name of the item something was worn from, which is what worn prints. 

/$ wear Objects/badge
badge is worn on HUD top right
/$ worn
left hand          lantern
HUD top right      badge
/$ detach badge
badge is no longer worn on HUD top right

Wearing adds. A bare wear puts the object on alongside whatever is already on that point, which is the viewer's Add rather than its Wear. --replace is the other one, and it says what it displaced. Without --at the object goes wherever the object itself says, and the line printed names the point the region gave back rather than one guessed here.

Wearing an item that is already on is refused. Two attachments from one item agree in every field a person could name one by, so detach would find both and be unable to choose.

8Objects in the world

take and place are a pair: take brings a rezzed object into inventory, and place puts one back out. move repositions something already standing there, and rez builds an object from a JSON description rather than from inventory. 

/$ place Objects/lantern
"lantern" a8de7e57-… (local 83565482) is at 129, 128, 25
/$ move lantern 128 130 25
lantern is at 128.0, 130.0, 25.0
/$ touch lantern
touched lantern, face 0
/$ take lantern
"lantern" a8de7e57-… (local 83565482) is in inventory as lantern

An object is named the way an inventory item is: by name, or by key where the name is ambiguous. Only what the region has described is findable — a region introduces itself once, and nothing beyond the draw distance is described at all — so an object that is not listed may be out of range rather than absent.

Joining and taking apart

link names the root first and everything that goes under it. unlink given a root takes the whole thing apart; given one prim of a set, it frees just that prim. 

/$ link chair seat "left leg" "right leg"
"chair" 5ef67e57-… (local 83565614) is one object of 4 prims
/$ unlink chair
"chair" 5ef67e57-… (local 83565614) came apart into 4 objects:
  5ef67e57-…                           chair
  76167e57-…                           Object
  8b537e57-…                           Object
  8c617e57-…                           Object
more than one of these is called "Object"; name one by its key, which "objects -c"
prints too

That is why it lists keys rather than printing a success line: a linkset answers to its root's name while the pieces keep their own, which for anything built by hand is often "Object" for all of them.

Permissions and faces

perms sets what the owner, the group, everyone or the next owner may do with a rezzed object, in letters: copy, modify, transfer, move. It answers in that order whatever order the flags were typed in, and at least one of them has to be. texture sets what a face looks like, or with no flags says what it looks like now. 

/$ perms --next cmt --everyone none lantern
everyone may now nothing
the next owner may now copy, modify, transfer
/$ texture -f 2 --id d8467e57-… lantern
lantern: face 2

9Notecards and scripts

cat prints a notecard or a script. new makes one, from a file or from nothing — a notecard made from nothing is empty, and a script gets a default { state_entry() { } } skeleton, because a script with no source is a compile error waiting for whatever runs it. save writes a local file into one that already exists — the two are different acts and have different names for that reason. 

/$ new --kind script --from flicker.lsl flicker
flicker 73427e57-…
/$ save flicker.lsl flicker
flicker: 81 bytes written, and it compiled
/$ cat flicker
default
{
    state_entry()
    …

A script that does not compile is still saved — the save succeeded and the compile failed, in that order — and the compiler's complaint is printed underneath. An inventory script is not running anywhere; it runs when it is inside an object.

Inside an object

An object holds inventory of its own, with its own ids. ls, rm and mv reach it with --in OBJECT, and so does new — making a script is an operation that exists in both places, and --in says which. The others above (cat, save) work on inventory only. 

/$ ls --in lantern
lsltext    flicker
/$ new --in lantern --from flicker.lsl flicker
flicker is in lantern and running
/$ stop lantern
stopped    flicker
/$ start lantern flicker
started    flicker

new --in compiles the script inside the object and starts it, which is what dropping one in does not do: drop copies an item in and leaves it there, unstarted. start and stop with no script named mean every script in the object, one line each, and they wait for the object to agree rather than reporting what they merely asked for. A script already in the state you asked for says already and nothing is sent.

10Talking to people

say puts one line into local chat without leaving command mode. chat enters chat mode, where everything typed is said until Escape. 

/$ say the lantern is lit
14:22:07 > [Local] the lantern is lit
/$ chat
Local> and the door is open
14:22:19 > [Local] and the door is open
<ESC>

Instant messages

im WHO TEXT sends one message and stays in command mode. im WHO with nothing after it opens the conversation in chat mode instead, which is what to use for a conversation rather than a remark. 

/$ im Example Resident are you about?
* new conversation with Example Resident
14:23:04 > [IM Example Resident] are you about?
/$ im Example Resident              no text: go and talk
Example Resident> I am here
<TAB>                              next conversation
Local>
<ESC>
/$ talk
*  1  Local
   2  Example Resident

In chat mode Tab cycles between conversations, so local chat and every instant message are one interface with a star against the one you are in. talk lists them without entering.

A name with a space in it is taken whole: the shell tries the longest run of words that names somebody, so im Example Resident hello says "hello" to Example Resident rather than saying "Resident hello". Quoting works too and is never wrong.

Finding somebody

A name is resolved from what this shell already knows, then from the avatars in the region, and — for profile alone — from a search of the whole grid. Only profile takes that last step, because reading a profile is public and harmless, while im and give reach out to whoever is found. lookup searches the grid on purpose. 

/$ profile Example Resident
Example Resident
  key       d8467e57-…
  born      9/15/2004
  payment   not revealed
  partner   nobody
  about     Building things, mostly badly.
  groups    2 listed, which is not every group they are in
  87f07e57-… Apprentice           Example Builders

The groups a profile lists are the ones somebody chose to publish, so it is what they say about themselves rather than a complete list.

Friendship, and handing things over

friends lists who is online, -a all of them. offer offers friendship; give offers an inventory item. Neither is a transfer: nothing moves until the other side accepts, and what they do is not reported back here.

An offer only reaches a client that is attached when it arrives. slgod relays it and does not keep it, so a shell started afterwards never sees it — and a one-shot slsh -c will not see one at all.

11Things waiting for an answer

A script puts up a dialog, somebody offers a teleport, an object asks permission to animate you, a group invites you in. They queue, the prompt counts them, and four commands deal with them. 

(2) /$ waiting
1  dialog      a lantern "on or off?"
                1 on, 2 off
2  teleport    Another Resident teleport: "Come and see this!"
                answer (takes it, and waits for the arrival), no, ignore
(2) /$ answer 1 on
pressed "on" on a lantern
(1) /$ ignore 2
2 is still waiting, and no longer counted; waiting -a lists it

A number keeps meaning the same thing. Answering one does not renumber the rest, so an answer 2 you had already half-typed still means what you meant; numbering starts again at 1 once the list is empty. no declines and tells whoever asked — a lure, an offered item, friendship, a permission request, a group invitation. A dialog is the exception: there is no message for its close box, so no drops it here and says a dialog cannot be declined, only left to expire.

A text box wants several lines

llTextBox is an editor rather than a field, so answer N with no text starts taking lines. Every line means itself.

^Dend the answer and send it, taking a half-typed line with it
<ESC>throw away what has been typed and keep the question
^Csend nothing; the question stays, and its number is named
 
(1) /$ answer 1
a sign asks: your name?
type the answer; ^D ends it, ESC starts again, ^C sends nothing
1 text> Example Resident
2 text> of no fixed abode
<^D>
told a sign 2 lines

Ordinary line editing works on the line in hand. For a scripted answer, answer --file PATH N sends a file's contents instead. A text box carries 254 bytes; more than that is refused before it is sent rather than truncated on the way.

When money is involved

A group invitation carrying a signup fee is never accepted by a bare answer N. The fee has to be typed back — answer 3 L$50 — and a wrong figure is refused by naming the right one. An invitation whose fee the message did not state is treated as costing something unknown rather than as free.

12The daemon and its avatars

agents lists the sessions slgod holds, then the profiles it could hold. The star is the default — what a command that names no avatar gets — and the arrow is the one this shell is driving. 

/$ agents
* example     Example Resident          Testville   <- this shell
  builder     Builder Resident          Testville
  helper                                stopped: logged out
  spare                                 configured

The states differ in what to do about them. configured can be started. stopped was put down deliberately and is left alone until asked for by name. failed will waste a login attempt if asked again too soon, and says how long it is waiting.

login NAMElog an avatar in and hold the session
logout NAMElog one out until it is logged back in via login
statushow this session and its circuit are doing
watchprint grid messages as they arrive, by name or all of them

A logout is remembered: slgod will not bring that avatar back on its own, so nothing is fighting you while you use it elsewhere — and login afterwards needs -f, because undoing a deliberate stop should be deliberate too. Both refuse to be casual: logout will not take a session that clients are attached to, and names them instead. 

/$ status
Example Resident (example) in Testville
  simulator   Second Life Server 2026-08-03.30838755483
  packets     49309 in, 14714 out (0 resent, 0 abandoned)
  duplicates  1
  clients     1
  caps        21
  no handler for:
    AttachedSound                    21769
    SimStats                         4917

status is what to reach for when a session looks idle and you want to know whether it is idle or broken. The last list is messages arriving that this build has no handler for, which is how a protocol change announces itself. watch prints what is actually crossing the wire and opens a connection of its own, so watching everything for an hour does not disturb the shell you are typing in.

13A viewer, when you want eyes

slgod can hand its live session to a real viewer: the avatar never logs in twice, so the session a script is driving and the session you are looking at are the same one. viewer says where that is offered and whether anybody has taken it; viewer --launch starts one and logs it in — and refuses when a viewer is already running, because open -a raises an application that is already up without passing it the arguments again. A second launch would bring the viewer to the front, log nobody in, and report success, which is the one outcome worth refusing outright. 

/$ viewer
viewer logins at https://127.0.0.1:9000/
  add a grid with that login URI and log in as Example Resident
  no viewer has taken this session
  "viewer --launch" starts one and logs it in, with a password good for that one login
/$ viewer --launch
starting a viewer at https://127.0.0.1:9000/, logged in as Example Resident
  open -a Firestorm-OpenSim --args --grid slgod --login Example Resident PASSWORD
  the password it was given works once and expires in 5 minutes

The password is minted by the daemon for that one login and expires. Nothing is stored: a profile keeps only a digest, which is why the launcher cannot simply read one. The command that was run is printed underneath with the password replaced by the word PASSWORD, so what happened can be read, and pasted, without the credential going with it.

Three things have to be true. The daemon must have been started with -viewer ADDR, or viewer says so and names the flag. The viewer must be a build that can be pointed at a private grid — one that reads its own grid list, rather than a Second Life–only build, which ignores the login URI and comes up on the main grid with no explanation. And the grid has to be added to that viewer once, by hand, using the login URI printed above.

The endpoint is TLS and has no plaintext form: it carries the viewer password one way and the whole session — the session id, the circuit code, every capability URL — the other. The daemon keeps a self-signed certificate for it and says where, and the viewer will refuse to connect until that certificate is trusted. On Firestorm, accept its certificate dialog once, or append the file to user_settings/CA.pem before adding the grid — adding a grid probes the address first, and that probe has no dialog behind it.

Which viewer is launched, and how, are settings — see the configuration file.

14Files and redirection

Any command's output can be redirected, and a file of commands can be run with . — which together are the point of having a shell at all. 

/$ ls -l /Objects > listing
/$ echo done >> listing
/$ . moves                       run a file of commands

$ awk '{print "mv " $3 " /Objects/spares"}' listing > moves
$ slsh -f moves
slsh: cd: no folder "spares"
slsh: moves:1: cd spares
slsh: stopped; 43 lines were not run

A file stops at the first command that fails, naming the line it gave up on and how much it did not run. That matters because such a file usually begins by changing folder, and carrying on after that failed would run every line that follows somewhere else. A one-shot run exits non-zero when anything failed, so a script wrapping slsh can tell without reading the output.

Two listings of a folder that has not changed are identical, which is what makes them worth diffing and worth editing into commands. echo prints its arguments, which is how to write a note into a file you are building. It is the one command with no --help: it exists to put a line into a file, so it has to be able to print the word --help like any other, and a usage message there would be a command refusing to do the one thing it is for.

15The configuration file

~/.config/slsh/config — or $SLSH_CONFIG_DIR if that is set, or slsh under $XDG_CONFIG_HOME — as key = value lines with # for comments. A command-line flag always beats the file, and a misspelled key is an error rather than a setting that silently does nothing. A # is a comment only where a line begins with one: written after a value it becomes part of the value. Whether that stops the shell depends on the setting. The ones whose value is checked — escape, log and the five map_* — refuse it and say so. The ones that take their value as text — addr, agent, log_dir and the four viewer_* — take the comment with it, silently, and go looking for a profile or a daemon with a # in its name. 

# which daemon, and which of its avatars
addr    = HOST:PORT
agent   = NAME
escape  = ESC

# the transcript: on by default, and where it goes
log     = on
log_dir = /a/directory   # empty is ~/.local/share/slgo

# which viewer "viewer --launch" starts, and how
viewer_app     = the application to run
viewer_grid    = the grid nickname it knows the daemon by
viewer_launch  = open -a {app} --args --grid {grid} --login {first} {last} {password}
viewer_running = how to tell whether one is running already

The launch line is a template: {app}, {grid}, {first}, {last}, {password} and {uri} are filled in. It is a setting rather than a constant because neither the viewer nor the way it is told where to go is guessable — a viewer that cannot be pointed at a private grid will silently use the main one instead.

The transcript

slsh keeps one, and it is on to begin with. What goes in it is what you saw: every command you ran, everything each one printed, everything you heard and everything you said. One file per avatar, named after the avatar, in $XDG_DATA_HOME/slgo — ~/.local/share/slgo where that is not set. 

2026-08-26 15:56:29 $ where
2026-08-26 15:56:29   Testville at 33, 70, 2001
2026-08-26 15:56:33 * new conversation with Example Resident
2026-08-26 15:56:33 < [IM Example Resident] are you still at the build
2026-08-26 15:56:41 > [IM Example Resident] on my way

A command is written down before it runs, so one that hung is still in the file that says what happened. Two things are deliberately left out. Output you redirected — ls > listing — is output you did not see, so the command is recorded and the listing is not; it is in the file you sent it to. A man page read at a terminal goes through the pager rather than to the screen a line at a time, and is not recorded either.

What no shell can record is what happened while none was running. slgod stays logged in and goes on hearing whether or not you are attached, but a transcript is what somebody saw, and with no shell there is nobody to see it. set log off stops it keeping one, and leaves the file where it is.

Each mode has a history of its own and neither reaches the other's: at a command prompt up and down walk commands, and at a chat prompt they walk what you have said. A command offered in chat would be said out loud rather than run, which is why the two are kept apart. What comes back lands on the line to be edited; nothing is sent or run until you press Return.

The chat history belongs to the shell rather than to the conversation, which is what to reach for when a line goes to the wrong place: Tab to the conversation you meant, up until the line comes back, and Return sends it there. It keeps the lines you entered, so a blank line, a repeat of the line before it and a line you abandoned are all left out — the same rules the command history has.

While a multi-line answer is being typed the same editing keys apply to the line in hand, and the three that end it are described under Things waiting. Through slgod, leaving the shell leaves the avatar logged in; with --direct it does not.

A man page a screenful at a time

A page longer than the terminal is shown a screenful at a time, and has keys of its own while it is up. A page that fits is printed whole and does not wait; one redirected to a file or sent through a pipe is not paged at all, because there is nobody there to press space.

space · fforward one screen
Returnforward one line
bback one screen
d · uforward half a screen, back half a screen
pthe top of the page
/text · ?textthe next line containing text, the previous one
/ · ?the next match of the last search, the previous one
nthe next match, whichever way the last search went
q · ^Cleave

Type the search after the / or the ? and press Return; <ESC> or ^C abandons it and leaves the page where it was. At the end of the page, space and Return leave as well.

Nothing is erased and the screen is never cleared. Each screenful is printed under the last, so whatever was on the terminal before the page began is still above it, and the page itself is still in the scrollback after you have left it. b and u therefore print that part of the page again underneath, rather than carrying the display back up to it.
